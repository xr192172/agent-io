## §1 一句话结论

两轮**外部**审计（不是我自己的复核）一共报出 **9 个真缺陷**，其中 **5 个是 P0（会静默改错数据 / 静默不拦）**；
全部已修，**每一笔都带一条会变红的判据**，每次都先跑红再跑绿。
另外我自查出 **2 个 P0**（审计没提），也修了；其中一个是**我自己前一天修的东西只修了半边**，被审计当场抓到。

今天最贵的三条教训（不是 bug，是方法）：

1. **我引以为最硬的那道门，是台机器上的私货** —— 判据门拿 `source_root`（Windows 绝对路径）当路径锚，
   换任何一台机器都全红。本地 10/10 全绿只因两串字符串恰好相等。**它从来没在别的机器上跑绿过。**
2. **"没有测试"这件事，我的十道门里没有任何一道会红** —— 全仓最危险的组件（`fuzzy_match`）零测试，
   而它的错是把 `'helloworld'` 换成 `'hello world'`：不抛错、不告警、回执照旧说成功。
3. **我修的东西会被审计抓到"只修了半边"** —— 修复的质量不能靠"我改完了"，只能靠"谁能推翻它"。

## §3 新增/改的办法（比修 bug 更值钱）

- **`AGENTS-RULES 0.13` 补「冷环境从零走查」**：不知情复核仍共享我的工具链与已建索引 ⇒ 它看不见"门与门之间的缝"。
  而 P0-1 正是在「干净仓库 + 禁 spawn + 禁写 gitignore」的沙箱里按 README 走前十分钟暴露的。
- **新增 `0.14` 容错代码必须自带双向判据**：同义变形**必须仍命中** / 异义近似**必须不命中**；
  只有第一向的判据**不具鉴别力**。自查问句：**把这条匹配腿打断，有没有一条用例会红？**
  另附：同一种容错写在两级上时，**只改一级等于没改**。
- **判据闸退出码 0/1/2 三态**：「判出了红」与「压根没判」必须能分开（0.12 的直接推论）。
- **判据闸进 CI**：`.github/workflows/judge-gate.yml`（独立可调 + artifact + 三态码）。
  ★ 顺带发现：**它以前在 Linux 上本来就红**（就是 P0-4 那个锚）。
- **产者护栏**：`run-tests.mjs` 每轮打印"真册 `projects.json` sha256 前后一致" —— 真数据仓里**已经躺着 5 条测试夹具幽灵**，
  这条护栏是唯一能阻止它们再长出来的东西。
- **`npm test` 别名**（外审：`run_tests` 口径是读 `scripts.test`，而它自己没有 ⇒ 它测不了自己）。
- **README 首次五分钟**：写闸默认开，新人第一次 `edit_code` 必被拒。

## §7 我犯的错（同一天内，都记下来）

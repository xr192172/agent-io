# R17 规格 · racy-git：mtime 粒度竞态（`subagent:flake-hunt` 两段实测 · 2026-11-05）

> **问题名 = `racy-timestamp` / `racy-git`**（不叫 `mtime-granularity race`）
> ★ 理由：**名字要自带解法**。叫 `mtime-granularity race` 会让人去**调大粒度**（治不了，只缩小窗口）；
> 叫 `racy-git`（git 的 racy-clean 规则：条目 mtime 落在「索引写入时刻 − 粒度」之内 ⇒ 不做 confident-clean，必须重验）
> 会让人去**加 racy 判定**（正解）。已写进 `AGENTS.md` 0.28。

## 一、复现（读数全给）

```
· 只跑该用例（--test-name-pattern "⑤"）×10 ⇒ **10 PASS / 0 FAIL**
  ⇒ ★ **按给定步骤本机不复现**（主控转述的"连跑 3 次不一致"在单跑口径下不成立）
· 换口径才复现：跑**整个文件** ×10 ⇒ **⑤ 红 5/10**（run 1/5/7/8/10）· **⑦ 红 6/10**（3/4/6/7/8/10，同一根因）
  失败断言原文：`夹具无效：本轮没重同步过任何文件（resynced=0）⇒ 走不到取变更集那一格`
· 为什么单跑绿 / 整文件红：单跑进程冷，首次 ensureFreshIndex ~109ms；
  整文件跑时 ①~④ 已把 parse/db 模块缓存焐热 ⇒ 首次保鲜只要 **4~6ms** ⇒ 落进同一时间戳格
  ★ **「机器越快，flake 率越高」** —— 这句话必须写进账，否则下一个人在更快的机器上会以为是随机
· 直接复刻时序的临时脚本：20 次里 **9 次 resynced=0（Δmtime=0）/ 11 次 resynced=1（Δ=8~19ms）**
  「stat 闸判未变」与 `resynced=0` **20/20 对齐** ⇒ 单一成因
· 确定性钉死（fs.utimesSync(abs, m1, m1)，m1 = 索引记录的 mtime）⇒ **3/3 复现漏检**，
  且库内 content_hash 仍是旧值、符号表仍是旧内容，磁盘已是新内容
```

## 二、根因链（file:line）

```
1. index_freshness.ts:626
   if (prev && prev.modified_at === Math.round(stat.mtimeMs) && prev.size === stat.size) continue;
   —— **纯 stat 闸**，判"未变"就 continue ⇒ 文件根本不进 pending
2. symbols.ts:481-503（syncFilePrelude）**确实有**第二道 content_hash 闸
   （existing.content_hash === hash ⇒ skipped）
   但 626 的 continue 让 **syncFile 压根没被调用** ⇒ **那道闸不可达**
3. 触发条件 = **两个**：size 相同 ∧ Math.round(mtimeMs) 相同
   夹具 'export function a() { return 1; }' → 'return 9;' 恰好等长（34B）
   ⇒ 两个条件同时成立 ⇒ **"等长"不是巧合，是必要条件**；充分的真正条件是「两次写落进同一时间戳格」
4. 粒度实测（纯 fs）：间隔 0ms ⇒ **12/12 塌成同一 mtime**；1ms ⇒ 1/12；≥2ms ⇒ 0/12
   正差值是 **15.6 / 24~26 ms**
   ★ 而 index_freshness.ts:200-203 自陈「**等长改写且落在同一毫秒**」会漏判
     ⇒ **把真实格子低估了约一个数量级**（实际 8~16ms 级）= **0.12 缺陷（读数写错了自己）**
5. 同族 6 处：判"文件变没变"共 4 处全走 stat + 2 处缓存 key（见 §四）
```

## 三、★★ 单独拎出来的一句：「后置校验存在但不可达」

```
symbols.ts:481-503 的 content_hash 闸**确实存在且正确**，但它装在
  「决定要不要修」的**下游**，而不是「决定要不要信」的**上游**
⇒ 读代码的人看到 symbols.ts:5 那句"content_hash 未变 ⇒ 整文件跳过"会**以为**兜住了
⇒ 实际决策点自己已经短路
★ 共同形态：**校验装在"决定要不要修"的下游，不是"决定要不要信"的上游**
★ 这比"没有后置校验"**更危险** —— 没有的东西人会去找，有的东西人就不找了
```

## 五、同族 6 处：按「决策点 / 告警点 / 缓存 key」分处置

| # | 位置 | 角色 | 漏检后果 | 处置 |
|---|---|---|---|---|
| 1 | `index_freshness.ts:626` | **决策点**（要不要重解析） | 索引留旧 symbols/edges，**静默** | ★真 bug，必修 |
| 2 | `watch_project.ts:328` | **决策点**（watch 兜底要同步哪些文件） | 同上，且是「watch 兜底」这条安全网本身失效 | ★真 bug，必修 |
| 3 | `index_freshness.ts:231` `detectStaleIndex` | 告警点（STALE_INDEX 标注） | 少一条警告 | 用同一 helper 收编（不新增入口） |
| 4 | `index_integrity.ts:776` | 告警点（自检"不一致 N"） | 自检说"全新鲜" | 同上 |
| 5 | `health_cache.ts:46/58` | 缓存 key（`Math.round(mtimeMs)` 编进 key） | health 报告复用旧结果 | 同族，同 helper（低优先） |
| 6 | `symbols.ts:1563/1788/1969/1991` | 进程内解析缓存 key（`mtimeMs` 全精度比） | 同进程内复用旧 reexport/ns/dynImport 索引 | 同族；注意这里粒度一样粗 |

## 六、三条路 + 推荐

```
路 A · 夹具钉 mtime（测试侧）：写等长新内容 → fs.utimesSync(a, m, m)（m = 索引记录值）
  代价：2 行 × 3 个用例（④⑤⑦）
  好处：确定性复现**真实 OS 状态**（Δ=0 已实测真实出现）
  ★ 副作用：它把"依赖时序"变成"依赖夹具" ⇒ 若日后有人把断言改成恒真也看不出来
    ⇒ **必须配"删掉修复必红"的验收**
路 B · 夹具改不等长内容：1 行，今天必绿
  代价：**永久丢掉这条能力**（夹具不再可能发现 mtime 竞态）⇒ 想留覆盖就得再加一条专测 ⇒ **入口 +1**（违 0.25②）
路 C · 修生产（racy-clean 检测）：
  unchanged = size 相同 ∧ mtime 相同 ∧ **(Date.now() - mtimeMs > GRANULARITY)**
  落在窗口内 ⇒ 交 syncFile（其内部 hash 闸让它只读 + sha1 一次，**不重解析**）
  1 处判定 + 1 个常量，其余 6 处调同一 helper
```

### ★ 性能读数（"修生产"这条路的唯一拦路虎）

```
本仓 walkFiles 实测 **507 个源文件 / 6.6MB**（★ 主控说的 591 是按另一口径，差异应是 include_tests / 扩展名）
· 全量 读+sha1 = **55ms**  vs  仅 stat = **7ms**  ⇒ **7.9×**
· syncFilePrelude:475 是**先 readFileSync 全文再算 hash**，**没有** size/mtime 快路径
  ⇒ 改纯 contentHash = **每条查询 +55ms**（每个工具响应都跑）⇒ **不可接受**
· racy 窗口方案的增量 ≈ "查询时刻前 16ms 内被写过的文件"的 hash，通常 **1~2 个文件 < 1ms**
  ⇒ 成本几乎为零
```

### 推荐 = **C（修）+ A（与 C 同批，把 ⑤/⑦ 的夹具钉死）**

```
① C 单独就能让 ⑤/⑦ 确定性变绿（钉不钉 mtime 都一样：文件刚写过 ⇒ 落在 racy 窗口 ⇒ 必被重验）
   ⇒ **flake 是症状，修因即消**
② A 保留下来当**反例电源**：把"窗口内改写必须检出"钉成不靠时钟的输入
③ 排除 B：换来"今天绿"，代价是**永久失去**这条能力，且下一步就有人问"那等长改写真的没问题吗"
```

### ★ 同批要改的两处文案/注释

```
① index_freshness.ts:200-203 自陈「同一毫秒」⇒ 改成 **8~16ms 级**（并写 `GRANULARITY` 的取值依据）
   ← 这是 **0.12 缺陷：读数自己写错**
② 测试的失败文案今天红的是「夹具无效：本轮没重同步过任何文件」
   ⇒ 关灯的人会去**修夹具**。应改成点名缺陷：
   同一时间戳格内的等长改写必须被检出（stat 闸漏检）⇒ 索引会留旧内容
```

## 七、「该红的输入」（删掉修复后必须红 · 对未修代码已实测 3/3 红）

```ts
write(a, 'export function a() { return 1; }\n'); await ensureFreshIndex(db, project);
const m = fs.statSync(a).mtime;                  // = 索引记录值
write(a, 'export function a() { return 9; }\n'); // 等长
fs.utimesSync(a, m, m);                          // 同一时间戳格（确定性）
const r = await ensureFreshIndex(db, project);
assert.equal(r.resynced, 1);                     // 现状 0 ⇒ 红（实测 3/3）；修后 1 ⇒ 绿
```

## 八、量化


## 九、标准解法 4 个 + 取舍

```
① content addressing（每次比 hash）—— **排除**：+55ms/查询、7.9× stat，且 syncFilePrelude:475 无快路径
② **racy-clean 检测（太新 ⇒ 不信，重验）—— 选它**
③ 显式失效 / 写穿（self_writes 已有，覆盖 1 tick 内的工具自写）—— 保留作 1-tick 补充
④ 目录事件（USN journal / ReadDirectoryChangesW，本仓已有 watch_project）
   —— 排除：异步、平台相关，适合最终一致性而非正确性判据
★ 测试侧另用"固定时钟"（utimesSync）**只用于让检测点确定**，不用来替代修复
```

## 十、★ 诚实边界（0.17①，必须写进声明）

```
时间戳方案有**不可消除**的盲区：内容变了但 **mtime 被改小 / 保持不变**
  （`tar -p` / `unzip` / `cp -p` / `rsync -t` 保留 mtime，或显式 utimes）
⇒ racy 判定**兜不住**这一类；要兜只能 contentHash 全量（代价见 §六）
★ 所以正确写法是：
  · 「等长 ∧ 同格」由 racy 规则覆盖
  · 「等长 ∧ mtime 被保留（甚至变旧）」**声明为不支持**，由 body 级同源闸（读时报错）兜底，
    并由 files.modified_at 的单调性在 detectStaleIndex 里显形
```

## 十一、★ 盲复核纠正（2026-11-05 · `subagent:blind-review` · P6 不符）

### 「content_hash 闸不可达」这句**绝对化过头**
```
复核结论：闸确实存在（symbols.ts:485-504，函数 syncFilePrelude，由 syncFile / syncFileSync 调）✓
          改动前的 stat 闸确实是纯 stat ✓
          缺陷（同格等长改写经 ensureFreshIndex 逃逸）**是真的** ✓  修法前提**没被推翻**
★ 但「不可达」只在 **ensureFreshIndex 的「stat 相等」那一支**成立：
  syncFile 全仓 **21 处**调用，其中**无 stat 前置**的至少有：
    watch_project.ts:127 handleWatchEvent（fs.watch 事件，内容未变也照调）
    symbols.ts:1497 syncProject（逐文件无闸）
    write_gate.ts:341/595 · edit_code.ts 5 处（1039/1110/1172/1247/1413）
    rename_file / rename_path / symbol_move · index_backfill.ts:129/233
  ⇒ **内容没变的文件随时会走到那道 hash 闸并 return skipped**
    （"保存但没改" / touch 之后的一次 watch 事件就是）
```

### 准确说法（以后引用这条缺陷时照这个写）
```
✗ 不许写：「content_hash 闸不可达」
✓ 应写：**「在 ensureFreshIndex 的「stat 相等」那一支上，content_hash 闸不可达」**
★ 为什么这句差别重要：写成"全局不可达"会让人以为 **racy 窗口是唯一必要项**；
  而**真正反复触发 hash 闸、也就是说真正在吞更新的，是 watch / syncProject / 写穿那几条腿**。
★ 复核的原话我照抄：「若把『只需加 racy 窗口』当全局事实，就可能宣布修好了，
  而真正反复触发 hash 闸的那几条腿并没被碰。」
```

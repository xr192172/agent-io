## 110. T-#SHIM-VALUE：值位置的包名也能垫片了（2026-10-29）

### 病
第 4 遍 tsc：**TS2304「Cannot find name」789 个**，样本 `filepath.Join` / `os.OpenFile` / `log.Printf`。
真因：垫片只从 **`TypeRef`（类型位置）** 收集 `pkg.Name`；而函数体里的 **值位置**（调用、常量）
根本不在类型树里 ⇒ 收不到 ⇒ 没有 `declare namespace filepath` ⇒ tsc 找不到。

### 解法（关键：不猜"小写就是包"）
1. 从 Go 的 `import_declaration` 取**包名**（别名优先，否则取路径最后一段：`path/filepath` → `filepath`）；
2. 全文件扫 `selector_expression`，**只收 pkg ∈ 本文件 import 表** 的 `pkg.Member`；
3. 存到 `TransUnit.usedQualified`，`project.ts` 里并入模块垫片。

现状（`builder.go` 实测，83/83 单元都带）：
```
filepath.Dir · log.Printf · fmt.Errorf · time.NewTicker · time.Second
strings.ToLower · filepath.ToSlash · strings.Contains · strings.HasPrefix …
```

### 为什么用 import 表而不是启发式
「小写开头就当包名」会把 `st.Load()` 的 `st`（局部变量）也当成包 —— 那是**猜**。
**import 表是 Go 的语义事实**，用它判定等于让编译器告诉我们答案。这条与仓规一致：判语法走 AST。

## 119. 最后一个错的真因：**缓存投毒**（2026-10-29）

### 症状
`retrieval_pipeline.ts` 里唯一残留的 TS1005：签名行正确（单行、以 `{` 结尾），但**下一行 body 里残留类型片段**
```ts
export function DefaultPipeline_keywordSearchDiverse(...): { ID: string; Score: number; Label: string }[] {
  ID: string; Score: number; Label: string }[] {     ← body 里的幽灵片段
```

### 真因（不是渲染错）
`fill` 缓存键 = `<rel>#<unitId>@<源片段哈希>`，**不含装配版本**。
装配层修好之后，旧缓存里"按**坏骨架**拼出来的 body"仍然命中并被原样回放 ⇒ 幽灵片段一直复现。
★ 我先后猜过"渲染错"（`renderTsType` 实测输出干净单行）、"单元重复"（实测只 1 个单元），都错了。

### 修法
缓存键加版本前缀 `v2|`：**装配/签名规则变更后升版本，旧条目自然失效**（不删文件，只是不再命中）。

### 教训（今天第 9 次同类）
**缓存 = 第二处权威。** 它比生成器更顽固：生成器改了，缓存还会把旧结果塞回来。
凡是"派生产物 + 缓存"的组合，缓存键必须包含**产生它的规则版本**，否则修 bug 等于没修。
（这与之前的 `type`/`typeRef` 双权威、`sig`/`sigTs` 双权威是同一种病：**同一件事有两份记录，且没有一致性约束**。）

## 121. 填孔验收升级到 TS 语法级（`T-#FILL-TSC`，证 t442 5/0）（2026-10-29）

### 病
全仓实测：填孔 body 带进 **`TS1184 ×173`**（Modifiers cannot appear here）+ **`TS2355 ×143`**（声明返回却无 return），
**全部通过当时的 `verifySkeletons`** —— 因为那道闸只有 tree-sitter 静态复核 + 名字/参数核对，
而 `TS1184` 属于 **TS 自己的语法规则**，tree-sitter 的容错语法照收。
⇒ **填孔的验收强度低于 tsc**，坏体照样落盘（与此前"LLM 返回函数外壳"是同一个洞）。

### 加了两道**确定性**判据（零 LLM）
1. `tsGrammarIssues`：用 **TS 语法器**（`ts.createSourceFile` 的 `parseDiagnostics`）查语法。
   只取语法档、不建 program —— 单函数骨架必然缺 import/类型，语义诊断是噪声。
2. `missingReturnIssue`：**TS2355 的确定性代理** —— 声明返回非 `void/any/undefined` 且体里
   既无 `return <值>` 也无 `throw` ⇒ 必报 TS2355。用 AST 判，不建 program。

### 证（`t442` 5/0）
- 合法体**通过**（不误杀）；
- `TS1184` 类**被拦**；`TS2355` **被拦**；语法截断**被拦**；
- **反向控制**：只有 `throw` 的体**不**被 TS2355 代理误杀 ⇒ 判据不过度。

### 边界（写进证里）
只查**语法**与**返回值有无**，不查类型正确性（那要 program + 完整依赖，单函数骨架做不到）；
`TS2554`（参数个数）等语义错仍需工程级 tsc（`verify=true`）兜。

## 123. 轴心中立化第一步：册子中心不再含 TS 痕迹（证 t443 4/0）（2026-10-29）

### 用户的判断（决定路线）
> 「我的愿景是未来什么语言都可以，所以这个轴心一定要做。你现在的薄轴心可拓展性怎么样？
> 如果可拓展性不行，那你不如直接做轴心。」

**回答：薄轴心可拓展性不行**，理由不是"薄"，而是它会**变成没人读的元数据**。今天已有 4 个前科：
`strategy`（填了分类不查）、`target`（填了重算抹掉）、`sigTs`（生成了下游绕过）、缓存 body（跨构建冒充质量证据）。
规律：**凡是"管线不走它"的中间产物，最后都会退化成注释。** ⇒ 直接做轴心。

### 做之前先抓的一个硬问题
旧册子的"轴心中心"全是 TS：
```jsonc
{ "from": "builder.go#AddFix", "to": "builder.ts#Builder_AddFix", "sigTs": "Builder_AddFix(b: Builder, …): void" }
```
`to` 把**三件事**塞进一个字符串：目标文件、目标命名规则（`Type_Method`）、目标扩展名。
⇒ 从中间再翻成 Rust，**Rust 会继承 TS 的命名习语**（用户说的"中转漂移"，且发生在轴心内部）。

### 中立化后（已落地）
```jsonc
{ "from": "builder.go#AddFix",                      // 源侧投影（证据，属 Go 适配器）
  "id":   "builder.go#Builder.AddFix",              // ★ 轴心身份：文件+接收者+原始名（中立）
  "targets": { "ts": { "file": "builder.ts", "name": "Builder_AddFix",
                       "signature": "Builder_AddFix(b: Builder, …): void" } } }
```
- `792/792` 符号有中立 `id`；顶层 `to` / `sigTs` 残留 **0**；
- `ref_rewrite` 的**方法索引改用中立 id**（不再从 TS 名 `Builder_AddFix` 反解类型/方法）；
- 反向映射唯一性：`targets.ts.name → id`，**真撞车 0**；
- 管线未退化：骨架签名 **777/840 仍来自册子**，引用改写仍 262 处。

### 证 `t443`（4/0）+ 它逼出来的两个真问题
1. **构建变体未建模**：`local_embedder_nocgo.go` vs `local_embedder.go` 各定义一次 `LocalEmbedder`
   ⇒ 反向映射有 **7 组同名**（不是撞车，是 Go build tag 的互斥变体）。
   **这直接解释输出里的 `TS2300 ×9`（Duplicate identifier）** —— 两个 `LocalEmbedder` 都被渲染进同一份 TS。
   立 `T-#BUILD-VAR`。
2. 轴心**还缺三样**（证里如实输出，不假装合格）：
   `typeRef 落盘 0/792`（类型树仍在内存）、`slots 0`、`lossiness 0 条`。

### 第 2 步（下一步）
`T-#PIVOT-TYPEREF`：把 `TypeRef` 落进册子（`pivot.types`）——
它同时解决"同一份事实解释两次"，也是槽位与失真账的载体。

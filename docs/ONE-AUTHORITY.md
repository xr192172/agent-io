# 一处权威（ONE-AUTHORITY）——设计文档

> 状态：**设计稿**（未实现）。2026-10-30。
> 起因：一天内**三次**同一 bug 要在两处各修一次（`if err :=` init / `case a,b:` / `delete(m,k)`），
> 外加两次"改一份等于没改"。用户判断：**同一域里同一行为只能有一个权威处。**
> 用户要求：**先设计好，不要盲目加。**

---

## 一、把问题说准（不然会做一个错的东西）

精确表述：

> **同一个 concern（行为）在代码里有多个独立实现处，且没有任何结构关系（委托/调用）把它们连起来。**

这个现象在学术界有专门名字：**concern scattering**（关注点散布）。
它的母问题是 Biggerstaff 1993 年提出的 **concept assignment problem**（概念指派问题）：
给定一个人类概念，找出它在代码里的实现位置。

**所以"一处权威"不是新问题，它是 concept assignment 的**反面约束**：
概念必须恰好有一个实现位置。**

### 实测（本项目，不是感觉）

```
pivot 处理点 7 · legacy 处理点 10（body_pivot.ts / body_mech.ts）
两侧都实现：range(8/7) · switch(11/13) · append(4/2) · delete(8/2) · len(37/26)
```

### ★ 决定性实测：按文本查重抓不到（0 簇）

把 `translate/` 下所有函数体去注释、去空白后哈希 ⇒ **重复簇 = 0**，
而那五个能力确实各有两份实现。

⇒ **我们这个问题在所有 clone 检测器眼里都"不存在"。** 这条实测决定了整个设计方向。

## 二、业内与学术界已有什么（以及为什么不能直接用）

| 方向 | 代表工作 | 它解决什么 | 对我们的适用性 |
|---|---|---|---|
| **代码克隆检测（Type-1/2/3）** | CCFinderX（token 后缀树）· SourcererCC（token 袋 + 剪枝）· NiCad（pretty-print + 灵活匹配）· Deckard（AST 向量聚类）· BigCloneBench 基准 | 复制粘贴、改名的重复 | ❌ **不适用**：我们测出 0 簇，属于 Type-4 |
| **语义克隆检测（Type-4）** | 语义克隆综述与深度学习类方法（克隆对分类/嵌入） | 语法不同、语义相同 | ⚠️ **理论对口，工程不可靠**：公开评测里 Type-4 长期是**高召回低精度**，仍属开放问题 `[未核]`；且我们的"同行为"是**设计意图**，不是代码相似 |
| **关注点定位（concern location）** | Biggerstaff concept assignment（1993）· Robillard & Murphy **Concern Graphs**（ICSE 2002）· ConcernMapper · FEAT | 概念 → 代码位置的映射与散布可视化 | ✅ **理论框架对**：它把"散在哪"变成结构化问题；但它**只回答"在哪"，不回答"该只有一处"** |
| **架构适应度函数（fitness function）** | Ford/Parsons/Kua《Building Evolutionary Architectures》· **ArchUnit**(Java) / ArchUnitTS · **dependency-cruiser**(JS) · **import-linter**(Py) · NetArchTest · eslint-plugin-boundaries | 把架构约束变成**自动判红的结构规则** | ✅ **执行机制对**：它们能表达"只有 X 模块可以做 Y"。但规则是**基于 import/注解**的静态结构，**判不了语义重复** |
| **单写者 / 单一真相源** | LMAX **single-writer principle** · CQRS · SSOT | 一个数据只有一个写入者 ⇒ 没有写冲突 | ✅ **心智模型对**：把"行为"当数据，权威 = 唯一写者 |
| **一个版本规则** | Bazel "one version" / live-at-head | 一次构建里每个依赖只有一个版本 ⇒ 没有菱形依赖 | ✅ **极好的类比**：*每个行为在构建里只有一个实现* |
| **翻译验证 / 等价性检查** | Necula **Translation Validation**(1998) · CompCert · **Alive2**(PLDI'21 逐规则证 LLVM 优化) · 关系霍尔逻辑 / product programs（Barthe） | 两个程序**等价**的证明 | ⚠️ **只能用在有数学校验的地方**；一般程序等价**不可判定** |
| **差分测试 / 属性测试** | McKeeman 差分测试(1998) · QuickCheck 系 | 用同一批输入比对两个实现 | ✅✅ **这是我们唯一能实际做"行为等价"的手段**（今天的 `t454` 就是它） |
| **行为模型挖掘** | Daikon（不变式推断） | 从执行里挖行为规格 | ⚠️ 对渲染器这类纯函数过重 |

### 三条从上面的表里读出来的硬结论

1. **不要做克隆检测器。** Type-4 精度不够，且我们实测 0 簇——做了也是白做（还会变成又一个"量具"）。
2. **"同行为"最终是设计意图，不是可判定事实。** 所以必须**声明 + 证据**，不可能"证明"。
3. **能判的部分只有两块**：① **结构**（谁调用谁、谁 dispatch 哪些输入构造）；② **差分证据**（同一批输入，两边输出是否相同）。

## 三、我们的设计：**权威账（Authority Ledger）**

四个部分：**行为键 → 候选发现 → 差分取证 → 结构闸**。

### 3.1 行为键（BehaviorKey）——用什么代表"一个行为"

一个行为 = **（域, 输入构造集合, 输出语言）**。键的取法必须**从 AST 机械抽取**，零 LLM：

```
BehaviorKey = <domain>#<lang-pair>#<tag>
tag 来源（三种可机械识别的 dispatch 判别）：
  a) switch 的 case 字面量：        case 'range_clause'      → go:stmt:range
  b) 对判别对象的比较：             c.type === 'range'        → go:stmt:range
  c) 被 dispatch 的内建名：         fname === 'append'        → go:builtin:append
```

产出：每个符号一个 `BehaviorSet`。**这是"谁在做哪些行为"的唯一机械事实。**

> 为什么这个抓得到而哈希抓不到：我们两份实现的**分支标签是同一套**（`range_clause` / `append` / `delete`），
> 只是渲染代码写法不同。**标签是行为，写法是皮肤。**

### 3.2 候选发现（不判定，只排序）

```
for 每个 domain：
  for 每对符号 (A, B) 满足 Jaccard(A.tags, B.tags) ≥ τ（τ 初值 0.3）：
    且 A、B 之间既无调用边也无 import 依赖（call-graph 双向距离 = ∞）
    ⇒ 进候选清单，附：交集标签、各自实现行数、最近修改时间
```

- 复杂度：按 tag 倒排索引，只比"共享 ≥1 个 tag"的符号对，实际 O(Σ tag 出现次数²)——本仓规模下毫秒级。
- 输出**清单**，不做任何改写。**这一步只是"把嫌疑列出来给设计侧判"。**

### 3.3 差分取证（唯一能说"它们是一个行为"的手段）

对每个候选对，用**共享输入语料**跑两边，比对规范化输出：

```
agreement = |输出相同| / |语料|
agreement = 1.0  ⇒ 证据：冗余实现（应委托/删除）
0 < agreement < 1 ⇒ 既是重复**又是 bug**（今天 t454 抓到 5 处就是这种）
agreement = 0    ⇒ 假阳性（同 tag 不同行为），记账
```

已具备的基础设施：`certs/t454` 已在做这件事（215→327 体、34 条已登记分叉），
语料是真实 Go 仓（624 体），回放 5–8 秒。**这套差分机器是这个设计能成立的前提，而它已经存在。**

> 关键：**证据必须带样本量和语料指纹**（"327 体上逐字相同"），否则就是感觉。

### 3.4 结构闸（把"权威"变成写不进去）

两部分，**都不新增判据种类**：

**① 声明（复用 `call-exists`）**
```json
{ "kind": "call-exists", "path": "…/body_mech.ts",
  "symbol": "translateGoBodyLegacy", "target": "projectTsBody",
  "why": "行为 go:stmt:range 的权威 = body_pivot#projectTsBody；legacy 只能委托" }
```
今天就能写、能判红绿。

**② 覆盖闸（新派生判据，唯一的"新"）**：`sole-implementer`
```
对每个已声明 BehaviorKey K：
  implementers = { s | K ∈ s.BehaviorSet ∧ 不存在 s → authority 的 call-exists 路径 }
  要求 |implementers| ≤ 1
```
- 有权威：implementers 必须为 0（权威自己不算"独立实现"）。
- 无权威：允许 >1，但**必须进候选清单**（可见、可追，不静默）。

**例外通道**（必需，否则会逼出假委托）：`authority-exception { id, reason, until }`，
过期自动转红——和本仓既有的"豁免清单"口径一致。

### 3.5 挂进已有载体（不新造工具）

AGENTS 的收敛原则要求"先挂已有载体"。现成的两处最贴：

| 已有能力 | 怎么复用 |
|---|---|
| `capability_audit`（语言 × 功能覆盖缺口） | 它已经在算"某语言有没有某能力" ⇒ `BehaviorKey` 是它的**细粒度版**；权威账输出并入它的报告，不另开工具 |
| `capability_map`（能力线 × 工具） | 声明"行为 → 权威符号"后，这条线才有确定的入口 |

⇒ **最终形态是一个只读报表（`authority_report`）+ 一条派生判据（`sole-implementer`）+ 一道写闸规则**，
不是新工具面。

## 四、这一步能/不能解决什么（诚实边界）

| 能 | 不能 |
|---|---|
| 抓"同一套 dispatch 标签、两处独立实现"（今天 5 个能力全覆盖） | 抓"标签不同但行为相同"（Type-4 语义克隆）——**明确放弃** |
| 用差分证据证明冗余（可复现、带样本量） | 证明等价（**一般程序等价不可判定**） |
| 把"新的第二处权威"挡在写入前 | 判断"这个行为**本该**只有一个权威吗"——那是设计决定 |
| 量化收敛进度（双权威数 → 0） | 处理跨语言/跨域同一行为（**先不做**，记为 `[未核]`） |

## 五、怎么知道这个设计是错的（可反驳性）

先定"失败的判据"，再开工：

1. **候选清单精度 < 50%**（人工判 20 条里真·双权威不足 10 条）⇒ 标签抽取算法错，停；
2. **`sole-implementer` 假红率 > 20%** ⇒ 例外通道被滥用或键切得太粗，停；
3. **一个月内"修一份等于没修"事件不为 0** ⇒ 覆盖面不够，回头改键的粒度；
4. **差分语料覆盖不到被声明的行为**（语料里没有该构造）⇒ 证据不成立，必须先补语料。

## 八、开放问题（需要更多讨论才能定）

1. **BehaviorKey 的粒度**：`go:stmt:range` 太粗（range 有三种形态）还是太细（每种形态一个键）？倾向"构造 + 形态"两级。
2. **跨语言算不算同一行为**：pivot 与未来的 Rust 渲染器是同一行为的两个**渲染器**（合法），还是两个权威（违规）？我倾向：**同一语言对内算违规，跨目标语言算合法**。
3. **纯函数等价实现**（如两个 `zeroValueOf`）是否需要例外通道的默认开口？
4. 语料不足时（某构造在 624 体里没出现）如何表达"证据不足"而不是假绿——倾向复用四态里的 `unsupported`。

## 九、P0 实做与实测（2026-10-30）

### 用户提的算法（已采纳，比标签法更直接）

> 「你不能直接算吐出来的东西和吃进去的东西有大幅度重合的吗？有嫌疑就报警；
>   另外放白名单/灰名单 —— 白名单直接放行，灰名单暂时放行后续处理，
>   有事没事扫一扫灰名单，或者灰名单过期了自动再次告警。」

落成 **两条独立信号 + 三态名单**：

| 信号 | 怎么算 | 抓什么 |
|---|---|---|
| **dispatch 标签重合** | 从 `case` 字面量 / `x.type === '…'` / `fname === '…'` 抽标签集合，取 Jaccard | 同一套分支标签的两份实现 |
| **I/O 足迹重合** | 函数体里**读到的名字/成员** ∪ **写到的名字/成员** 的 Jaccard（另收返回形状） | 「吃进去/吐出来」高度重合的实现 —— **标签法抓不到的那半** |

名单三态（`certs/authority-allowlist.json`）：

- `whitelist`：确认合理并存 ⇒ 直接放行，不再检查；
- `graylist`：暂时放行，**必须带 `until`** ⇒ 到期后**自动重新告警**（不让"暂时"变成"永久"）；
- 都不在 ⇒ 新嫌疑 ⇒ 证书红。

### 实测（`certs/t455-authority-candidates.mjs`，只读）

```
无门槛（tag≥3 或 io≥0.5）：246 个顶层函数 ⇒ 嫌疑 128 对   ← 假阳性爆表（两个小函数读同一变量即 io=1）
加规模门槛（读数≥8、行数≥15、共用标签≥3）      ⇒ 20 对
再要求两信号同时成立                          ⇒ 10 对
```

人工判这 10 对：

| 判定 | 对 | 说明 |
|---|---|---|
| **真·双权威** | `body_pivot#projectTsExpr` <> `go_body_codegen#goExpr` | 表达式渲染两份（tag 1.0） |
| **真·双权威** | `body_pivot#projectTsStmt` <> `go_body_codegen#goStmt` | 语句渲染两份（tag 0.92） |
| 待判 | `go_codegen#renderGoType` <> `ts_codegen#renderTsType` | 两个方向的类型渲染，可能合法并存 |
| 假阳性 | `renderGoType` <> `slotsOf` / `collectQualifiedPkgs` 等 | 都是"按同一套 AST 种类分派"的不同步骤 |

### 结论（P0 出口判据**未**达成，如实）

```
精度 ≈ 40%（10 条里 2 条确认真 + 1 条待判）  <  出口线 50%
⇒ 不进入 P1（不写判据、不开写闸），先把精度做上去
```

### 下一步调优方向（已想清，未做）

1. **第三条信号：输出介质** —— 真·双权威都是渲染器（**首参是 AST 节点、返回 string**），
   假阳性多是分析器/选取器（返回 Set/数组）。加这一条能砍掉大半噪声；
2. **按标签集合的支配性排序**：A ⊂ B 且 |A|/|B| ≥ 0.8 ⇒ 更像"漏委托"而不是"两个权威"；
3. **灰名单投入实战**：确认的假阳性进 `whitelist`、待判的进 `graylist`（30 天），
   让下次扫描只剩增量，人只判新增。

## 十、修正粒度：不算"函数像不像"，算**流转的数据流是不是同一批货**

### 用户指出的错（我 §三~§九 的粒度错了）

> 「我指的是整个应用里面某一个环节启动了，然后它会自动往下面流转数据，
>   此时流转的数据流相同，或者说大幅度相同。」

§三 的 `BehaviorKey`（按函数的分支标签）和 §九 的 I/O 足迹（按函数的读写集合）都是**函数级**，
而问题在**链路级**：某个环节被触发后，数据沿一条通路往下传；**另一条通路搬的是同一份数据**。
函数长得像不像不重要——**重要的是两条链路运输的载荷是否同一批货**。

### 用本仓的真实例子说清

```
路径 A（pivot/机械）  extractGo ──体──▶ liftGoBody ──IR──▶ projectTsBody ──TS 文本──▶ 模块
路径 B（legacy）      extractGo ──体──▶ translateGoBodyMech ──TS 文本──────────▶ 模块
                                  ▲                       ▲
                        载荷相同：Go 函数体 AST      载荷相同：TS 语句文本
```

两条链路 **入口相同、载荷相同、出口相同，中段实现完全不同** ⇒ 这就是"两处权威"。
今天所有"改一份等于没改"的 bug（if-init / case 标签 / delete / append / range）
都发生在**同一份载荷、两条搬运路径**的中段。

而 `projectTsExpr <> goExpr` 这类函数级相似只是它的**症状**——
我昨天判为"真·双权威"的那两条，本质是上面这两条链路的下游段。

### 修正后的检测单位：**流转路径（FlowPath）**

```
FlowPath = {
  trigger:   入口环节（谁被触发：事件/命令/入口函数/定时）
  hops:      [环节1, 环节2, …]（有向，来自调用/接线图，或运行时 trace）
  payload:   每个 hop 上**搬运的载荷形状**（字段集 + 类型）
  sink:      落点（写文件/发消息/返回给谁）
}
```

**载荷形状**怎么拿（都不需要 LLM）：
1. 索引里的**类型事实**：参数类型、返回类型、结构体字段集（本仓 `cache.db` 已有）；
2. 运行时**事件实参**：`observe` 已经能落 `<project>/.agent/observe/` 事件，含调用链与参数摘要；
3. 接线事实：`chain_wiring` / `observe action=line` 已经在建"功能主链"。

### 判定算法（路径级）

```
for 每对 FlowPath (P, Q):
  if P.trigger 与 Q.trigger 不同族            → skip（不同触发不算同一行为）
  if P.stageSet ⊆ Q.stageSet 或反向           → skip（是委托/复用，不是双权威）
  payloadSim = 按 hop 对齐后的平均 Jaccard(P.payload[i], Q.payload[i])
  stageDisjoint = 1 - Jaccard(P.stageSet, Q.stageSet)
  if payloadSim ≥ 0.8 且 stageDisjoint ≥ 0.7:
      报「同一批货走两条管道」
      并给出 **首个分叉 hop**（两载荷开始不同的那一跳）← 这就是 bug 的诞生地
```

★ **首个分叉 hop 比"嫌疑对"有用得多**：它直接告诉你去哪一行改，
这正是今天 `t454` 干的事（逐体对拍，第一个字符不同的位置），只是抬到链路级。

### 为什么这个粒度才对（三条理由）

1. **它对应"改都改不完"的成因**：两份实现不是"抄代码"，是**两个入口各自往下流**，
   所以补一处另一处不会跟上；
2. **它自带权威判据**：链路 A 与 B 载荷相同 ⇒ 只留一条，另一条必须**并流**（在某个 hop 汇入）；
   这和"一条管道多个下游分支"（合法）在结构上可区分；
3. **它能免掉函数级噪声**：`slotsOf` 与 `renderGoType` 函数级像，但它俩不在"同一批货的两条管道"上，直接不被考虑。

### 对 P0 原型的处置（如实）

`certs/t455-authority-candidates.mjs` 的**粒度不对**（函数级），但**不是白做**：
它的 I/O 足迹与 dispatch 标签正好可以当 `payload` 的**近似来源**（字段/名字集合），
⇒ 保留为**组件**（stage-level footprint 抽取器），不再当检测单位。

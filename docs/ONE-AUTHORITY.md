# 一处权威（ONE-AUTHORITY）——设计文档

> 状态：**设计稿**（未实现）。2026-10-30。
> 起因：一天内**三次**同一 bug 要在两处各修一次（`if err :=` init / `case a,b:` / `delete(m,k)`），
> 外加两次"改一份等于没改"。用户判断：**同一域里同一行为只能有一个权威处。**
> 用户要求：**先设计好，不要盲目加。**

---

## 一、把问题说准（不然会做一个错的东西）

精确表述：

> **同一个 concern（行为）在代码里有多个独立实现处，且没有任何结构关系（委托/调用）把它们连起来。**

这个现象在学术界有专门名字：**concern scattering**（关注点散布）。
它的母问题是 Biggerstaff 1993 年提出的 **concept assignment problem**（概念指派问题）：
给定一个人类概念，找出它在代码里的实现位置。

**所以"一处权威"不是新问题，它是 concept assignment 的**反面约束**：
概念必须恰好有一个实现位置。**

### 实测（本项目，不是感觉）

```
pivot 处理点 7 · legacy 处理点 10（body_pivot.ts / body_mech.ts）
两侧都实现：range(8/7) · switch(11/13) · append(4/2) · delete(8/2) · len(37/26)
```

### ★ 决定性实测：按文本查重抓不到（0 簇）

把 `translate/` 下所有函数体去注释、去空白后哈希 ⇒ **重复簇 = 0**，
而那五个能力确实各有两份实现。

⇒ **我们这个问题在所有 clone 检测器眼里都"不存在"。** 这条实测决定了整个设计方向。

## 二、业内与学术界已有什么（以及为什么不能直接用）

| 方向 | 代表工作 | 它解决什么 | 对我们的适用性 |
|---|---|---|---|
| **代码克隆检测（Type-1/2/3）** | CCFinderX（token 后缀树）· SourcererCC（token 袋 + 剪枝）· NiCad（pretty-print + 灵活匹配）· Deckard（AST 向量聚类）· BigCloneBench 基准 | 复制粘贴、改名的重复 | ❌ **不适用**：我们测出 0 簇，属于 Type-4 |
| **语义克隆检测（Type-4）** | 语义克隆综述与深度学习类方法（克隆对分类/嵌入） | 语法不同、语义相同 | ⚠️ **理论对口，工程不可靠**：公开评测里 Type-4 长期是**高召回低精度**，仍属开放问题 `[未核]`；且我们的"同行为"是**设计意图**，不是代码相似 |
| **关注点定位（concern location）** | Biggerstaff concept assignment（1993）· Robillard & Murphy **Concern Graphs**（ICSE 2002）· ConcernMapper · FEAT | 概念 → 代码位置的映射与散布可视化 | ✅ **理论框架对**：它把"散在哪"变成结构化问题；但它**只回答"在哪"，不回答"该只有一处"** |
| **架构适应度函数（fitness function）** | Ford/Parsons/Kua《Building Evolutionary Architectures》· **ArchUnit**(Java) / ArchUnitTS · **dependency-cruiser**(JS) · **import-linter**(Py) · NetArchTest · eslint-plugin-boundaries | 把架构约束变成**自动判红的结构规则** | ✅ **执行机制对**：它们能表达"只有 X 模块可以做 Y"。但规则是**基于 import/注解**的静态结构，**判不了语义重复** |
| **单写者 / 单一真相源** | LMAX **single-writer principle** · CQRS · SSOT | 一个数据只有一个写入者 ⇒ 没有写冲突 | ✅ **心智模型对**：把"行为"当数据，权威 = 唯一写者 |
| **一个版本规则** | Bazel "one version" / live-at-head | 一次构建里每个依赖只有一个版本 ⇒ 没有菱形依赖 | ✅ **极好的类比**：*每个行为在构建里只有一个实现* |
| **翻译验证 / 等价性检查** | Necula **Translation Validation**(1998) · CompCert · **Alive2**(PLDI'21 逐规则证 LLVM 优化) · 关系霍尔逻辑 / product programs（Barthe） | 两个程序**等价**的证明 | ⚠️ **只能用在有数学校验的地方**；一般程序等价**不可判定** |
| **差分测试 / 属性测试** | McKeeman 差分测试(1998) · QuickCheck 系 | 用同一批输入比对两个实现 | ✅✅ **这是我们唯一能实际做"行为等价"的手段**（今天的 `t454` 就是它） |
| **行为模型挖掘** | Daikon（不变式推断） | 从执行里挖行为规格 | ⚠️ 对渲染器这类纯函数过重 |

### 三条从上面的表里读出来的硬结论

1. **不要做克隆检测器。** Type-4 精度不够，且我们实测 0 簇——做了也是白做（还会变成又一个"量具"）。
2. **"同行为"最终是设计意图，不是可判定事实。** 所以必须**声明 + 证据**，不可能"证明"。
3. **能判的部分只有两块**：① **结构**（谁调用谁、谁 dispatch 哪些输入构造）；② **差分证据**（同一批输入，两边输出是否相同）。

## 三、我们的设计：**权威账（Authority Ledger）**

四个部分：**行为键 → 候选发现 → 差分取证 → 结构闸**。

### 3.1 行为键（BehaviorKey）——用什么代表"一个行为"

一个行为 = **（域, 输入构造集合, 输出语言）**。键的取法必须**从 AST 机械抽取**，零 LLM：

```
BehaviorKey = <domain>#<lang-pair>#<tag>
tag 来源（三种可机械识别的 dispatch 判别）：
  a) switch 的 case 字面量：        case 'range_clause'      → go:stmt:range
  b) 对判别对象的比较：             c.type === 'range'        → go:stmt:range
  c) 被 dispatch 的内建名：         fname === 'append'        → go:builtin:append
```

产出：每个符号一个 `BehaviorSet`。**这是"谁在做哪些行为"的唯一机械事实。**

> 为什么这个抓得到而哈希抓不到：我们两份实现的**分支标签是同一套**（`range_clause` / `append` / `delete`），
> 只是渲染代码写法不同。**标签是行为，写法是皮肤。**

### 3.2 候选发现（不判定，只排序）

```
for 每个 domain：
  for 每对符号 (A, B) 满足 Jaccard(A.tags, B.tags) ≥ τ（τ 初值 0.3）：
    且 A、B 之间既无调用边也无 import 依赖（call-graph 双向距离 = ∞）
    ⇒ 进候选清单，附：交集标签、各自实现行数、最近修改时间
```

- 复杂度：按 tag 倒排索引，只比"共享 ≥1 个 tag"的符号对，实际 O(Σ tag 出现次数²)——本仓规模下毫秒级。
- 输出**清单**，不做任何改写。**这一步只是"把嫌疑列出来给设计侧判"。**

### 3.3 差分取证（唯一能说"它们是一个行为"的手段）

对每个候选对，用**共享输入语料**跑两边，比对规范化输出：

```
agreement = |输出相同| / |语料|
agreement = 1.0  ⇒ 证据：冗余实现（应委托/删除）
0 < agreement < 1 ⇒ 既是重复**又是 bug**（今天 t454 抓到 5 处就是这种）
agreement = 0    ⇒ 假阳性（同 tag 不同行为），记账
```

已具备的基础设施：`certs/t454` 已在做这件事（215→327 体、34 条已登记分叉），
语料是真实 Go 仓（624 体），回放 5–8 秒。**这套差分机器是这个设计能成立的前提，而它已经存在。**

> 关键：**证据必须带样本量和语料指纹**（"327 体上逐字相同"），否则就是感觉。

### 3.4 结构闸（把"权威"变成写不进去）

两部分，**都不新增判据种类**：

**① 声明（复用 `call-exists`）**
```json
{ "kind": "call-exists", "path": "…/body_mech.ts",
  "symbol": "translateGoBodyLegacy", "target": "projectTsBody",
  "why": "行为 go:stmt:range 的权威 = body_pivot#projectTsBody；legacy 只能委托" }
```
今天就能写、能判红绿。

**② 覆盖闸（新派生判据，唯一的"新"）**：`sole-implementer`
```
对每个已声明 BehaviorKey K：
  implementers = { s | K ∈ s.BehaviorSet ∧ 不存在 s → authority 的 call-exists 路径 }
  要求 |implementers| ≤ 1
```
- 有权威：implementers 必须为 0（权威自己不算"独立实现"）。
- 无权威：允许 >1，但**必须进候选清单**（可见、可追，不静默）。

**例外通道**（必需，否则会逼出假委托）：`authority-exception { id, reason, until }`，
过期自动转红——和本仓既有的"豁免清单"口径一致。

### 3.5 挂进已有载体（不新造工具）

AGENTS 的收敛原则要求"先挂已有载体"。现成的两处最贴：

| 已有能力 | 怎么复用 |
|---|---|
| `capability_audit`（语言 × 功能覆盖缺口） | 它已经在算"某语言有没有某能力" ⇒ `BehaviorKey` 是它的**细粒度版**；权威账输出并入它的报告，不另开工具 |
| `capability_map`（能力线 × 工具） | 声明"行为 → 权威符号"后，这条线才有确定的入口 |

⇒ **最终形态是一个只读报表（`authority_report`）+ 一条派生判据（`sole-implementer`）+ 一道写闸规则**，
不是新工具面。

## 四、这一步能/不能解决什么（诚实边界）

| 能 | 不能 |
|---|---|
| 抓"同一套 dispatch 标签、两处独立实现"（今天 5 个能力全覆盖） | 抓"标签不同但行为相同"（Type-4 语义克隆）——**明确放弃** |
| 用差分证据证明冗余（可复现、带样本量） | 证明等价（**一般程序等价不可判定**） |
| 把"新的第二处权威"挡在写入前 | 判断"这个行为**本该**只有一个权威吗"——那是设计决定 |
| 量化收敛进度（双权威数 → 0） | 处理跨语言/跨域同一行为（**先不做**，记为 `[未核]`） |

## 五、怎么知道这个设计是错的（可反驳性）

先定"失败的判据"，再开工：

1. **候选清单精度 < 50%**（人工判 20 条里真·双权威不足 10 条）⇒ 标签抽取算法错，停；
2. **`sole-implementer` 假红率 > 20%** ⇒ 例外通道被滥用或键切得太粗，停；
3. **一个月内"修一份等于没修"事件不为 0** ⇒ 覆盖面不够，回头改键的粒度；
4. **差分语料覆盖不到被声明的行为**（语料里没有该构造）⇒ 证据不成立，必须先补语料。

## 八、开放问题（需要更多讨论才能定）

1. **BehaviorKey 的粒度**：`go:stmt:range` 太粗（range 有三种形态）还是太细（每种形态一个键）？倾向"构造 + 形态"两级。
2. **跨语言算不算同一行为**：pivot 与未来的 Rust 渲染器是同一行为的两个**渲染器**（合法），还是两个权威（违规）？我倾向：**同一语言对内算违规，跨目标语言算合法**。
3. **纯函数等价实现**（如两个 `zeroValueOf`）是否需要例外通道的默认开口？
4. 语料不足时（某构造在 624 体里没出现）如何表达"证据不足"而不是假绿——倾向复用四态里的 `unsupported`。

## 九、P0 实做与实测（2026-10-30）

### 用户提的算法（已采纳，比标签法更直接）

> 「你不能直接算吐出来的东西和吃进去的东西有大幅度重合的吗？有嫌疑就报警；
>   另外放白名单/灰名单 —— 白名单直接放行，灰名单暂时放行后续处理，
>   有事没事扫一扫灰名单，或者灰名单过期了自动再次告警。」

落成 **两条独立信号 + 三态名单**：

| 信号 | 怎么算 | 抓什么 |
|---|---|---|
| **dispatch 标签重合** | 从 `case` 字面量 / `x.type === '…'` / `fname === '…'` 抽标签集合，取 Jaccard | 同一套分支标签的两份实现 |
| **I/O 足迹重合** | 函数体里**读到的名字/成员** ∪ **写到的名字/成员** 的 Jaccard（另收返回形状） | 「吃进去/吐出来」高度重合的实现 —— **标签法抓不到的那半** |

名单三态（`certs/authority-allowlist.json`）：

- `whitelist`：确认合理并存 ⇒ 直接放行，不再检查；
- `graylist`：暂时放行，**必须带 `until`** ⇒ 到期后**自动重新告警**（不让"暂时"变成"永久"）；
- 都不在 ⇒ 新嫌疑 ⇒ 证书红。

### 实测（`certs/t455-authority-candidates.mjs`，只读）

```
无门槛（tag≥3 或 io≥0.5）：246 个顶层函数 ⇒ 嫌疑 128 对   ← 假阳性爆表（两个小函数读同一变量即 io=1）
加规模门槛（读数≥8、行数≥15、共用标签≥3）      ⇒ 20 对
再要求两信号同时成立                          ⇒ 10 对
```

人工判这 10 对：

| 判定 | 对 | 说明 |
|---|---|---|
| **真·双权威** | `body_pivot#projectTsExpr` <> `go_body_codegen#goExpr` | 表达式渲染两份（tag 1.0） |
| **真·双权威** | `body_pivot#projectTsStmt` <> `go_body_codegen#goStmt` | 语句渲染两份（tag 0.92） |
| 待判 | `go_codegen#renderGoType` <> `ts_codegen#renderTsType` | 两个方向的类型渲染，可能合法并存 |
| 假阳性 | `renderGoType` <> `slotsOf` / `collectQualifiedPkgs` 等 | 都是"按同一套 AST 种类分派"的不同步骤 |

### 结论（P0 出口判据**未**达成，如实）

```
精度 ≈ 40%（10 条里 2 条确认真 + 1 条待判）  <  出口线 50%
⇒ 不进入 P1（不写判据、不开写闸），先把精度做上去
```

### 下一步调优方向（已想清，未做）

1. **第三条信号：输出介质** —— 真·双权威都是渲染器（**首参是 AST 节点、返回 string**），
   假阳性多是分析器/选取器（返回 Set/数组）。加这一条能砍掉大半噪声；
2. **按标签集合的支配性排序**：A ⊂ B 且 |A|/|B| ≥ 0.8 ⇒ 更像"漏委托"而不是"两个权威"；
3. **灰名单投入实战**：确认的假阳性进 `whitelist`、待判的进 `graylist`（30 天），
   让下次扫描只剩增量，人只判新增。

## 十、修正粒度：不算"函数像不像"，算**流转的数据流是不是同一批货**

### 用户指出的错（我 §三~§九 的粒度错了）

> 「我指的是整个应用里面某一个环节启动了，然后它会自动往下面流转数据，
>   此时流转的数据流相同，或者说大幅度相同。」

§三 的 `BehaviorKey`（按函数的分支标签）和 §九 的 I/O 足迹（按函数的读写集合）都是**函数级**，
而问题在**链路级**：某个环节被触发后，数据沿一条通路往下传；**另一条通路搬的是同一份数据**。
函数长得像不像不重要——**重要的是两条链路运输的载荷是否同一批货**。

### 用本仓的真实例子说清

```
路径 A（pivot/机械）  extractGo ──体──▶ liftGoBody ──IR──▶ projectTsBody ──TS 文本──▶ 模块
路径 B（legacy）      extractGo ──体──▶ translateGoBodyMech ──TS 文本──────────▶ 模块
                                  ▲                       ▲
                        载荷相同：Go 函数体 AST      载荷相同：TS 语句文本
```

两条链路 **入口相同、载荷相同、出口相同，中段实现完全不同** ⇒ 这就是"两处权威"。
今天所有"改一份等于没改"的 bug（if-init / case 标签 / delete / append / range）
都发生在**同一份载荷、两条搬运路径**的中段。

而 `projectTsExpr <> goExpr` 这类函数级相似只是它的**症状**——
我昨天判为"真·双权威"的那两条，本质是上面这两条链路的下游段。

### 修正后的检测单位：**流转路径（FlowPath）**

```
FlowPath = {
  trigger:   入口环节（谁被触发：事件/命令/入口函数/定时）
  hops:      [环节1, 环节2, …]（有向，来自调用/接线图，或运行时 trace）
  payload:   每个 hop 上**搬运的载荷形状**（字段集 + 类型）
  sink:      落点（写文件/发消息/返回给谁）
}
```

**载荷形状**怎么拿（都不需要 LLM）：
1. 索引里的**类型事实**：参数类型、返回类型、结构体字段集（本仓 `cache.db` 已有）；
2. 运行时**事件实参**：`observe` 已经能落 `<project>/.agent/observe/` 事件，含调用链与参数摘要；
3. 接线事实：`chain_wiring` / `observe action=line` 已经在建"功能主链"。

### 判定算法（路径级）

```
for 每对 FlowPath (P, Q):
  if P.trigger 与 Q.trigger 不同族            → skip（不同触发不算同一行为）
  if P.stageSet ⊆ Q.stageSet 或反向           → skip（是委托/复用，不是双权威）
  payloadSim = 按 hop 对齐后的平均 Jaccard(P.payload[i], Q.payload[i])
  stageDisjoint = 1 - Jaccard(P.stageSet, Q.stageSet)
  if payloadSim ≥ 0.8 且 stageDisjoint ≥ 0.7:
      报「同一批货走两条管道」
      并给出 **首个分叉 hop**（两载荷开始不同的那一跳）← 这就是 bug 的诞生地
```

★ **首个分叉 hop 比"嫌疑对"有用得多**：它直接告诉你去哪一行改，
这正是今天 `t454` 干的事（逐体对拍，第一个字符不同的位置），只是抬到链路级。

### 为什么这个粒度才对（三条理由）

1. **它对应"改都改不完"的成因**：两份实现不是"抄代码"，是**两个入口各自往下流**，
   所以补一处另一处不会跟上；
2. **它自带权威判据**：链路 A 与 B 载荷相同 ⇒ 只留一条，另一条必须**并流**（在某个 hop 汇入）；
   这和"一条管道多个下游分支"（合法）在结构上可区分；
3. **它能免掉函数级噪声**：`slotsOf` 与 `renderGoType` 函数级像，但它俩不在"同一批货的两条管道"上，直接不被考虑。

### 对 P0 原型的处置（如实）

`certs/t455-authority-candidates.mjs` 的**粒度不对**（函数级），但**不是白做**：
它的 I/O 足迹与 dispatch 标签正好可以当 `payload` 的**近似来源**（字段/名字集合），
⇒ 保留为**组件**（stage-level footprint 抽取器），不再当检测单位。

### 下一步（P0′，仍未写判据、不开写闸）

1. 抽 **flow 图**：先用静态调用图 + 类型事实（`cache.db`），跑通"入口 → hops → sink"；
2. 用今天已知答案做**回填验证**：
   ```
   期望被报出：extractGo→liftGoBody→projectTsBody  与  extractGo→translateGoBodyMech
   期望不被报出：slotsOf / renderGoType / collectQualifiedPkgs 之间的任意组合
   ```
   ★ 这一条是**可证伪的验收**：已知真例必须报出，已知假例必须不报；
3. 精度 ≥ 80% 才谈 P1（路径级比函数级噪声低，出口线应更严）；
4. 有运行时事件时，再用 `observe` 的真实参数摘要替换静态载荷近似。

### [未核]

- 静态调用图对**动态分派/回调/队列**会断链（本仓 `translate` 里有 provider 回调），需要运行时 trace 补；
- 跨进程/跨语言的链路（Go 源仓 → TS 产物仓）目前只做**单进程内**路径；
- "触发不同族"如何机械判定（入口函数 vs 命令行 vs 定时）——先用入口所在的 domain + 入口名族判。

## 十一、P0′ 探针的两次失败（可证伪验收起作用了）

`certs/t456-flow-authority-probe.mjs`：从入口出发枚举流转路径，比**载荷**、报「同一批货两条管道」，
并带**已知答案**做验收（真例必须报出、假例必须不报）。**目前 2 PASS / 1 FAIL，未通过。**

### 失败一：要求"阶段几乎全不交" ⇒ 0 命中

真实的双管道**共享主干后才分叉**：
```
extractGo → collect → unitFromFunc → translateGoBodyMech ─┬─▶ liftGoBody → projectTsBody   （新路径）
                                                          └─▶ translateGoBodyLegacy        （旧路径）
```
我第一版要求 `stageDisjoint ≥ 0.7`、且"阶段互相包含就跳过" ⇒ 共享 4 跳的两条分支被当成"委托"排除，命中 0。

**修法**：先求**最长公共前缀（LCP）**，只比**岔开之后的那段**；LCP=0 视为不同触发。

### 失败二：载荷取"参数/返回类型" ⇒ 报出来的全是"兄弟分支"

改完之后命中 9 对，但全是这种：
```
extractGo→collect→unitFromFunc       <>  extractGo→collect→unitFromTypeSpec   载荷 1.0
translateGoToTs→renderTsSkeleton→renderConstSkeleton <> …→renderFuncSkeleton   载荷 1.0
```
它们**是合法的兄弟分支**（处理不同构造），但**类型签名完全一样**
（都是 `(node: SyntaxNodeLike) => TransUnit | null`）⇒ 载荷相似度恒为 1 ⇒ 无法区分。

**结论：类型级载荷不够。** 必须下沉到**字段级**——
这正是用户说的"吃进去/吐出来"：一个 hop 的载荷 = 它**读了输入的哪些字段** ∪ **写了输出的哪些字段**。
`unitFromFunc` 读的是 `name/parameters/result`，`unitFromTypeSpec` 读的是 `name/type` ⇒ 这样才能分开。

### 目前状态（如实）
```
① 报得出东西            ✓（9 对，非恒空）
② 已知真例必须报出      ✗（真例那两条在 LCP 之后只有 1 跳，且类型签名不同 ⇒ 载荷相似度不足 0.6）
③ 已知假例必须不报      ✓（slotsOf / renderGoType / collectQualifiedPkgs 无组合被报）
```

### 下一步（P0″）
1. 载荷改**字段级**：每 hop 取「读字段集 ∪ 写字段集」，来自 AST（成员访问 / 赋值左值）；
2. 真例要能报出，需要把"中段实现"作为**阶段**纳入：
   `translateGoBodyMech` 之后的两条尾段本身只有 1 跳，
   ⇒ 判定应允许**比较"分叉点之下的子图"**，而不是逐跳对齐（长度不等时按集合比）；
3. 仍然只读、不写判据、不开写闸；精度 ≥80% 才谈 P1。

### 这两次失败的价值
不是"又没做成"，而是：**可证伪验收让我在半小时内否掉了两版算法**，
而不是做完一周才发现它报的全是兄弟分支——那正是又一个"量具"。

## 十二、第三个信号：**上下游相同**（structural clone / sandwich）—— 立刻抓到一个大发现

### 用户提的信号
> 「有一两条同样的管道都 import 同样的，或者说都有同一个文件作为上游和同一个文件作为下游，
>   并且处理的数据大幅度相同。」

这在文献里有名字：
- **structural clones**（Kapser & Godfrey）：设计层重复 —— "同样的邻居 + 中间那份重复实现"；
- **sandwich / bottleneck**（Sangal 等, OOPSLA'05 依赖模型）：上下游相同、中间可替换的结构单元。
两者都比"函数相似度"更接近我们的病，而且**算起来极便宜**（只看 import 关系与引用计数）。

### 实测：一加进 t455，四条"真·双权威"全部落在 ↑0 的文件里

```
body_pivot.ts#projectTsExpr(↑4)      <>  go_body_codegen.ts#goExpr(↑0)      ★ 死代码里的第二份
body_pivot.ts#projectTsStmt(↑4)      <>  go_body_codegen.ts#goStmt(↑0)      ★ 死代码里的第二份
go_codegen.ts#renderGoType(↑0)       <>  ts_codegen.ts#renderTsType(↑5)     ★ 死代码里的第二份
go_codegen.ts#renderGoType(↑0)       <>  pivot.ts#slotsOf(↑1)               ★ 死代码里的第二份
```
（`↑n` = 有多少个文件 import 它。）

**`go_body_codegen.ts` 与 `go_codegen.ts` 的 importers 都是 0。**
交叉核对：只有**证文件**在 import 它们 ——
```
certs/t449-body-roundtrip-cert.mjs → go_body_codegen
certs/t446-pivot-roundtrip-probe.mjs → go_codegen
```
生产代码**没有任何一处**引用它们。

### 这说明什么（重要）

1. 我昨天判为"真·双权威"的两条（`projectTsExpr<>goExpr`、`projectTsStmt<>goStmt`），
   其实是**死代码里保留的第二份渲染实现** —— 不是"活的两条管道抢权威"，而是"旧的没删干净"。
2. ⇒ **双权威分两类，处置完全不同**：

| 类型 | 特征 | 处置 |
|---|---|---|
| **死代码里的第二份** | 上游为空（importers=0） | **删**（最便宜，风险最低） |
| **活着的双管道** | 上下游均有、中间实现不同 | 并流（一条委托另一条） |

3. ⇒ "上下游"这个信号的价值：**它不判语义就把两类分开了**。
   今天所有函数级相似度算法都在这件事上打转，而 import 计数一句话解决。

### 判据形态（P0 内就能用，不需要等 P1）
```
for 每对嫌疑 (A, B):
  if A.importers = 0 或 B.importers = 0  →  分类为「死代码里的第二份」，建议删（不报警为"活的双权威"）
  else if 上下游集合相同 且 数据相似      →  分类为「活的双管道」，建议并流（P1 才拦）
  else                                   →  分类为「邻居不同」，降级/进灰名单
```

### 下一步（比原计划更划算）
1. 先用**上下游信号**把 20 对全部分类（死/活/邻居不同），人只需判"活的双管道"那一小撮；
2. 死的那批走正常删除流程（证 t449/t446 里对它们的引用要一起改）；
3. 活的再用**字段级载荷 + 差分**取证；
4. 仍不写判据、不开写闸。

### [未核]
- importers=0 也可能是**动态 import / 反射 / 外部调用**（本仓没有，但换项目要查）；
- 证文件引用它们说明"证本身依赖死代码"——删的时候要连证一起改成引用活实现（否则证在验死代码）。

## 十三、P0″ 第三/四版仍不成：**枚举单位错了**（如实记录）

### 第三版：载荷改字段级（用户说的"吃进去/吐出来"）

载荷从"参数/返回类型"改成 `in:<读到的成员名>` ∪ `out:<写到的成员名>` ∪ `lit:<短字面量>`。
结果：**命中 0** —— 因为路径深度上限 3 把两条真实尾段都截掉了。

### 第四版：深度放到 5

```
函数 241 · 路径 161 · 命中 105
  [载荷 0.98 / 阶段不交 0.5] …→renderFuncSkeleton→mapParam→renderTsType
                       <>  …→renderFuncSkeleton→renderTsType        分叉 hop 3
```
**105 命中全是路径片段互比**：`mapParam` 内部就调 `renderTsType`，
所以"经过 mapParam"和"直接调 renderTsType"本来就是同一条路上的两截，不是两条管道。

### 结论：枚举单位错了

`DFS 枚举所有简单路径` 会产生组合爆炸，而且**大部分候选是"片段 vs 片段"**。
正确的单位应该是**触发级联（entry → sink 的完整通路）**：
```
path = 入口（CLI 命令 / 事件 / 导出 API） → … → 落点（写文件 / 发消息 / 返回值）
```
- **必须以 sink 收尾**，否则就是"半截路"；
- 只在**同一个入口**的分支之间比（同一 trigger）；
- 分支因子大的地方限制深度，或先按"是否到达同一 sink"过滤。

本仓的 sink 是明确的：`项目.ts`（写文件）· `db`（写库）· `gateway`（发请求）· CLI 的 stdout。
⇒ 用"到 sink 为止"做终止条件，候选数会从 161/105 掉到个位数。

### 现状（不吹）

| 组件 | 状态 |
|---|---|
| 三信号（标签/I-O/上下游） | 有原型，精度 ≈40%，**不可上线** |
| 上下游分类（死/活/邻居不同） | ✅ 唯一真正落地的部分 |
| 链路级 detector | ✗ 三版都不成（0 / 105），根因是枚举单位错 |
| 字段级载荷 | 已实现，但**没能改变结论**（载荷不再是瓶颈，路径定义才是） |
| 判据 / 写闸 | 未开（按用户要求：先设计清楚） |

### 下一版（P0‴）的明确设计

1. **入口集合**：CLI 子命令 + 对外导出 API + 事件处理器（本仓可从 `cli.ts` 与 `TRIGGER_ROWS` 派生）；
2. **落点集合**：写文件 / 写库 / 发网络 / 返回（从调用名与 fs/db/fetch 调用识别）；
3. **枚举**：从入口 DFS，**只保留到达 sink 的完整路径**；分支因子 >8 的 hop 记"未展开"（显式缺口，不静默截断）；
4. **判定**：同一入口、不同 sink 前的分支 ⇒ 比该分支的载荷（字段级）；要求两条分支都到达同类 sink；
5. **验收**：仍用已知答案（真例必出、假例必不出）；另外要求"候选数 ≤ 20"（可人判）。

### 我为什么停下来写这个而不是接着调参
用户的原话是"不要盲目加"。三版都失败说明**不是阈值问题，是单位问题**；
继续调阈值只会得到一个"看起来能报点什么"的量具 —— 那正是今天反复吃的亏。

## 十四、缺的那一层：**字段级 / 变量级转运流**（用户的原始设想，也是两根难柱的共同底座）

### 用户的原话与判断

> 「我本来是想 AST 直接精确解析到字段级的，但是似乎实际 DB、设计 DB 都只达到了函数级……
>   如果到了字段级精度，什么变量被哪个函数用了、又运到下一个函数里、怎么转运的都能写出来，
>   那是不是对你重写就更加如虎添翼？」

**判断正确。** 今天两处最难的问题（一处权威的检出、结构化重写的安全性）**卡的是同一层**。

### 核对：我们现在的库到哪一级（实测 schema）

```
nodes(12042)        id,kind,name,qualified_name,signature,params,return_type,members,…   ← 符号级
edges(15448)        source,target,kind(调/import),line,col,metadata                     ← 符号级调用图
identifiers(314476) file_id,name,kind,line,col,start_index,end_index                    ← 原料齐全
unresolved_refs(32426) from_node_id,reference_name,candidates,status,resolved_node_id    ← 原料齐全
```

**31 万个标识符出现位置都索引了**，但没有一处把它们连成：
- 这个标识符绑定的是**哪个**局部/形参/字段；
- 它的**定义点**在哪、**使用点**有哪些（def-use）；
- 在调用点，谁做**实参**喂给了谁的**形参**；
- `x.y.z` 这条**字段路径**的根是什么（形参/局部/全局/返回值）。

⇒ 库是**符号级**（谁调用谁），不是**变量级**（什么值流到哪）。设计 DB 更粗（文件 + 判据）。
这解释了为什么我只能用"标签重合 / 类型签名"这类**代理信号**去猜行为异同 —— 那些信号之所以 40% 精度，
**根本原因就是它们都是字段级事实的劣质替身**。

### 这一层能同时解开两根难柱

| 现在卡住的事 | 有了变量级转运流之后 |
|---|---|
| 一处权威只能靠标签/I-O 近似（精度 40%） | 两个函数的**效应摘要**（读哪些字段路径、写哪些字段路径、实参→形参映射）可直接比 ⇒ 字段级等价，兄弟分支自然分开（实测：类型级让 `unitFromFunc` 与 `unitFromTypeSpec` 相似度恒 1.0，字段级立刻不同） |
| 结构化重写只能"看着改"，改完不知道波及谁 | **切片**：从某行为反向求依赖闭包，只改这一片；并能证明"该字段无其它消费者"⇒ 安全重构 |
| pivot 槽位是类型级（`Time→number`），字段级映射靠猜 | 槽位表下沉到字段（`Time.Format→Format(t,l)` 这类方法槽位已经是这个方向）；缺字段 = 结构性错误，设计期可判 |
| 嵌入字段 `graphNode` 丢失只能靠读产物发现 | 摘要里"Go 结构体声明了字段 X、写它的地方 W、读它的地方 R"与 TS 侧对账 ⇒ **声明/写入/读取三处不一致当场红** |

### 文献：这条路是成熟的，不用自创

| 技术 | 出处 | 用途 |
|---|---|---|
| **IFDS / IDE**（域敏感过程间数据流） | Reps, Horwitz, Sagiv (POPL'95 / TOSEM'05) | 字段敏感的过程间可达定义；精确但贵 |
| **SVFG 值流图** | Sui & Xue, *SVF: interprocedural static value-flow analysis in LLVM* (CC'16) | **"哪个值定义在哪、流到哪个函数"** —— 用户描述的正是这个 |
| **程序切片 / PDG** | Weiser (ICSE'81) · Horwitz-Reps-Binkley (PLDI'90 系统依赖图) | 结构化重写只改切片；跨过程的切片靠 SDG |
| **ModRef / MemorySSA** | LLVM | 单函数内"读了哪块内存、写了哪块"的摘要 |
| **数据流库 / taint** | CodeQL dataflow · Semgrep taint mode | 工程化的字段级流查询（可借鉴其查询形态） |
| **TypeChecker 符号解析** | TypeScript Compiler API | ★ **TS 侧不用造轮子**：`Program.getTypeChecker()` 直接给符号、引用、类型；我们本来就在跑 tsc |

### 落地分四段（每段都有可验证产出，不一次性造大机器）

**A. TS 侧效应摘要（最便宜，先做）**
```
summary(fn) = {
  reads:  Set<字段路径>      // 形参/局部/成员，如 "u.fields[].typeRef.kind"
  writes: Set<字段路径>
  calls:  [{ callee, argMap: [{ argIdx→paramIdx, pathFrom }] }]
  returns: 路径集合
}
```
- 实现：`tsc` 的 `Program` + `TypeChecker.getSymbolAtLocation` 解析每个标识符到符号；
  赋值/二元运算左值 = 写；其余引用 = 读；`CallExpression` 记录实参表达式与目标符号。
- 存放：`cache.db` 新增 `summaries(node_id, json)`；**只加一表，不加新门**。
- 验收：对 `body_pivot#projectTsStmt` 与 `go_body_codegen#goStmt` 求摘要，**必须高度相似**（真双权威）；
  对 `unitFromFunc` 与 `unitFromTypeSpec`，**必须明显不同**（兄弟分支）。← 这一条直接检验"字段级能否分开兄弟"

**B. Go 侧变量级转运流**
- 局部绑定：我们已经有了作用域栈（`body_pivot` 里为声明语义写的），扩到"标识符→绑定"；
- 字段路径：`selector_expression` 链 + 根解析（形参/局部/包名/接收者）；
- 调用点映射：Go 的实参位置→被调函数形参位置（我们已有 `countArgsAt` 这类工具）；
- 产出：`flows(from, to, path)` 边，落 `cache.db`。

**C. 跨界对账（Go 声明 ↔ pivot 槽位 ↔ TS 渲染）**
- 用 A/B 两侧的摘要对账：Go 侧"写了该字段"必须在 TS 侧"有对应写入"；
  ⇒ 今天的嵌入字段 bug 属于这一类（Go 声明了、TS 接口没有）⇒ **设计期可判**。

**D. 切片 API + 权威检出（建立在 A/B 之上）**
- `slice(symbol, criterion)` ⇒ 反向依赖闭包（结构化重写的"范围"）；
- 权威检出 = 摘要等价 + 上下游分类（死/活/邻居不同）——今天的 §十二 结论直接复用。

### 为什么这不违反"不要盲目加"

它不是又一个量具：**它把今天所有"代理信号"替换成事实本身**，

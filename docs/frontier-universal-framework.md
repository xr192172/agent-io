> **状态**：**不做**（2026-10-05 裁定）。本文是**研究纲领 + 阵亡记录**，不是施工计划。

> 2026-10-05 删除 —— 不是因为"实现有 bug"，而是因为**前提不成立**。本文保存前提本身。

## 1. 原始的设想（逐字保留，别改写）

> 「因为我们是有那个积木线的嘛……这是当时我一个设想，属于是一个**许愿的一个幻想**，但是我不知道它怎么实现。
> 如果真的要做到项目融合的话，其实是我们**自己去创造一个真正普适的一个框架**，然后**抽出零件**，
> 然后**往框架里面填**。但是这样一个**万能的框架**要怎么做？
> 而且做成了那个万能框架之后，其实**可以先把我们这个项目再往那边拉**。
> 也就是说，我们现在这个框架**是否可以抽象成万能框架**？
> 就是不管是什么工具也好，还是前端后端也好，还是不同的跨语言的也好，
> 比如说里面**既存 Python 又存 Java** 这种，然后让它们**互相桥接**，这种也好，这种万能框架怎么做？
> ……他刚需一个这种万能框架，**既能处理前端和后端，又能处理不同语言之间的耦合和桥接**，
> **一个服务起出多种语言然后同时运行，一个一个进程同时运行多种语言的编译的结果**，
> 而且还要**支持不同的依赖**，或者说是**把那个依赖重构成当前依赖**等这种乱七八糟的要求。
> ……如果**实在实现不了**的话，就把它删除吧，毕竟这个**积木线有点异想天开**。毕竟这个**深水区**，
> 假如我们**统一了各语言的运行时**、并真的造出了这么一个万能框架，**也许编程就真的没有门槛了**。」

★ 注意最后一句：**设想的终点不是"代码复用"，是"编程没有门槛"**。§8 会回到这一点。

---

## 2. 一句话结论

**做不了 —— 但理由不是"难"，是"它不是一个东西，是六个东西"，而其中四个已经有更强的主人。**

> 判据来自我们的既有纪律（`oss-prior-art-first`）：
> **"造格子"（补别人没有的那一格）可以自造；"造整座房子"不行。**
> 设想的"万能框架"是**整座房子**；它内部只有两格是空的。

★★ **但这句"做不了"只管**版本 A**（框架自己懂一切语义）—— 见 §5.2。**
用户 2026-10-05 指出还有**版本 B**（**框架只给插槽，语义由模型填**），
那个版本**不在本结论的证伪范围内**，而且 §4.1 第 3 条正是它的依据。
⇒ 读这一节之前，**先读 §5.2 的两个版本对照**。

## 3. 把设想拆成可讨论的子目标

"万能框架"这个词太大，先拆。拆完就会发现它混了**六层不同的东西**：

| # | 子目标 | 它本质要解决什么 |
|---|---|---|
| ① | 跨语言运行时 / 内存 / ABI | 让 A 语言的对象能被 B 语言安全调用；同一进程共存、互不踩内存 |
| ② | 跨语言接口生成 | 从**一份**接口定义生成各语言的绑定（让"桥接"不必手写） |
| ③ | 多语言构建编排 | 一次构建、多工具链协同、增量、可缓存 |
| ④ | 依赖统一 / 改写 | 多生态版本收敛；"把依赖重构成当前依赖" |
| ⑤ | ★ **什么算一块"积木"** | 从代码里切出**有意义的**可复用单元（切点在哪？） |
| ⑥ | ★ **这块积木对外承诺什么** | 它的契约（能不能被判定、被验证） |
| ⑦ | 组装 / 填胶 | 把积木拼进新项目、生成 glue 代码 |

★ **关键**：设想里的"万能"感，来自把 ①–⑦ 当成**一件事**。它们其实**分层**，而且**层与层的最优解完全不同**。

## 4. 逐层查：这一层有人做完了吗？（回答"怎么做"）

★ 顺序按 `oss-prior-art-first`：先本地、再 GitHub、再论文/新闻；**证据分级见 §7**。

| 层 | 已有主人（先例） | 我们当前状态 | 该不该自造 |
|---|---|---|---|
| ① 跨语言运行时/组合 | **WebAssembly Component Model**（WIT 接口 + 组件链接 + 每组件独立内存沙箱）；GraalVM Polyglot；JVM/CLR | **0** | ❌ 别造。这是**正在成型的标准**，且需要语言工具链集体配合 |
| ② 跨语言绑定生成 | SWIG · **uniffi**(Mozilla) · napi-rs · PyO3 · wasm-bindgen · cgo/JNI | **0**（我们有 Go→TS **源码翻译**，不是运行时绑定） | ❌ 别造。选一个现成的，或用 ① 的 WIT |
| ③ 多语言构建编排 | **Bazel** · Pants · Nx · Buck2 · Turborepo | 0（只有 npm scripts + 一个 Go 小工具） | ❌ 别造。Bazel 这条护城河是十几年 |
| ④ 依赖统一 | 各生态包管理器 + **MVS**(Go modules) · Nix | 只借了 **Go 的 MVS** + npm 版本比较（**2 个生态**） | ⭕ 借用。我们已经在这样做（借对了） |
| ⑤ ★ **什么算一块积木** | **❌ 无通用解。** 研究原型：IBM **Mono2Micro**（拆巨石为微服务，自认 ~70% 且需人工）· MIT **CodePhage**（窄：只做漏洞修复式移植）· 东南大学 **ToolRosetta**（把项目批量转成 AI 可调用"工具"，而非可组装组件） | 启发式（role / fan-in / confidence） | ✅ **这一格是空的** —— 可以自造，但**只在自己的领域** |
| ⑥ ★ **契约本身** | **❌ 无通用解**（"这段代码承诺了什么"没有能自动判定的一般形式） | 部分（`contracts.json` / DSL contract）→ **这正是我们的 T18** | ✅ **这一格是空的** |
| ⑦ 组装 / 填胶 | 各生态的脚手架/模板；容器镜像 | 曾有（`assemble_bricks` = 文件复制 + import 重写，**仅 TS/JS/Go**） | ⚠️ 只有当 ⑤⑥ 站得住时才值得做 |

### 4.1 从这张表能直接读出的三件事

1. **设想的主体（①–④）都有主人** ⇒ 自造必然更差。这正是 `oss-prior-art-first` 说的"造整座房子"。
2. **只有 ⑤⑥ 是空的**，而它们恰好是**"格子"**。
3. ★★ **⑤⑥ 有一个反直觉的性质**：它们的消费者**可以不是运行时，而是人 / LLM**。
   ⇒ **做 ⑤⑥ 不需要先有 ①**！这是全篇最重要的一个解耦。

## 5. "我们现在的框架能不能抽象成万能框架？" —— **不能**

这一问值得单独回答，因为它不是"能不能"，而是**问错了层**。

| | 我们的框架 | 万能框架需要 |
|---|---|---|
| 抽象轴 | **符号 / 依赖 / 契约**（**静态**：读代码得结构） | **运行时对象模型 / ABI**（**动态**：让对象在语言间流动） |
| 时间 | 编译前 | 运行时 |
| 产物 | 可判定的结构（索引 / 影响面 / 契约） | 可执行的桥 / 组件 |

按 `oss-prior-art-first` 的三形态判读，这是第三种：**「看起来像、其实不同层」** ⇒
**不能互换，只能 compose**。

⇒ 正确动作**不是**"把我们的框架往那边拉"，而是：
**我们的 ⑤⑥ 可以"喂给" ① 那种运行时（给它提供契约），但替代不了它。**
⇒ 所以"先把我们这个项目往万能框架那边拉"这条路，**起点就不成立**。

---

## 5.2 ★★★ 「万能」有两个版本，只有一个能被上述结论证伪（2026-10-05 用户指出）

用户 2026-10-05 对上面的"不能"提出反驳 —— **而他是对的**，因为 §2/§5 否掉的是**版本 A**，
他描述的是**版本 B**。两个版本共用一个词，正是 §3 那句"设想混了六层"的同一种病：

> 用户原话（意思）：*「未来的开发势必是 AI 的开发……我说的**万能**是指在**工具 + 框架 + 模型三者协同**下进行万能。
> **只要许愿就能得到积木，得到积木就可以插进框架**，然后框架看作一个小型电脑系统，对外展示是 MCP 或应用，
> 对内它就是一个完整的操作系统，就像 Unix……各文件夹、各分类细分可以**包罗万有**，把各种工具的分类、
> 抽象层次全都展示出来，然后**只需要往里面堆积木**即可。」*

| | **版本 A：框架自己懂一切** | **版本 B：框架只给插槽，语义由模型填** |
|---|---|---|
| 谁负责 ⑤「什么算一块积木」 | **框架**要能自动切出有意义的单元 | **模型**（"许愿就能得到积木"） |
| 谁负责 ⑥「这块积木承诺什么」 | **框架**要能自动判定契约 | **模型写 + 判据守门** |
| ①–④ 怎么办 | **框架自造** | **不造**：要就交给 WASM CM / uniffi / Bazel 这些现成主人，不要就整个不需要 |
| 本文是否证伪它 | ✅ **是**（§2 六层里四层有主人 + ⑤⑥ 无通用解） | ★ **不是**。**§4.1 第 3 条恰恰是它的依据**：「⑤⑥ 的消费者**可以不是运行时，而是人 / LLM** ⇒ 做 ⑤⑥ 不需要先有 ①」 |
| 它的真难点 | 造算法（自动切积木 / 自动判定契约） | ★ **定义一套让模型能"可靠产出 + 落对位置"的插槽与判据** |

### ★★★ 判定「万能」的正确定义（这也是它和"能装一切错东西"的分界）

> **万能 ≠ 框架懂一切语义。**
> **万能 = 「①任何语义都能用同一种方式插进去」+「②插进去之后能用同一种方式组合」。**

- ① 只要求 **接口统一** —— **可能**，Unix 已证明。
- "框架懂一切语义"才要求通用解 —— **不可能**，§4 已证。

### ★★ 由此得到一条可命名的原则：**「无知的内核」**

Unix 内核**不知道** `ls` / `ffmpeg` / `nginx` 在干什么，**也不妨碍它万能** ——
它只知道 **ELF 格式 + 系统调用**。⇒ **框架"万有"的前提，是框架"无知"。**
一个试图"懂语义"的内核会立刻塌回 §3 那张表：①–⑦ 全得自己造。

### ★ 但版本 B 要成立，还缺一条腿：**「积木之间能组合」**

★★ **Unix 的万能来自 `|`，不是来自 `/usr/bin` 里什么都有。** 能装进去 ≠ 能互相插。
组合需要**双方对"流里是什么"有共同约定**（文本行 / 退出码 / stdin-stdout）。

本仓的三条腿现状（2026-10-05 实测）：

| 腿 | 内容 | 现状 |
|---|---|---|
| **① 接口统一** | `[B]` = 纯函数：显式参数 + 结构化产物 + `touched` | ⚠️ **只成了"产物"那一半**；**"入参"那一半没成** ⇒ 链接不起来 |
| **② 模型填语义** | 模型写 `[B]`、写语言包 | ✅ 已有；★ 且 2026-10-05 起**"加一门语言"真的只要一个文件**（族引擎已对语言零知识） |
| **③ 判据守门** | 受控词表机检 / 棘轮 / 各门 | ⚠️ 部分（`b_terms.ts` 是"**判据是机器**"的样板） |

⇒ **缺的正是第一条腿的另一半：入参形状统一 + "能把 A 的产物喂给 B"。**
⇒ 那才是"万能"这两个字真正的落点（`docs/todo.md` 里我称之为"补管道"）。

### ★★ 本仓 ↔ Unix 概念对照（哪些已对、哪些缺）

| Unix | 本仓对应物 | 现状 |
|---|---|---|
| 内核（不懂语义、只懂接口） | `[B]` 纯函数契约 + `[C]` 路由 | ✅ 形状已定（`Touched`） |
| 系统调用 | `tools/call` → `[C]` → `[B]` | ✅ |
| **管道 `\|`** | **A 的产物 → B 的入参** | ✗ **缺 —— 本仓最大的空格子** |
| 设备驱动 | **语言包**（"怎么读写 TS/Go/Python/C#/Java…"） | ✅ 2026-10-05 起：包对象自带 `exts` + 族引擎对语言零知识 ⇒ **加驱动 = 一个文件 + 注册一行** |
| 文件系统（位置由**结构**决定） | 域表 + 目录结构 | ⚠️ 位置仍靠**表**（T31 那族的病根：表会腐） |
| `/proc`（**现算**的事实，只读） | `code_health` / `structure:gap` | ✅ |
| `/etc`（人写的**意图**） | DSL / 域表 / 受控词表 | ✅ |
| 用户态工具 | 56 个 MCP 工具 | ✅ |
| ★ **`exec`：内核不必认识程序** | 加语言 / 加积木 **不改引擎** | ★ **2026-10-05 才第一次成为事实** |

### 结论：**算 —— 但要按上面的定义算，并且补齐"管道"那条腿**

按"能被同一种方式插进去 + 插进去之后能被同一种方式组合"这个定义，
本仓已经做到约 **三分之二**，而**剩下的三分之一（管道）是可判定的、具体的**。
★ 反过来：**若缺"组合"那条腿，版本 B 会退化成"能装一切错东西"** ——
那才是真正该怕的（不是"装不进来"，而是**装进来了却拼不出东西，且没人发现**）。

## 6. 我们真做过的尝试，与它的死因（阵亡记录，别丢）

代码侧我们**确实造了一半**（2026-08 ~ 2026-10，已删）。它是**七阶段管线**：

| 阶段 | 名字（已删） | 做什么 |
|---|---|---|
| 1 | `harvest_closure` | 给定种子文件，沿 import 边算"拎走它要连根带走什么"（**保留**：被 `dead_deps` 承重） |
| 2 | `extract_contracts` | 逐文件提 role / shape / effects（**保留**：是值得留的分析内核） |
| 3 | `harvest_from_url` | 编排：浅 clone → 建索引 → 抽契约 → 选种子 → 算闭包 → 入盒 |
| 3R-C | `reconcile_brick` | 用运行时观测事件对账盒内契约 |
| 4 | `search_bricks` | 积木盒货架：跨项目统一检索 |
| 5 | `assemble_bricks` | **拼装区**：把积木搬进**全新目录**，生成 go.mod、MVS 取高 |
| 6 | `slim_brick` | 效仿 Go 编译器 DCE：按 live 集把积木剪成衍生积木（配 `go-slim/` 剪刀） |

外加"项目融合"侧：`cross_repo_symbol_index`（两仓符号冲突）· `hybrid_precheck`（融合**判定**）。

### 6.1 它为什么是"假工具"（三条实测证据，不是感觉）

| 判据 | 实测结果 |
|---|---|
| **端到端跑通过吗** | **没有**。`.agent-io/` 下有 `features/` `code-snapshots/` `mindmap/` `drift/`，**独独没有 `bricks/`** ⇒ 积木盒从未建立 |
| **跨语言桥接实现量** | **0**。`assemble` 只做 **TS/JS 零改动** + **Go import 重写 + go.mod 生成**；设想要的是 Python↔Java |
| **"一个进程跑多语言"** | **0**。完全没有 |

⇒ **许愿与现状之间的距离 = 整个 ① 层**（而那层已有主人）。
⇒ 这就是它删掉的理由：**不是写坏了，是它站在一个不成立的前提上。**

### 6.2 但它有**一个真收获**（为什么这不算白干）

`slim_brick` 的思路原话是：「**效仿 Go 编译器——它只编译那些，我们也只读取那些**」。
这是一个**正确的、跨领域的机制观**：**用语言自己的编译器级可达性分析，来决定"什么不用带"**。
⇒ 这个想法**不需要万能框架**，它在**单语言**里就成立，且已经有价值（死代码/闭包最小化）。
★ **阵亡的是"盒子"，不是这条思路。**

## 7. 如果重开：三个**最小可证伪**实验（都不必自造框架）

★ 这是本文最该被复用的部分 —— 它们把"许愿"变成"能证伪的判据"。

### 实验 0（半天，尽量零成本）—— 先撞 ① 的墙
拿 WASM Component Model 官方 tutorial，用**两种**语言（如 Rust 组件 + Python 宿主）走通一次跨语言调用。
- **判据**：能跑起来，且接口由 **WIT** 定义（不是手写 glue）。
- **若这一步就卡住**（工具链、语言支持不齐）⇒ **① 这层我们更不该自造**，死心。
- ★ 先做这个的原因：它**最便宜**，且它若通了，后面 ②③ 都能直接站在它上面。

### 实验 1 —— 测 ⑤（"什么算一块积木"到底能不能自动）
用**我们的** `harvest_closure` + `extract_contracts`，对**一个真实项目**抽出 1 个候选积木，然后**人工判**。
- **判据（要量化）**：**人工改判率**。若 > 50% 需要人工纠正切点 ⇒ **⑤ 不能自动**，
  那"从任意项目抽零件"就是假命题，只能做成"给人**建议切点**"。
- ★ 这个实验**现在就能做**（两个工具都保留着）。

### 实验 2 —— 测 ②（能不能"零 glue"跨一种语言对）
只挑**一对**语言（如 TS ↔ Python），用现成工具（napi-rs / PyO3）做"**同一份契约 → 两端绑定**"。
- **判据**：不改一行手写 glue 就能调通。
- ★ 若通了 ⇒ ② 不用造；若不通 ⇒ 记下**卡在哪**，那才是真正的研究问题。

### 实验 3（可选）—— 测 ⑦ 的**最小**形态
"拼装"最小可用版 = **把两个已存在的包，装配成一个可运行项目**，不抽零件、只做装配。
- 判据：装配产物**能跑**且**依赖不冲突**。
- ★ 若连这个都要大量人工 ⇒ ⑦ 也不值得自造，直接用容器/镜像。

## 8. 回到终点：怎样才能"让编程没有门槛"？

设想的终点是「**也许编程就真的没有门槛了**」——这一句值得认真对待，因为**它的答案可能不在"万能框架"里**。

门槛的大头，**不是"语言不通"**（那是 ① 的问题，且正在被标准化解决），
而是「**改了一处，不知道会坏什么**」。

⇒ 所以"无门槛"更可能的来源是：
**LLM（有意图的人） + 可判定的结构（改了会坏什么，机器能算出来）**。

★ 而**后者正是我们项目一直在做、且真在用的那些东西**：
`code_health`（83 次调用）· `edit_code`（58）· `find_references`（31）· `impact_analysis` ·
`rename_symbols` / `rename_files`（安全改名）· `structure_gap`（结构意图 vs 现状）。

⇒ **结论（也是本文的立场）**：
> **造"万能运行时"是别人的格子（①）；造"可判定的结构"是我们的格子（⑤⑥）。
> 而通向"无门槛"的那条路，更可能经过我们的格子，而不是绕过它。**

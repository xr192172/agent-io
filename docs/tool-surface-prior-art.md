## 4. ★★★ 一条与我们**正面冲突**的设计主张

| | 先例（HyperTool / ToolPipeline / Code Mode） | 本仓现行设计 |
|---|---|---|
| 主张 | **确定性链不该对模型可见** —— 把子步骤折叠进**一次外层调用 / 一段代码**，中间值**局部传递**，模型只做高层判断。原话：*"the LLM must act as the glue between tools for **deterministic** operations that could be handled more efficiently by code"* | 每一步**都是**模型可见的一调用，靠 `touched` 交接、靠「下一棒提示」提醒 |
| 读数 | HyperTool：MCP-Universe **15.69% → 35.29%**（Qwen3-32B） | 我们**没有**读数 |
| 机制 | ToolPipeline 的 **adapter = 普通代码，不是 LLM 调用** | 目前"适配"由调用方（LLM）手工做 |

★★ **调和点（我认为这是本次检索最值钱的一句）**：
本仓的 `chainExprOf` **已经**把边分成两类 ——
- `cardinality: 'single'` ⇒ `touched.<键>`（**集合确定只有一个 ⇒ 取即确定 ⇒ 无需判断**）
- `cardinality: 'pick'` ⇒ `touched.<键>[i]`（**可能需要选 ⇒ 语义判断 ⇒ 必须留给调用方**）

⇒ **`single` 的那些段正是"可以折叠"的**（确定性、无判断）；**`pick` 的必须保持可见**。
这与先例的主张**并不矛盾** —— 先例说的是"**确定性**的部分不该占模型的决策"，而 `pick` **不是确定性的**。
⇒ 结论：**折叠的边界 = `cardinality`**，而这条边界**我们已经有数据**（不是新发明的判据）。

## 8. 第一手读数 + 一个 SDK 层面的决定性发现（2026-10-06 晚，用**真 server** 量的）

### 8.1 `tools/list` 载荷（★ 一手：起 stdio 客户端向真 server 发 `tools/list`）

| 量 | 值 |
|---|---|
| 工具数 | **61** |
| `tools/list` JSON | **87,379 字符**（CJK 17,808 / ASCII 69,571） |
| 粗估 token | **28,078 ~ 38,679**（CJK 0.6~1.0/字 · ASCII 0.25~0.30/字 —— **估算，非分词器**） |
| 平均每工具 | **1,432 字符** |
| 最占地方的 5 个 | `refactor_pipeline` **4292** · `get_dsl` 3620 · `edit_code` 3298 · `rules` 3260 · `edit_dsl` 2993 |

★ **前 5 个占 17,463 字符 = 载荷的 20%** ⇒ "砍描述"有明确靶子。
★ 对照 §3（二手）：58 工具 ≈55k tokens / 每工具 ≈1000 ⇒ **我们同量级**（每工具略轻）。

### 8.2 ★★ 一个陷阱（本日**第二次**撞 zod v4）

先用 `zod-to-json-schema` **本地折算**得 33,633 字符 —— ★ **那个数不可信**：
它在本仓（zod **4.4.3**）**61 个全部抛错**（该库面向 zod 3）⇒ 折出来的**不含参数 schema**，
**低估 2.6 倍**（33,633 vs 真值 87,379）。
⇒ 两条教训：① 折数**必须拿真值对一次**；② **"全抛错"这种信号会被 `catch` 吞掉**（我第一版只在一个计数里留了 `fail=61`，差点当成正常）。

### 8.3 ★★ SDK 层面：「只裁 `listTools`、不裁 `callTool`」在这套 API 下**做不到**

一手（`node_modules/@modelcontextprotocol/sdk/dist/esm/server/mcp.js`）：

| 行 | 内容 |
|---|---|
| `:67-68` | `ListToolsRequestSchema` handler ⇒ 读 `this._registeredTools` |
| `:100-102` | `CallToolRequestSchema` handler ⇒ **读同一张 `_registeredTools`** |
| `:649` | `registerTool` ⇒ `this._registeredTools[name] = registeredTool` |
| `:626` | 有 `delete this._registeredTools[name]` ⇒ **移除**是支持的（= 真的不能调了） |

⇒ **两者同源**：要么都暴露、要么都不能调。类注释说"要自定义 handler 就用底层 `Server`"，
但 `assertCanSetRequestHandler` 已把这两个方法占住 ⇒ **不能简单覆盖**。

**对「面」的结论（落点要改）**：

1. ❌ **不能靠"裁 `listTools`"** —— 原方案的那条铁律在这套 SDK 下不成立。
2. ✅ **可用的两个杠杆**：
   - **(a) 客户端侧开关**（客户端都支持禁用单个工具；`install_mcp.mjs` 可以生成"推荐启用集"）
     —— 这正是 **Serena「可选工具」** 的做法；
   - **(b) 描述瘦身** —— 不改注册结构、不碰 SDK，**直接减 token**（§8.1 已给出靶子）。
3. ★ 我们原方案的 `capability_map` + `direct`（"不裁 list，改裁**注意力**"）**反而成了唯一无需改协议的路** ——
   这一格我们**本来就对**，只是**理由要换**（不是"裁 list"，是"客户端开关 + 描述瘦身"）。

## 9. 盲测基准：方法与两轮读数（2026-10-07，一手）

> **为什么要它**：§3 那些数字（43%→14% 等）**全是二手的**，我们自己**一次都没量过**"选错工具"。
> 这一节就是"把二手换成一手"的最小复刻。

### 9.1 方法（可复跑）

| 步 | 做法 | 防的是哪个坑 |
|---|---|---|
| 1 | **被试 = 全新上下文的子代理**（它不知道哪个是对的） | ★ **我自己当被试毫无意义**（这些工具是我做的，我"必然"选对） |
| 2 | 两个**面材料**由探针生成（`name` + **完整 description**）：`face_all.txt`（61 个）/ `face_composed.txt`（9 个） | 保证"两个面"是**真材料**，不是我口述 |
| 3 | 题面**不许出现工具名**（说"文件"/"符号"/"未用到的 import"，那是**任务语言**） | 否则变成"按名字匹配" |
| 4 | 输出**机器可读**（`任务N: <工具名> \| 置信度: 高/中/低 \| 理由: …`） | 便于逐条比对，不靠印象 |
| 5 | 允许答 `NONE`（"清单里没有能干这个的"） | ★ 否则被试会**硬凑**，把"够不着"伪装成"选错" |

**材料口径（★ 别和真载荷混）**：`face_all.txt` **59,400 字节** / `face_composed.txt` **14,439 字节**；
**不含参数 schema** —— 真 MCP 载荷是 **87,379 字符**（§8.1）。⇒ 被试面对的材料**比真实更小**。

### 9.2 两轮读数（6 个任务 × 2 个面 = 12 次选择）

| 轮 | 任务（题面原话要点） | 61 面 | 编排面（9） |
|---|---|---|---|
| 一 | 看 `Kk` 在哪些文件被引用（改名前置） | `find_references` ✓ | `find_references` ✓ |
| 一 | 模块级符号从 `a.ts` 搬到 `moved.ts` + 改 import | `move_symbol` ✓ | `move_symbol` ✓ |
| 一 | 清掉没被用到的 import | `remove_dead_imports` ✓ | ★ **`NONE`**（诚实） |

| 二 | 给函数补一句语义注释 | `annotate_functions` ✓ | ★ **`edit_code`** ✗（**自标"中"置信度**） |

### 9.3 ★★ 结论（三条，都可证伪）

1. ★ **"列 61 个会导致选错"在我们语料上仍未被观察到（6/6）。** 连最像的镜像对
   （`rename_files` vs `rename_symbols`）两个面都选对 ⇒ **要么描述真的清晰，
   要么"选错"需要比这更大的相似度**。⇒ **先例那个 43%→14% 不能拿来说我们自己。**
2. ★★ **"少列"的真实代价被测出来了，而且不是"错误率上升"**：
   - 覆盖不到时它会 **①诚实说 `NONE`**（任务 3）**或 ②硬凑一个近似的**（边界任务 2，选 `edit_code` 补注释）；
   - ★ **硬凑那次它自己标了"中"置信度** ⇒ **"够不着"这个状态是**可被自己察觉**的**。
3. ★★ **编排面缺什么，有了任务覆盖层面的证据**（不是用量）：`remove_dead_imports`（清 import）·
   `annotate_functions`（补注释）—— **两者都是日常高频类**，却都不在面内（8 个 = 派生链 4 + `direct` 4）。

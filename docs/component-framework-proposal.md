## 0. 一句话定位

**做一个"组件框架"：让 LLM 以"搭积木"的方式组装功能，而"能不能拼"由框架判定、不由 LLM 猜。**

- **做**：⑤ 什么算一块积木 · ⑥ 一块积木承诺什么 · ⑦ 怎么把积木装配起来 · ⑧ 谁有权进、怎么退场 · **★ 管道（A 的产物 → B 的入参）**
- **不做**：跨语言运行时 · 跨语言绑定生成 · 多语言构建系统 · 包管理器（这四层已各有更强的主人，见 §5）

---

## 1. 结论摘要（TL;DR）

1. **现在不另立项目。** 框架的"技术底座"四层（①–④）都不该自造；**能自造的只有 ⑤⑥⑦⑧ + 管道**，而其中 **⑤⑥ 已经在现有项目里有落地**（`contracts.json` / `Touched` 契约 / 受控词表）。
   ⇒ 新开一个仓 = **把已有的 ⑤⑥ 扔掉重做一遍**，正是 `docs/frontier-universal-framework.md` §6 那次阵亡的同一种错（立在未验证的前提上）。
2. **先出一份企划书（本文），并把"立项"变成一个可判决据** —— 见 §8 的三个门。
3. **框架真正缺的那条腿是「管道」**（`A 的产物 → B 的入参`）。它**不需要新项目**，它是现有项目**已经排在下一步**的事（`todo.md` ④ 统一 `[B]` 契约形状）。
4. **新项目的正确时机**：管道与身份双双验证通过（§8 门 G1+G2）**之后**，且只在"现有项目装不下"时才另立仓。**新仓是里程碑（§9 的 M2+），不是起手式。**

## 2. 问题陈述

AI 写代码现在有两个稳定痛点：

| 痛点 | 现象 | 根因 |
|---|---|---|
| **重复造轮子** | LLM 为一个 logger / HTTP client / 校验器反复重写 | 没有"写之前先查已有"的强制路径（`§11.3-④` 的"倒逼"） |
| **组合靠人** | 两个各自没问题的功能拼一起就坏 | **没有统一接口 + 没有组合的判据**（`§11.4` 的"组合算子"） |

★ 注意：**这两个痛点的解，都不在"打包"里，而在"契约 + 组合"里。** 这是本文与"积木=压缩包"设想的分别。

## 3. 为什么"另立项目"是错的起手

| # | 理由 | 依据 |
|---|---|---|
| 1 | **底座四层有更强的主人**，自造必然更差 | `frontier §4` 表：① WASM CM / GraalVM · ② uniffi / SWIG · ③ Bazel · ④ MVS / Nix |
| 2 | **能自造的两格（⑤⑥）已经在现有项目里** —— 另立仓等于重做 | `todo.md` T43：⑥ 已有落地（产物端 `Touched` 契约 + 受控词表 + 量具棘轮） |
| 3 | **历史已经证过一次同样的错** | `frontier §6`：上次"积木线"删掉的理由**不是写坏了，是站在不成立的前提上**；那次前提 = 版本 A |
| 4 | **框架缺的不是"新地方"，是"新机制"** | `frontier §5.2`：三条腿只差第一条的另一半（入参形状 + 管道） |

⇒ **一句话**：不是"换个地方就能搭起来"，是"**有一条机制还没搭**"。换地方不会让它出现。

## 4. 分层盘点：谁做哪一层（★ 先查先例，再决定自造与否）

| 层 | 内容 | 已有主人 | 我们 | 自造？ |
|---|---|---|---|---|
| ① | 跨语言运行时 / 内存 / ABI | **WASM Component Model**（WIT）· GraalVM Polyglot | 0 | ❌ 借 |
| ② | 跨语言绑定生成 | **uniffi** · napi-rs · PyO3 · wasm-bindgen | 0（只有 Go→TS 源码翻译） | ❌ 借 |
| ③ | 多语言构建编排 | **Bazel** · Pants · Nx · Buck2 | npm scripts + 一个 Go 小工具 | ❌ 借 |
| ④ | 依赖统一 / 去重 | **MVS** · Nix · OCI layer · Bazel remote cache | 只有 2 个生态（Go MVS + npm） | ⭕ 借（已在做） |
| ⑤ | ★ **什么算一块积木** | ❌ 无通用解（Mono2Micro ~70% 且需人工） | 启发式（role / fan-in / confidence） | ✅ **做**（只做"推荐切点"） |
| ⑥ | ★ **一块积木承诺什么** | ❌ 无通用解 | 部分（`contracts.json` / DSL contract） | ✅ **做** |
| ⑦ | 组装 / 填胶 | 各生态脚手架 / 容器镜像 | 曾有（`assemble_bricks`，已删） | ⚠️ **只在 ⑤⑥ 站得住时做** |
| ⑧ | 信任 / 权限 / 生命周期 | ❌（原表没有这层） | 0 | ✅ **做**（跨信任域才必需） |
| ★ | **管道 `A 产物 → B 入参`** | ❌ | ✗ **缺（本仓最大的空格子）** | ✅ **做**（★ 最高优先） |

★ **只有 ⑤⑥⑦⑧ + 管道 是空格子。** 其余的每一次自造都是"造整座房子"（`oss-prior-art-first`）。

## 5. 我们要做的那几格：定义

### 5.1 ⑤ 什么算一块积木 —— **只做"推荐切点"，不承诺"自动"**

- **判据**：用 `harvest_closure` + `extract_contracts` 对真项目抽候选，量化**人工改判率**。
- **门**：改判率 > 50% ⇒ "从任意项目自动抽零件"是假命题 ⇒ **只做"给人 / 给 LLM 建议切点"**（自动化止步于此）。
- ★ 不承诺"自动切积木"——`frontier §4` 已证无通用解。

### 5.2 ⑥ 一块积木承诺什么 —— **模型写 + 判据守门**

积木的**契约**必须含三样（缺一不可）：

| 要素 | 内容 | 为什么必需 |
|---|---|---|
| **输入 / 输出 schema** | 结构化（不是 `message` 字符串） | LLM 靠它选积木；框架靠它判可连性 |
| **语义类型（受控词表 ID）** | 不是自由字符串，而是**全局注册的稳定 ID** | 见 §5.3 |
| **例子 / 属性测试** | 至少一组"投什么 → 出什么"的样例 | 黑盒论证的前提（`§11.4-②`） |

★ **契约必须"全函数"**：输入域全覆盖 + 每个输入有定义输出。否则黑盒实际是**灰盒**，未定义处正是组合炸掉的地方。

### 5.3 ★ 语义身份：**受控词表**（这是"语义化名字"之前的那一步）

- "把 `String` 起名叫邮箱"改的是**名字**。框架遇到 `Email` / `邮箱` / `contact_email` 仍不知是不是同一个。
- ⇒ 需要**全局 + 稳定 ID + 机器可校验的受控词表**（= `/etc`：人写的意图，**需 curation，不会自动长出来**）。
- ★ 本仓现成样板：`b_terms.ts`（受控词表 = 机器判据，**活**）；反例：手工名字表（**腐**）。
- ★ 一句收口：**"一切皆文本"解决"能用同一种方式处理"，不解决"两个文本是不是同一个意思"。**

### 5.4 ⑦ 组装 / 填胶 —— **胶水由 LLM 写，但"可连性"由框架判**

- 组合算子 = **有向图**（A → B → C），每条边带**契约匹配证据**。
- 框架能判的：schema 层面**类型可连**（受控词表 ID 相同 / 有已注册的 adapter）。
- 框架判不了的：**语义兼容**（`{b: string}` 不知是邮箱还是手机号）⇒ 由**例子 / 运行期**裁定。
- ⇒ 按需生成 adapter 骨架交给 LLM 填；**不承诺"零胶水"**。

### 5.5 ★★ 管道（最高优先）—— `A 的产物 → B 的入参`

- **这就是 `frontier §5.2` 三条腿缺的那一条**，也是"工具链做不出来"的根因。
- **已实测在数据上通了**：`find_references.touched` → 直接构造 `rename_symbols` 入参（`read_files[0]`→`file`、`symbols[0]`→`symbol`，**零字段名翻译**）→ 跑通。唯一手工动作 = **取 `[0]` = "选"**。
  ⇒ 缺的**不是数据/形态**，是「把"从集合选一个"写成明文的约定」+「一条链的**真跑验收**」。
- ★ **这条不需要新项目** —— 它就是 `todo.md` ④ 统一 `[B]` 契约形状的直接产物。

### 5.6 ⑧ 信任 / 权限 / 生命周期

- **单信任域（"项目全是我们的"）⇒ 本层不存在**（无第二信任主体）⇒ **不需要凭证 / 签名 / 准入**。
- **跨信任域（第三方积木 / 公开市场）⇒ 必需**，且需要得**比操作系统更多**（在执行第三方的构建产物）。
- ★ **一条硬约束（若真做）**：**凭证不能住在积木里** —— 住进去 ⇒ 内容哈希会泄露凭证、跨用户去重会串凭证 ⇒ 凭证必须由**框架在边界注入** ⇒ 积木**不能自包含**。
- ★ **OS 类比的正解**：OS 有"重重认证"**因为它托管互相不信任的代码**；积木 = 任意代码，**契约是人机接口、不是权限边界** ⇒ 去认证 + OS 级权限 = **每块都是 root**。

## 6. 架构草图（三层，各自归属）

```
┌─ 积木（Block）= 一等公民 ─────────────────────────────┐
│  manifest.json    id · version · 依赖(精确版本) ·       │
│                   导出接口清单 · ★子块内嵌清单 · stateless? · 凭证需求声明
│  contract/        输入/输出 schema(受控词表 ID) · 例子/属性测试
│  impl/            实现（语言无关：编译成 WASM component 或 保留源码+声明）
│  tests/           黑盒/白盒/变异测试（★ 封装前的验证证据）
└──────────────────────────────────────────────────────┘
        ↑ 由「装配器」取用、去重、拼成组合体 ↓
┌─ 框架四件套 ────────────────────────────────────────┐
│  1 注册表 Registry  受控词表 + 积木目录 + 召回索引   （/etc，人 curate）
│  2 装配器 Assembler 依赖图解算 · 内容寻址去重 · 生成组合体   = ⑦
│  3 运行器 Runner    ★底座用 WASM CM / OCI（不自造）        = ①
│  4 治理 Governance  凭证注入 · 准入判据 · 生命周期          = ⑧
└──────────────────────────────────────────────────────┘
        ↕ 组合体 = DAG（A→B→C），边 = 契约匹配证据；运行期 correlation id 贯穿
```

★ **两个易漏点**（都写进 manifest 才算数）：
- **子块内嵌清单**：要对"大包内嵌小包"做**子块级去重**，制品必须声明"我内嵌了哪个积木、在哪个导出/哪段范围"。**没有边界标记，就没有哈希的锚点。**
- **`stateless?` 声明**：无状态积木可安全共享单例；有状态（连接 / 缓存）**不能因实现相同就合并实例**。哈希相同只说实现相同，**不说配置相同**。

## 7. 组合算子（★ 唯一未定的地基）

"框架都没开始搭"的最根本原因，是**这个还没定**。候选与判据：

| 候选算子 | 含义 | 判据 |
|---|---|---|
| **类型导向接线** | schema 可连（受控词表 ID 相同 / 有 adapter）就自动接 | 组合体能否通过**例子验证**（每条边给样例，跑通） |
| ~~函数组合 / 服务编排 / 依赖注入~~ | 三选一的老问法 | **偏了** —— 三者可以并存；真正的判据是"**能不能被验证**" |

⇒ **本文的立场**：算子 = **带证据的 DAG**；"能不能拼"**由例子/属性测试裁定**，不由类型签名单方面裁定。

---

## 8. ★★★ 决策门（全文最重要的一节：**先有判据，再动代码**）

按成本从低到高。**任一门的结论都能否决整个企划** —— 这正是它的价值。

| 门 | 实验 | 判据（要能变红） | 若不通 |
|---|---|---|---|
| **G0**（半天，最便宜） | 用 **WASM CM 官方教程**走通一次跨语言调用（如 Rust 组件 + Python 宿主） | 能跑起来，且接口由 **WIT** 定义（不是手写 glue） | **① 层死心** ⇒ 框架只能走"同语言先行"的窄路 |
| **G1**（便宜） | **同一功能写两次，框架能否判出"已有等价积木"并拦住第二个** | 两个读数：**召回率**（真等价被列出）· **误拦率**（不等价被拦） | 召回低 ⇒ 身份/倒逼不成立 ⇒ **市场无意义**（复用率 0） |
| **G2**（★ 现在就能做，且在现有仓） | 把 `find_references → rename_symbols → edit_code → run_tests` **真跑通一条链** | 一条链跑通，且**产物 = 下一步入参**（零字段名翻译） | **管道不成立** ⇒ 框架无意义 ⇒ 企划终止 |
| **立项门** | **G1 + G2 双通过**，且"现有项目装不下" | — | ⇒ **不另立仓**，继续在现有项目里长 |

★ **顺序**：**G2 → G1 → G0**。理由：G2/G1 在现有仓就能做、直接测本企划的命门；G0 是"借底座"的可行性，最便宜但它通了也不代表企划成立。

## 10. Anti-goals（明确不做，防止重蹈 §6）

1. ❌ 不造跨语言运行时 / ABI（① 有主人）
2. ❌ 不造绑定生成器（② 有主人）
3. ❌ 不造构建系统（③ 有主人）
4. ❌ 不造包管理器（④ 有主人）
5. ❌ 不承诺"自动切积木"（⑤ 无通用解 ⇒ 只做"推荐切点"）
6. ❌ 不承诺"自动判定契约"（⑥ ⇒ 模型写 + 判据守门）
7. ❌ 不承诺"任意两块能拼"（组合爆炸 ⇒ **只保单块 + 逐组合验证**）
8. ❌ 不做"保谁进市场"的签名/溯源 —— **单信任域下不需要**（仅跨信任域才需要，见 §5.6）
9. ❌ 不把"省运行期实例"当卖点 —— 一旦"再编译成静态包"，收益只剩"产物更小"（已被 tree-shaking / link-time dedup 解决）

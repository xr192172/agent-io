## 1 · 实际侧 DSL（2026-10-18 用户原话）

> "首先我们现有的有一个实际侧的 DSL，它的来源是**源码抽一直往上抽象**，然后作用是让你可以**一次性看清整个项目的全貌**并且了解它里面**符号级的依赖关系**之类，而且是**渐进式披露**的 —— 你想看最浅层的你就看 DSL，想看深一层就看 DB，再深一层就继续往下探，一直探到源码。"

| 要点 | 落地形态 |
|---|---|
| **来源**：源码 → 往上抽象 | `.agent-io/live/<f>.dsl.json`（扫描）+ `cache.db`（符号/调用） |
| **作用**：全貌 + 符号级依赖 | 全局 = 641 节点；符号 = `cache.db`（7528 条 call / 4832 条 type_ref / 1223 条 import） |
| ★ **渐进式披露** | **DSL（浅）→ DB（深一层）→ 源码（最深）** |

★ **这一条对实现的约束**：**DSL 不该"什么都装"** —— 越深的东西越该留给 DB 和源码。

## 2 · 为什么不能直接改源码

> "光看没有别的修改，或者说想要进行修改的话，**你不能直接在源文上进行修改，因为它会被重建被覆盖**，所以你需要将其**复制成一份一模一样的设计 DSL**，或者说设计侧的这些全套的流程，**除了源码，因为源码它是绑定的**。"

| 要点 | 落地形态 |
|---|---|
| **实际 DSL 会被重建覆盖** | `import_project` 重扫（设计侧受"意图保护"拒绝覆盖，2026-10-18 已加） |
| **复制一份一模一样的设计侧** | `.agent-io/design/<f>.dsl.json`（fork 自 live，641 节点） |
| ★ **除了源码**（源码是绑定的） | 设计侧**没有源码副本** —— 源码只有一份 |

## 3 · 设计侧的流程（**反着来**）

> "那么你就反过来……用户需要一个功能，你把这个**需要这个功能登记下来**，然后**在设计 DSL 上面进行修改**，并且把你的每一段修改对应的、或者说每一个范围的修改对应的是用户说的哪个功能，**贴上对应的这个决策卡**，然后**再继续往下探，探到 DB 层** —— 这个功能实现的话需要有哪些具体的这些，**这要比你直接改源码要快**，再继续往下探，一路探到源码。"

```
用户需求 → 登记 → 改设计 DSL → 每段修改贴决策卡（对应哪句需求）
  → 下探到 DB 层（实现需要哪些具体的符号/调用）
  → 一路下探到源码
```

★ **对实现的约束**：**设计侧的三层（DSL / DB / 源码）该能逐层下探**，而且**每一层都要能挂"对应哪句需求"**。

## 4 · 决策卡的两个作用（**第二个是最容易被忽略的**）

> "决策卡还有另一个存在意义：一是为了**规范化的、有迹可查**地告诉你为什么要改这个地方；**二是可以让不同的子代理、甚至同一个子代理的不同轮次** —— 因为同一个哪怕你是同一个 agent，你的上下文也是有限的，**当你压缩完上下文了之后你可能就不知道要干什么了**，但是当你一看到这个**角色卡、整个这个 DSL 的时候你就知道自己接下来应该要做什么**。"

| 作用 | 落地形态 |
|---|---|
| ① 有迹可查（为什么改） | `decision.creator` / `decision.source` |
| ★★★ ② **上下文压缩后的"我该做什么"** | **`decision.summary` + `decision.handoff`** —— 一张卡 + 一遍 DSL 就能接手 |

★★ **这一条对实现的约束**：**决策卡必须"自足"** —— 一个没有上下文的 agent 只看它，就知道**要做什么、做到什么程度、交给谁**。

## 5 · 三个工具（用户称之为「精髓」）

> "我们还有一套**更好用的工具**，比如说**智能读、智能编辑和智能重写**这三个工具是整套这个 MCP 工具里的精髓，**我希望你是经常用它的**，而且这一套工具就是为了这个 DSL 而实现而服务的，因为它们可以**直接通过这个 DSL 去定位到那个范围**，然后你只需要**把旧串换新串**就可以，或者说不是旧串换新串，就是**它会帮你把所有的依赖关系全都处理好**。"

| 工具 | 我理解对应 | 作用 |
|---|---|---|
| **智能读** | `explore_code` / `get_dsl` | 通过 DSL 定位范围（不是全文 grep） |
| **智能编辑** | `edit_dsl` / `edit_code` | 在范围内改，**依赖关系自动处理** |
| **智能重写** | `apply_refactor_plan` / `refactor_pipeline` | 整块重写（不是逐串替换） |

★★★ **这一条对实现的约束（也是最重的一条）**：
**这三个工具是"入口"，我的脚本（`dec` / `dep` / `fork` / `diff` …）是"脚手架"** ——
★ **脚手架不该长期存在，它该被这三个工具吸收。**

# 裁决（2026-10-18 用户答复）

## 冲突 1 → **副本**（设计侧是实际的完整副本，改动才写增量）

> "由于我们有对拍，所以对拍后我们修改了文件，就修改了源码，此时再重算实际侧，然后再进行对拍，你会发现它们是一致的。
> 这才证明你设计或者说你的实现是对的，你的实现和你的设计是对得上的。"

★ **所以 `calls` = 全量副本 + `dep` 的增量**，**"没动的部分" = 设计认可现状**（不是空白）。
★★ **而"一致"就是证明**：对拍 → 改源码 → 重算 → 再对拍 ⇒ 一致 ⇒ 实现和设计对得上。

## 冲突 2 → **不冲突**：三个工具操作源码，脚本管设计侧

> "智能读、智能编辑、智能重写都是**直接对源码进行操作**的，和你这个应该不冲突。"

★ **所以**：`explore_code` / `edit_code` / `apply_refactor_plan` = **源码侧**；
`dec` / `dep` / `fork` / `diff` / `contract` = **设计侧**。**两边各管一头，不抢。**
★ 而 `edit_dsl`（操作 DSL 的）**仍是空白** —— 见下「还有什么问题」。

## 冲突 3 → **现状对**，且**重写也是渐进式深入、重算逐层返回**

> "渐进式披露是**渐进式**的，我们的**重写也是渐进式深入**的：先有意图 → 重写设计 DSL → 往深入写设计 DB → 再往深入写实际源码；
> 然后重算的时候，它又会**从源码再一层层层渐进式地返回**实际的 DSL。"

★★ **这一句补上了我漏掉的【返回路径】**：
```
写：意图 → 设计 DSL → 设计 DB → 源码
返：源码 → 实际 DB → 实际 DSL（重算时逐层返回）
```

## 冲突 4 → **A**：设计侧不跟实际变（实际是追上来）

# 补充定义（2026-10-18 用户）

## 5 · 决策卡的作用域 = 一群**互相连通的点**

> "并不是一个节点，而是一群节点 —— 一群互相连通、互相影响的点，因为改一个功能它肯定有一群点。
> **只要一个节点上挂着角色卡，它周边的这一群点都附属于这个角色卡。**"

★★★ **所以 `decision` 的作用域 = 一个【连通子图】**，不是一个节点。

★★ **而“连通的点”不需要新造概念** —— **它就是 `impact_analysis` 的【反向可达闭包】**：
```
一个节点挂卡 ⇒ 它的"周边连通点" = 从它出发的反向闭包（谁依赖它 / 它依赖谁）
⇒ ★ decision.scope 可以从 impact_analysis 的结果推出来
```

## 6 · 设计 DB → 源码：**接入重构线**（用户建议）

> "设计 DB 到源码这一节，你去看一下重构工具能不能接入进来 —— 把这里受到影响的这些点，
> 便利地帮你列出来，还差什么要改。我们的重构线做得还是挺完善的，只是差把它接进去。"

★ **结论：能接，而且不用改它。** `impact_analysis(change_points)` 的输出就是那份清单：

| 它给什么 | 对应我们要什么 |
|---|---|
| 直接/间接受影响文件 | ★ **还差什么要改** |
| 引用证据行 | ★ **为什么这里要改** |
| 风险排序（波及半径 × 距离） | ★ **先改哪** |
| `fell_back` 标记（符号级解析不到 ⇒ 降级整文件闭包） | ★ **诚实标注"这个只能粗判"** |

★ **而 `refactor_pipeline` 是另一件事**（它是**自动改**：死 import / 死语句 / 包迁移 / 函数注释）——
★ **现在不需要它“改”，只需要 `impact_analysis` “列”。**

## 7 · diff 之后的两条路（用户确认）

```
diff 出差异
  ├─ ★ 无卡 ⇒ 补卡（dec --init --source …）→ 再上架
  └─ ★ 有卡且未实现 ⇒ 直接上架任务系统 → 供人接取 → 设计 DSL → 设计 DB → 源码
```

★ **而“曾经挂过卡的”** 就是第二条路（跳过补卡）。

## 8 · 设计侧 DB 的第三个用途：重写时看【影响面】（2026-10-18 用户）

> "这也是为什么我要你**设计侧也要有个 DB** 的原因 —— 你**重写的时候你也不能是胡乱重写**，
> 你要去看到这些**影响面**，然后把这些影响面也整好。就像是你直接写源码的时候你不也要分析这些吗？
> **你不能是直接加一个功能就是加一个功能吧** —— 那样的话后续必定有 bug、必定要打补丁。"

★★★ **所以设计侧 DB 该有三样，而第三样现在没有**：

| 层 | 现在有吗 | 用途 |
|---|---|---|
| **符号**（`contract.ts`） | ✅ 27 条 | 我要什么 |
| **调用**（`calls`） | ✅ 7533 条 | 谁调谁 |
| ★ **影响面** | ❌ **没有** | ★ **改这里会炸哪里** |

★ **而“影响面” = `calls` 的【反向闭包】** —— 可以从设计侧**自足算出来**（不用 MCP）。
★★ **而 `impact_analysis` 多给两样**：**引用证据行** + **风险排序**（`calls` 没有这两样）。

★ **所以两条路**：
- **A**：从 `calls` 算反向闭包 —— **设计侧自足**，但没有风险排序
- **B**：跑 `impact_analysis` —— 有证据+排序，但**要调 MCP**（设计侧不自足）

## 9 · 补丁的态度：**整个重写，不打补丁**（2026-10-18 用户）

> "而且**打完补丁我们对于补丁的态度也是直接整个重写，而不要打补丁** ——
> 因为**补丁只管那一下**，而且**整个应用的逻辑不流畅**。"

⇒ ★ **所以“修一个 bug”不是“加一行 if”**，是**把那一块重写清楚**。
⇒ ★★ **而那需要“影响面”**（知道那一块牵动谁）⇒ 回到 §8。

★★★ **这一条把“为什么不打补丁”和“为什么要设计侧 DB”连起来了**：
**没有影响面 ⇒ 只能打补丁（因为不知道重写会牵动谁）⇒ 打补丁 ⇒ 逻辑不流畅 ⇒ 更多补丁。**

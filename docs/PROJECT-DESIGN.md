# Agent IO：长期项目设计与接续开发契约

状态：目标设计 + 当前实现的差距说明。不是现状说明，不是用户原话，不是一次性待办清单。

读者：接手本项目的模型、实现者与维护者。先读本文，再按第 15 章选择下一件工作。

## 0. 本设计的边界与效力

本设计回答：**怎样把任意已有软件，持续改造成更简单、紧凑、可验证的项目，或在其上可靠地新增功能。**

- 用户愿景原文唯一住处：`docs/VISION-ORIGINAL.md`。本文是解释与实现设计，不得反向改写原文。
- 当前现状唯一入口：`docs/INDEX.md`。本文不代替现状表。
- 轴心裁决记录：`docs/PIVOT-VERDICT.md`。出现方向改变时新增裁决，不静默改写历史。
- 删除记录：`docs/RETIRED.md`。已证明不该重建的东西，不因“这次想做完整”而复活。
- 本文没有承诺“自动判断什么设计最好”；模型与人负责语义选择，框架负责事实、定位、机械展开、可回溯执行和对账。
- 本文中的数量、工具和路径不是永久指标。实际数量由注册表与检查器现算，不得写入验收判据。

**防漂移不是让文档永不变，而是：愿景变更只能由用户提出；实现变更必须保留对象、证据、代价与替代路径。**

## 1. 不可漂移的产品定义

Agent IO 是面向 AI 开发的项目理解与渐进改造底座。

它改变的不是“模型能不能生成一段代码”，而是模型进入已有项目后的工作方式：

```text
不靠局部 grep 猜项目
→ 先取得与功能有关的可信上下文
→ 在设计上表达目标与变化
→ 把变化定位到文件、符号、依赖和行为
→ 逐步执行机械改写，保留语义决策
→ 重建实际事实并与设计对账
```

### 1.1 产品只承诺四件事

1. **理解**：面对陌生项目，找到功能相关位置及其结构、关系、行为证据。
2. **设计**：允许目标结构暂时不同于当前实现，并保存原因和验收方式。
3. **改造**：按设计差异逐步执行重构、新增、退役或翻译，不要求整仓重写。
4. **对账**：证明哪些要求已落实、哪些尚未落实、哪些无法判断。

### 1.2 不承诺什么

- 不保证所有语言一开始就有相同精度。
- 不保证编译通过就是行为等价。
- 不保证结构与设计一致就是设计优秀。
- 不保证所有文件都需要人写职责或判据。
- 不保证所有变更都能机械执行。
- 不通过工具数、判据数、字段填充率证明产品成功。

## 2. 愿景整理稿

> 本章是对用户历次表达的完整整理，不是逐字原文，不替代 `VISION-ORIGINAL.md`；用词或方向如有偏离，以用户后续澄清为准并修订本章。

### 2.1 我们真正想消灭的是什么

AI 已经能凭一句话做出一次性产品，也能在陌生仓库里迅速生成看似可用的代码。但一次性生成不等于高质量开发：它会只看到局部、重复已有能力、把项目越改越大，最后继续制造人工作业时代就存在的屎山。

我们要的不是更强的“一次性许愿生成器”，而是让 AI 具备持续开发已有软件的能力：**理解原有结构、找到正确接入点、在设计层重排、逐步改造、证明改造后的实现符合设计。**

面对屎山，目标不是默认推倒重写，也不是只修一个报错；是把它逐渐梳理成简单、紧凑、职责清楚、没有重复权威、能够继续演化的项目。

### 2.2 项目要成为什么样的底座

它应成为 AI 时代的外置开发机甲：用户表达意图，模型作必要的语义判断，框架承担一切能够确定完成的计算、定位、补全、关联、迁移与对账。

它可以面向不同语言、不同项目、不同功能；重构、新增、退役、翻译和观测都可以纳入。**但“大而全”意味着同一个底座能承接更多操作，不意味着每个方向再造一套平行工具与数据体系。**

### 2.3 一次开发的正确循环

```text
源码与已有材料
→ 框架建立实际 DB 与实际项目地图
→ 模型问“有什么功能 / 要改的功能在哪里”
→ 框架给出相关功能、结构、依赖、行为证据与已知边界
→ 模型先修改设计，而不是直接猜着写源码
→ 设计检查职责、依赖、逻辑、冲突与第二处权威
→ 框架把设计变化展开到文件、符号与工作顺序
→ 确定性部分由框架执行，语义实现由模型完成
→ 重建实际 DB
→ 实际侧与设计侧对账，确认哪些已落实、哪些没有、哪些判不了
→ 核销本次变更，并把无争议的新事实自动回填到设计底色
```

这个循环既用于旧项目改造，也用于新增功能和跨语言翻译。新项目可以从空项目出发，不要求先手工写完整设计册。

### 2.4 模型与框架各自负责什么

模型负责：功能意图、职责分配、结构选择、语义实现和必须由人作出的方向裁决。

框架负责：从源码提取事实，保持事实新鲜，提供相关上下文，找出关联与影响，展开设计差异，自动补齐可确定的参数，执行机械变更，保存证据，重新对账。

**重写是否优雅不是机器假装可判的事；机器要做的是给模型足量且可定位的信息，让模型的选择能可靠地落实。**

### 2.5 设计侧为什么存在

DSL 不是为了让人额外维护一套文档，而是让模型有一个可以查看、修改、定位、验证的项目工作区。

设计侧由实际侧派生，包含完整的可读底色；模型只修改需要改变的部分。它可以暂时与实际不同，因为目标本来就尚未实现。落地后框架自动维护事实细节，不能把持续手维护 DSL 的成本转嫁给人。

### 2.6 什么意味着做对了

不是工具多、字段满、判据多或所有灯绿，而是：

- 模型能找到一个陌生项目真正的功能改动面；
- 修改前能知道哪些东西必须保留、哪些关联必须跟上；
- 不再重复实现已有能力；
- 设计能转成有归属、有顺序、可验证的工作；
- 修改后能逐项确认已做、未做和不可判；
- 项目每轮变得更清楚，而不是更依赖救火；
- 框架自身的问题也能被同一套机制发现。

用户保留愿景与轴心设计权；实现者不得用当前实现的困难或偏好悄悄替换这个方向。

## 3. 用户、场景与价值判据

### 3.1 目标使用者

让 AI 继续开发一个已有软件的人，尤其是：项目陌生、历史结构混乱、修改牵涉多个模块、不能直接推倒重来的场景。

同样服务新项目，但新项目从空实际侧起步，不制造“先建一套文档才能开发”的门槛。“任意项目/语言”是终态方向，不是当前能力承诺。

### 3.2 价值只能由任务结果证明

每个重大版本至少用一个真实改造任务回答：

- 模型是否比直接搜索更快找到正确改动面？
- 是否发现了原工作流会漏掉的关联或副作用？
- 是否完成了原来不敢做、只能推倒重做的改造？
- 设计侧自动维护后，用户实际需要持续手维护多少内容？
- 失败后能否定位是设计、事实、执行还是对账的问题？

这些问题是产品取舍依据；它们不是“结构一致所以有价值”的替代品。

## 总体架构：一个项目模型，一条改造闭环

```text
                     ┌──── 语言 / 平台 / 运行适配器 ────┐
                     │                                  │
源码、配置、文档、测试、运行事件
        │
        ▼
[事实核 Actual Facts]  ←──── 唯一代码事实来源
        │ 可重算投影
        ▼
[项目地图：文件 / 符号 / 关系 / 功能视图]
        │
        ▼
[设计侧 Intent + Overlay + Target]
        │ 编译为差异和依赖有序的工作项
        ▼
[变更计划 Change Plan]
        │ 机械操作 / 模型实现 / 人裁决
        ▼
[源码与外部产物]
        │ 重建事实
        └────────► [对账 Reconcile] ──► 继续 / 核销 / 明确未决
```

**全语言、全功能扩展发生在适配器与操作集，不在每条线上重建事实核、设计核和任务体系。**

### 三类数据必须分账

| 类别 | 例子 | 权威 | 生命周期 |
|---|---|---|---|
| 事实 | 实际签名、引用、调用、类型成员 | 源码及其解析/语义索引 | 可重建 |
| 意图 | 目标结构、禁止边界、行为期望、理由 | 设计侧 | 人/模型显式修改 |
| 事件与历史 | 某次写入、某次观测、某次裁决 | 只追加或版本化记录 | 不按当前事实覆盖 |

派生视图可以有多个，不能各自成为可写事实。历史不是当前状态，不能通过改写历史来让当前检查变绿。

## 4. 事实核：实际侧

### 4.1 必备事实域

按需采集，不为填满表而采集：

1. **身份**：项目、路径、稳定符号标识、语言、来源版本。
2. **结构**：文件、符号、导出、类型、字段、成员。
3. **关系**：import、引用、调用、类型引用、实现/继承。
4. **行为材料**：函数体来源位置、输入输出、已有测试、可执行夹具。
5. **外部效果**：文件/环境/网络/进程/资源/事件，标明静态候选或运行实测。
6. **事实出处与完整性**：来源解析器、扫描版本、语言档位、未解析和截断面。

### 4.2 语法与语义是两层，不相互冒充

- 语法层：tree-sitter 等，项目不能编译时仍可用。
- 语义层：TypeScript Checker、go/types 等，提供绑定、类型、接收者和字段选择。
- 运行层：测试、trace、effect 事件，提供静态看不到的证据。

能力声明至少区分 `syntax-only / semantic / runtime-observed`。没有语义证据时返回“不足”，不能把静态候选写成实测。

### 4.3 语言扩张合同

新增语言不是注册一个语言名。必须按能力逐格声明：

```text
可解析 → 可索引符号 → 可解引用 → 可解调用 → 可编辑 → 可构建/测试 → 可观测
```

某格做不到就明确不做。所有下游按语言能力降级，不在工具内手写语言名单。

新项目/低能力语言的最小路径是：先登记项目与可识别的文件事实；能建立符号才允许符号定位，能解引用才允许自动关联改写。仅有 syntax-only 时，工作项交给模型或人完成语义设计与文本实现，验收靠该项目已有的构建/测试；没有可用执行环境时只能标未验证。禁止宣称已自动找到全部影响面，也禁止因缺少设计字段而要求先填满 DSL。

### 4.4 新鲜度是读取前提，不是最后告警

读事实时必须知道：

```text
索引对应哪个源码版本；
本次哪些文件实际刷新；
哪些不在保鲜范围；
哪些失败、未解析或被截断。
```

索引陈旧时，依赖该事实的判据为不可判定；它既不证明设计失败，也不证明设计通过。

传播链必须落在现有路径：`index_integrity/fileFacts/indexStaleFor` 提供覆盖与新鲜度 → `judgeExpectations` 对每个依赖该事实的 kind 返回 `unsupported`（缺前置条件的另用 `pending`）→ `cardStanding` 返回 `unknowable` → `complete` 拒绝核销。任何读取失败不能折叠成空事实；pending 也不能因不计入 fail/unsupported 而被判满足。

## 5. 项目地图与功能视图：模型理解项目的入口

文件树是存储视图，不是用户任务的自然入口。需要一等的功能视图：

```text
FeatureContext
  query / feature identity
  entry points
  related files + symbols
  dependency and call subgraph
  public contracts
  behavior evidence + tests
  known external effects
  active design decisions / change sets
  omissions and confidence limits
```

### 5.1 功能不是手写目录副本

功能映射以下来源组合：

- 显式功能标签（意图）；
- 路径/符号/文本检索；
- 调用和类型闭包；
- 测试与运行链；
- 现有设计边界。

结果必须给候选、依据和未覆盖面；语义检索不能把“最像”冒充“就是它”。

### 5.2 渐进披露

```text
功能一句话 → 功能子图 → 契约与关系 → 精确源码
```

默认输出与当前任务有关的上下文，并带全量分母与截断原因。模型可以主动下钻，框架不能宣称一次返回了整个项目语义。

## 6. 设计侧：全量可读底色，少量可追踪笔迹

采用已有讨论中的正解：**设计 DSL 是工作区，不只是 diff。**

```text
Design view = current actual projection
            + accepted intent
            + active target changes
            + exclusions / declared blind spots
```

读取要看到相关全貌；落盘和治理必须区分：

- 从事实派生的底色；
- 已接受的设计意图；
- 本次尚未实现的目标变化。

### 6.1 设计不是源码镜像

设计可以要求当前不存在的文件、符号、边或行为。核销前这些差异是工作，不是“设计错了”。

反之，实际侧存在而设计侧没有，可能是：

- 尚未纳入设计；
- 有意不收录的槽位；
- 该退役的现状；
- 事实扫描新增。

必须给出处置类别，不能全叫漂移。

### 6.2 意图最小字段原则

字段只有能支撑检索、目标表达、执行定位或验收才存在。

推荐最小单位：

```text
stable identity + path
responsibility（按需、人写）
contract constraints（按需）
behavior expectations（按需）
dependency rules（按需）
effect constraints（按需）
decision rationale + non-goals（需要裁决时）
```

实际 API、实际 import、行数、调用次数等事实不写成第二份可编辑意图。

### 6.3 `contract` 是组合视图，不是平行宇宙

公共 API、数据形状、依赖、外部效果各自有唯一住处。`contract` 如需存在，只是这些约束的组合投影。

- `expected_apis` 保存被要求保持的公共契约，不是当前导出的复制。
- `expected_deps` 若等于实际 import，应退为事实投影；意图侧真正需要允许/禁止规则。
- `effects` 可以表达无副作用、允许写哪些目标、发哪些事件。
- 未声明与显式空集合不同：前者不派生判据，后者可派生否定约束。
- 一个展开器没有输入或消费者时，不能进入主链验收。

### 6.4 槽位必须声明

空值有两种：

```text
未设计：需要人/模型决定；
有意槽位：允许从落地后的事实回填。
```

每类字段声明属于“主干要求、可选意图、可回填槽位”哪一种。禁止用文件名或自动统计文案填满职责位。

## 7. 从设计到工作项：设计编译器

这是当前最需要加强的一层。

```text
Target design + actual snapshot
→ semantic diff
→ change set
→ ordered work items
```

### 7.1 ChangeSet 先是现有对象的组合视图，不是新存储

**不要先建 ChangeSet 表、类型家族或新工具。** 先给现有对象做映射，并在一个真实任务里验证它足够：

| 变化集需要的内容 | 现有承载 |
|---|---|
| 目标、理由与验收 | `decision` / `expectations` |
| 执行责任与归属 | task/card |
| 文件与符号级工作项 | `RewritePlan.entries[]` |
| 目标文件、改动类型与细节 | `RewritePlan.path`、entry.kind/detail |
| 验收引用与先后依赖 | entry.judgement_ref / depends_on |
| 同任务跨文件工作面 | card 名下全部 RewritePlan 的坍缩集 |
| 实际事实基线与施工证据 | plan 冻结指纹、实际索引、判据执行结果 |

这个组合视图称为 **ChangeSet**；它只回答“这次要改什么、如何验、做到哪里”。它由现有对象现组装，不能成为第二份目标副本。

首个试点只允许补实测缺口，例如“尚未裁决的问题在哪里”“某项由谁执行”。**每新增一个字段必须指出现有对象为什么表达不了，以及哪个消费者会读它。**

目标差异的家是当前设计侧的 decision/expectations 与由其生成的 RewritePlan；`design_line action=plan` 是已有写入入口。diff 和核销按稳定条目 id/引用读取它们。design DB 仍是可重算投影，不能靠从 cache.db 填满事实来冒充目标。

不要求所有设计都先编译成机器实现。模型实现和人裁决是合法执行方式；框架必须让剩余判断显式存在。

### 7.2 画布是 ChangeSet 的工作视图

现有 RewritePlan 可继续承载单文件计划，但必须能：

- 关联同一变更跨文件的所有计划；
- 表示有序依赖；
- 记录冻结时的符号和事实版本；
- 检测计划外改动；
- 被后续变更显式取代；
- 核销后退出活动范围而保留历史。

不要让同一变更在设计卡、任务卡、画布和 diff 工具里各写一份目标。它们共享 ChangeSet 引用。

### 7.3 每次变更都必须有停止条件

至少以下之一不成立时，不能核销：

- 要求的行为或结构尚未实现；
- 有明确反例失败；
- 存在未裁定的开放决定；
- 所需事实不可信；
- 有本次计划外改动未解释。

“无法验证”可以保留改动，但不能标记完成。

核销的唯一编排应是现有 `complete` 路径，输入必须齐：`checkRewriteExit` 的结构与计划外改动、每个 `judgement_ref` 的真实判定、当前事实可信性、未决决定清单。任一输入缺失或含 fail/unsupported/pending/未解释计划外改动，结论为不可核销。`plan_exit_check` 本身不核行为，绝不能单独被当作完成证明。

## 8. 执行：渐进式重写与新增功能

### 8.1 机械执行器

已有且应继续复用的能力：

- 符号级读取与编辑；
- 模块级/局部改名；
- 文件移动和 import 改写；
- 跨文件符号移动；
- 影响面与引用查找；
- 可预览、可回滚的批量变更；
- 写后索引保鲜。

这些不是目的，而是 ChangeSet 的机械执行零件。

### 8.2 模型实现

模型接收的是带上下文的工作项，不是空白编辑器：

```text
目标 + 相关功能子图 + 当前原文 + 关联契约 + 已有测试 + 禁止条件
```

它决定语义实现，框架负责定位、事实供给、写入、回滚和再对账。

### 8.3 失败与回滚

区分：

```text
未改、已改未验、验证失败已回滚、回滚失败、已改且指定验收通过
```

“没做”“没跑”“不支持”不能使用与成功相同的返回形状。任何降级都必须改变结果类型或状态，而不是只写一条日志。

外部直写无法被进程内写闸完全控制，这是明确边界；不要把工具面拦截说成“不可能绕过”。

## 9. 对账与验证：证明做到了设计，而非证明设计最好

### 9.1 四层证据

| 层 | 回答 | 不能证明 |
|---|---|---|
| 结构 | 该存在的文件、符号、边是否存在 | 实现语义正确 |
| 契约 | 签名、类型、依赖、效果是否满足约束 | 所有调用场景正确 |
| 行为 | 给定输入是否有独立预期输出 | 未覆盖行为正确 |
| 运行 | 真实执行是否满足观测约束 | 未运行路径正确 |

### 9.2 证据、施工与替代关系分轴，不另造混合状态

- **证据判定**复用现有 `pass / fail / unsupported / pending`。
- **施工状态**复用 plan entry 的 open/stale/done；写入结果另行区分未变化、未验证与已回滚。
- **后续替代**用显式的取代引用表达，不复活一套同名状态。

`unsupported/pending` 不算违反，也不算通过；它们阻止核销并给出补证据的动作。

### 9.3 核销与回填是两个动作

1. **核销**：本次 ChangeSet 的结构与行为要求均有证据，计划外变化已解释。
2. **回填**：把实现后无争议的事实细节更新到设计底色，不覆盖意图与理由。

不要求两册所有字节永久相同；要求当前认可的设计与事实可解释地一致。

### 9.4 判据、测试、门的边界

- 判据：生产产物应满足的独立约束。
- 测试：受控输入下，执行器是否产出独立预期结果。
- 门：这次检查是否针对正确对象、完整运行并正确阻断。

当前工具数量、字段覆盖率、总判据数属于现态读数，不能写成永久能力验收。

## 10. 翻译侧：同一改造闭环的跨语言形态

```text
源语言事实核
→ 源功能与行为上下文
→ 目标设计（语言习惯、结构、依赖与兼容约束）
→ 目标 ChangeSet / 翻译工作项
→ 机械翻译 + 模型语义处理
→ 目标事实核
→ 结构/行为对账
```

翻译不是只生成同形骨架，也不是源语言 AST 的另一次独立抽取。

### 10.1 必须保留的现有正确原则

- 已知事实、未知假设、验证结果分开。
- 只有同一输入下源/目标行为一致才构成等价证据。
- 编译通过不是完成。
- 无类型/无库/无语义槽时显式保留未知，不猜成 any 或空实现。

### 10.2 中立轴心的使用条件

概念、类型、语义槽与目标映射可以共享，减少 M×N 的维护。

但单语言对的体 IR 与双渲染器已实测未产生质量收益，因此：**先有至少三种语言或明确跨语言复用需求，再扩大体 IR 覆盖面。** 翻译质量优先补事实提取、术语决策、依赖策略和行为对拍。

## 11. 运行时观测与生态扩张

观测回答静态事实看不到的事：真实调用、效果、时序、重试、资源占用。

它是按需事实适配器：

```text
某个判据或设计问题需要运行证据
→ 选择少量观测点
→ 执行真实场景
→ 事件进入事实证据
→ 对账或修改设计
```

没有判据/设计消费者的插桩、事件、提案队列不进入主链。

未来可纳入数据库、API、部署、配置和跨仓库关系，但必须：

1. 新增事实能回答一类原来看不见的问题；
2. 使用同一身份、事实出处、能力和对账协议；
3. 有至少一个真实改造任务消费；
4. 不另建一套任务和验证体系。

## 12. 工具与界面：能力多，公共概念少

### 12.1 公共入口按任务组织

目标是少量稳定入口，内部能力可很多：

```text
project：建立/刷新项目事实
explore：按功能、符号、关系理解项目
design：读取/修改意图与目标
change：形成计划、预览、执行、回滚
verify：行为/结构/运行对账与核销
```

现有工具可以通过适配层渐进收编，不需要一次性破坏性删除。MCP、CLI 和未来显示端必须调用同一应用层用例。

### 12.2 工具进入正式面的条件

- 它有唯一操作对象；
- 有真实主链消费者；
- 与已有工具的输出能直接交接；
- 有正例、反例与失败语义；
- 它减少模型寻找上下文、表达设计、定位改动或确认落地的成本。

不满足者留在内部库、实验目录或退役，不注册成主路。

### 12.3 任务与画布是辅助机制，不是产品目标

只有权限、责任或可追溯事件发生变化时才需要持久状态。工作步骤不自动等于新状态。

用户设计裁决不可被框架代替；模型执行失败不应自动替用户改目标。缺少信息时给具体缺口和下一步，不制造需要还原的假领取状态。

## 13. 自我监督与可靠性

框架必须能检查自身，但每个机制都要有成本边界。

### 13.1 必须长期守住的系统不变量

1. 同一事实只有一个可写权威。
2. 事实不被当成意图，意图不从当前实现复制后冒充期望。
3. 事实不可信时不输出确定结论。
4. 未验证、未执行、无变化不能报成已完成。
5. 失败必须可定位，不能只记日志后照常成功。
6. 每次写入可关联目标与回滚依据。
7. 读取/写入项目根不静默改变归属。
8. 删除旧能力时同时迁移它的消费者、守卫与文档。

### 13.2 检测点必须能证明会红

每道防线至少回答：

```text
它守什么；
造什么坏输入它必红；
它没覆盖什么；
失败后谁负责什么动作。
```

删除测试对象后检查自动变绿，不是修复。对“覆盖率、总数、灯变绿”都必须问检查范围是否缩小。

### 13.3 不要为每个故障再建一个体系

优先把故障加入现有不变量、行为测试和统一门。若需要新增台账、状态、报告和独立 runner 才能处理一个小问题，先证明现有承载点为什么接不住。

## 14. 扩张与退役算法

### 14.1 新能力进入主干前

必须填完：

```text
用户场景：
属于理解 / 设计 / 执行 / 对账哪一步：
输入来自哪个权威：
产物被哪个下游消费：
做不到时返回什么：
最小反例：
复用了哪些现有能力：
替代或退役了什么：
```

没有下游消费者、输入永远为空、只生成自己才读的产物，均不进入主干。

### 14.2 同生态位合并

先找权威和全部消费者，建立等价基线，再保留一个入口和可复用执行核。不能只删工具名而丢掉唯一行为验证。

### 14.3 退役必须记代价

删除记录包含：判据、替代路径、丢失能力、历史兼容方式、回炉条件。

区分“需求消失”“实现错误”“重复发明”“死代码”；不要把翻译等未完成方向写成永久错误。

## 15. 实施顺序：先闭合一个真实任务，再横向扩张

### 阶段 A：复用现有对象，修可信边界

1. 产出 decision / task / RewritePlan 的组合映射，确认 ChangeSet 只是现组装视图；缺哪一格须由试点证明，不新建平行表。
2. 标出事实、意图、事件和派生字段；design DB 不复制目标差异。
3. 验证“事实范围与新鲜度 → 具体 judgement 为 unsupported/pending → cardStanding 不可核销”的传播；反例必须含只有 pending 后态的卡。
4. 盘点主链/内部零件/实验/退役，不以工具数量为目标。

**出口**：一个现有卡的计划能被读取为完整 ChangeSet；陈旧事实与 pending 反例均不能 complete；仍缺的能力具名列出。

### 阶段 B：用现有工具完成一个受控试点

试点选一个小型 TypeScript 纯函数，目标行为改变同时保持公共签名不变。可使用 `tests/fixtures/` 的独立夹具或专门临时项目，不能直接拿本仓生产模块冒险。

按当前实际入口执行，不等新门面：

```text
import_project({project_dir, feature})
→ get_dsl query=locate {text:'<功能名>'} / explore_code read 读完整函数与消费方
→ edit_dsl 修改 decision，增加 behavior-cases 的独立输入输出与反例
→ design_line action=plan {card, file, entries:[{anchor:{symbol},kind:'rewrite',detail,judgement_ref}],apply:true}
→ edit_dsl claim / 必要时 start（以当时状态机为准）
→ edit_code op=replace 修改该函数
→ design_line action=judge 真跑引用判据
→ design_line action=plan sync_status:true，核销检查后再 complete
```

产物是夹具项目内的实际索引、设计册、任务库中的画布与判据结果。每次调用的具体字段以当时 `ToolDef.description` 为准。

- **通过例**：源码的新行为等于事先写下的独立期望，计划外改动已解释，才允许核销。
- **不得核销例**：只改一个无关注释或保持旧行为；结构变了但 behavior-case 仍红；索引陈旧或判据 pending。三者不能因文件发生变化而完成。

记录模型仍需猜什么、手工搬什么、哪些上下文没找到。它们决定下一轮，不以字段覆盖率代替。

**出口**：同一夹具输入重复执行能重现通过与不核销两条结论，并列出与通用真实功能闭环之间的剩余差距。

### 阶段 C：让自动维护取代手工喂养

1. 只读视图自动合并事实底色与意图笔迹。
2. 只回填已声明的可回填槽位。
3. 自动维护功能关联与工作项状态。
4. 合并同对象重复入口，保留行为证据。

**出口**：没有本次变更时，用户不需要为维持 DSL 而做手工同步。

### 阶段 D：按任务需要扩语言和操作

优先补当前真实项目需要的绑定、接收者、字段、行为和效果事实。翻译继续使用同一事实/设计/对账协议，不独立铺第三套主链。

**出口**：新语言/操作增加的是适配器或执行器，不是另一套项目模型。

## 17. 核心数据结构与 DSL 边界

### 17.1 DSL 到底是什么

DSL 通常指 **Domain-Specific Language（领域特定语言）**。本项目里它主要不是一套需要执行的语言，而是用 JSON 表示项目结构、意图和变化的**结构化数据模型与交换协议**。

**结论：采用 DSL 是合理的；让一份 DSL 承担所有职责是不合理的。** 它适合机器读写、跨工具传递、版本化与人机共同查看；不适合成为另一个可手改的事实数据库，或把 UI 布局、运行日志、工具说明和任务状态都塞进去。

约束不是“必须叫 DSL”，而是：有稳定 schema、身份、引用和读写语义；缺少这些，就只是大 JSON。

### 17.2 先定逻辑形状，不先建表

以下是给实现者的**逻辑契约与现有对象映射**。它们不是要求新增六套存储；优先由当前 `cache.db / design DSL / tasks.db#plans` 投影。

#### A. 项目与身份

```ts
type ProjectRef = {
  projectRoot: string;       // 本次进程解析到的绝对根
  feature: string;           // 现有项目分册标识
};

type FileRef = { path: string }; // 仓库相对 posix path
type SymbolRef = FileRef & {
  name: string;
  kind?: string;              // function/class/interface/...
  parent?: string;            // 方法等所属符号
};
```

- 身份决定“在改谁”，路径/符号不能靠 label 猜。
- 路径/名字可从事实取；移动后的身份继承由 lifecycle/变更事件记录，不在每个视图复制。
- 多册归属和冲突沿用现有归属检查，不把同一对象复制成两张可写卡。

#### B. 事实单元与证据边界

```ts
type FactBasis = {
  source: 'ast' | 'semantic' | 'runtime' | 'build-test';
  sourceRevision: string;
  coverage: string[];
  limitations: string[];
};

type Fact<T> = {
  value: T;
  basis: FactBasis;
};
```

- 这是**读写响应的逻辑包裹**，不要求每个数据库列都变成嵌套对象。
- 实际 file/symbol/signature/edge 由当前解析索引提供。
- 取不到、未覆盖、范围外、陈旧必须保留；不能把失败折成空数组。
- 函数体原文仍住源码，DSL 只保留定位与事实引用。

#### C. 功能上下文

```ts
type FeatureContext = {
  query: string;
  candidates: Array<{
    ref: FileRef | SymbolRef;
    why: string[];
  }>;
  files: FileRef[];
  symbols: SymbolRef[];
  relatedEdges: Array<{ from: string; to: string; kind: string }>;
  contractRefs: string[];
  evidenceRefs: string[];
  changeRefs: string[];
  omissions: string[];
};
```

- 候选不是确认归属，模型/人负责语义选定。
- 闭包和关系由实际事实派生；功能标签/归属是意图，只有它需要人工保存。
- 读取时组装，不生成第二套功能文件清单。

#### D. 设计意图与目标差异

```ts
type IntentRef = {
  nodeId: string;
  expectationIndexes?: number[];
};

type TargetChange = {
  subject: FileRef | SymbolRef;
  operation: 'create' | 'rewrite' | 'move' | 'delete' | 'retire';
  goal: string;
  verification: IntentRef[];
};
```

- 目标差异由现有 design decision/expectations 与 plan entry 组合表达。
- `goal` 是语义目标，不是实际源码的复制。
- 验收指向已有判据，不能在 plan 里另写一套判据正文。
- 公共契约、依赖、行为、效果约束留在各自唯一住处，contract 只是组合视图。

#### E. 工作项：复用 RewritePlan

```ts
type WorkItem = {
  ref: string; // 指向既有 plan entry
  subject: FileRef | SymbolRef;
  kind: 'rewrite' | 'create' | 'delete';
  detail: string;
  judgementRef: string;
  dependsOn: string[];
  executor?: 'mechanical' | 'model' | 'human-decision';
};
```

对应现有 `RewritePlanEntry.anchor/kind/detail/judgement_ref/depends_on`。

- `executor` 暂为规划时的派生或待补元数据，只有执行调度器真消费它才允许入存储。
- 多文件工作面 = 同卡所有 plan 的现有坍缩集，不复制一份文件列表。
- 冻结时的内容/符号指纹是实际事实证据，不是目标设计。

#### F. 结果：三轴，不造总状态

```ts
type EvidenceVerdict = 'pass' | 'fail' | 'unsupported' | 'pending';
type WorkState = 'open' | 'stale' | 'done';
type WriteOutcome =
  | { kind: 'no-change' }
  | { kind: 'changed-unverified' }
  | { kind: 'changed-verified'; evidence: EvidenceVerdict & object }
  | { kind: 'reverted' }
  | { kind: 'rollback-failed'; detail: string };
```

上面展示结果分类，不是建议原样替换所有现有返回类型。

- 核销只读取证据与施工事实，不能把二者混成 `success:true`。
- 任务被后续替代用显式替代引用，不作为证据 verdict。
- 完成需要：所有关联 judgement 均 pass、无未决/不支持/等待项、结构出口通过、计划外改动已解释。

### 17.3 必须保持的存储分账

| 数据 | 现有权威/优先载体 | 不得另存为 |
|---|---|---|
| 实际文件、符号、签名、关系 | 源码 + 项目实际索引 | 可编辑设计事实副本 |
| 设计理由、目标、判据 | 设计侧 decision/expectations | 工具描述/计划正文副本 |
| 施工工作项与冻结证据 | 现有 RewritePlan/tasks.db | 新 ChangeSet 表 |
| 当前责任与执行事件 | 任务系统 | DSL 字段填充率 |
| 历史裁决与运行事件 | 历史/观测记录 | 当前事实字段 |
| 功能上下文、地图、摘要 | 按需投影 | 第二套手工清单 |

### 17.4 给开发窗口的实施指令

不要一次性实现本章类型。先在阶段 B 的试点中写一张“所需信息 → 当前对象/字段 → 当前读入口”的对照；只有某一项没有权威且被真实消费者需要，才扩现有 schema。

优先补的是：功能上下文组装、设计差异到 plan 的交接、核销证据聚合。不要先改全部数据库结构，也不要把“数据结构设计完成”当作产品闭环。

## 18. 给下一位开发模型的操作卡

开始前：

1. 读 `VISION-ORIGINAL.md`，不要把本文当用户原话。
2. 读 `INDEX.md` 和 `RETIRED.md`，核实现状和已有退役理由。
3. 用项目自己的 `capability_map` / `index_integrity` 确认工具与索引当前可用性。
4. 选一个真实功能任务，不从“新增一个字段/工具/状态”开始。
5. 先查现有权威和消费者，再决定改哪里。

工作时：

```text
取得功能上下文
→ 明确目标与不变的部分
→ 写独立验收和反例
→ 形成工作项与依赖
→ 选机械/模型/人裁决执行者
→ 预览并执行最小一批
→ 重建事实并对账
```

交付时：

- 哪些意图已核销，证据是什么；
- 哪些没有验证、没有执行或不可判；
- 哪些现有能力被复用或删除；
- 用户需要持续手维护的东西是否减少；
- 下一项真实任务是什么。

**若一项工作没有推进理解、设计、执行、对账之一，不要把它注册成主链能力。**

## 最后一句

**大而全的实现方式，不是让所有工具都成为一条新产线；而是让任何项目、任何语言和任何改造操作，都能进入同一个“事实 → 意图 → 变化 → 执行 → 对账”的循环。**

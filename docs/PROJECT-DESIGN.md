# PROJECT-DESIGN.md — 目标设计

> 这是目标设计，不是现状说明。现状见 `INDEX.md`；用户原话见 `VISION-ORIGINAL.md`。

## 1. 产品定义

AgentIO 让 AI 具备持续开发已有软件的工作方式：

```text
不靠局部 grep 猜项目
→ 先取得与功能有关的可信上下文
→ 在设计上表达目标与变化
→ 把变化定位到文件、符号、依赖和行为
→ 逐步执行机械改写，保留语义决策
→ 重建实际事实并与设计对账
```

产品只承诺四件事：**理解、设计、改造、对账**。不保证所有语言同精度，不保证编译通过就是行为等价，不保证结构与设计一致就是设计优秀，不用工具数/判据数证明成功。

## 2. 一条主链，不造第二套

```text
源码/配置/文档/运行事件
        ↓
事实核（唯一代码事实来源）
        ↓
项目地图（文件/符号/关系/功能视图）
        ↓
设计侧（意图 + 接受的目标变化）
        ↓
工作项（由现有 decision / expectations / plan / task 组合）
        ↓
施工（机械操作 / 模型实现 / 人裁决）
        ↓
重建事实 → 对账 → 继续 / 核销 / 明确未决
```

新增语言、操作、运行观测都走适配器与能力声明，不重建事实核、设计核和任务体系。

AgentIO 的通用层面向不同 Agent 宿主提供同一套理解—设计—改造—对账能力。DSH 只是未来的一种宿主适配器；通用能力未被独立宿主和真实项目验证前，不把 DSH 专属插件、远端会话控制或宿主审批体系并入产品主干。

## 3. 事实、意图、事件分账

| 类别 | 权威 | 规则 |
|---|---|---|
| 事实 | 源码及解析/语义/运行证据 | 可重建；不把静态候选当实测 |
| 意图 | 设计侧 decision / expectations | 人/模型显式修改 |
| 事件与历史 | ledger / task_history / git | 只追加或版本化；不因当前检查变绿而改写 |
| 派生视图 | docs、capability_map、gen-db | 从权威现算；不是可写事实 |

## 4. 行为契约编译器

目标：模型和人只表达"什么输入应当产生什么行为"，框架把它变成可执行、可定位、可核销的测试。

逻辑输入：

```ts
type BehaviorContract = {
  id: string;
  subject: { file: string; symbol: string };
  intent: string;
  cases: Array<{ given: unknown[]; expect: unknown }>;
  source: 'design' | 'existing-test' | 'approved-baseline' | 'translation';
  setupRefs: string[];
};
```

流水线：

```text
契约提取 → 主体定位 → 读取语言能力 → 生成调用计划 → 最小夹具
→ 编译到现有 behavior-cases 执行核 → 真跑 → verdict + 证据
→ plan / complete 只引用实际 verdict
```

每一步可失败：主体不存在、导出不可达、参数无法构造、夹具不完整、运行器未执行，都返回 unsupported/pending 并点名缺口，不能从分母剔除。只有当前实现而没有独立预期时，结果只能是"已运行/与基线相同"，不能判行为正确。

## 5. 阶段出口

### 阶段 A — 目标链与可信边界

- 一个现有卡的计划能读作完整工作项。
- 陈旧事实与 pending 反例不能 complete。
- 仍缺能力具名列出。

### 阶段 B — 受控试点

- 在小型 TypeScript 纯函数上跑通：定位 → 改设计 → plan → 领卡 → edit_code → judge → complete。
- 同一夹具输入能重现"通过"和"不核销"两条结论。
- 不改生产模块冒险。

### 阶段 C — 自动维护取代手工喂养

- 只读视图自动合并事实底色与意图笔迹。
- 只回填已声明槽位。
- 功能关联与工作项状态自动维护。
- 行为契约编译器接工具面并真跑；不冒充核销。
- 合并同对象重复入口，保留行为证据。

出口：没有本次变更时，用户不需要为维持 DSL 而手工同步。

### 阶段 D — 按任务扩语言与操作

- 优先补真实项目需要的绑定、接收者、字段、行为和效果事实。
- 新语言/操作增加的是适配器或执行器，不是另一套项目模型。

## 6. 翻译与轴心约束

- 翻译必须保留未知，不把无类型/无库猜成 any 或空实现。
- 同一输入下源/目标行为一致才构成等价证据；编译通过不是完成。
- 中立名词/概念层有价值：把术语从 M×N 降到 M+N。
- 单语言对下，体 IR 与双渲染器未证明质量收益；在至少三种语言或明确跨语言复用需求前，不扩大体 IR 覆盖面，把投入放在事实提取、术语决策、依赖策略与行为对拍。

## 7. 扩张判据

新能力进入主干前必须回答：

```text
用户场景是什么？
属于理解/设计/改造/对账哪一步？
输入来自哪个权威？
产物被谁消费？
做不到时返回什么？
最小反例是什么？
复用了哪些现有能力？
替代或退役了什么？
```

没有下游消费者、输入永远为空、只生成自己读的产物，不进主干。

## 8. 核销与停止条件

至少以下之一成立，不能核销：

- 要求的行为或结构尚未实现；
- 有明确反例失败；
- 存在未裁定的开放决定；
- 所需事实不可信；
- 有本次计划外改动未解释。

`complete` 只读实际执行 verdict，不把"文件变了"当完成；无法验证可以保留改动，但不能标记完成。

## 9. 每次开发四问

```text
我们现在在执行哪个上层目标？
当前设计要改变什么？
这次源码改动属于哪个工作项？
凭什么说它已完成？
```

任一句答不出，先补目标链或证据，不继续扩写实现。

# 预案：任务系统做进设计 DSL（v2，2026-10-16）

> **v2 = v1 + 独立评审（一份）的修正。** 每条修正都注明"谁挑的、什么情况下坏掉"。
> ★ 体例照 `docs/discussion-log.md`：**微缩在前，展开在后**。

## 微缩（10 秒可读）

**任务 = 设计侧的对象**（住 `design/<f>.dsl.json` 的节点上，**不挂 overlay**）。
**五态**：`候选 → 已领 → 已完成`，另有 **`失效`**（target 没了）与 **`被取代`**。
★ **"领取时校验" = 对着 DB 判 `expectations`**（复用现成 `judgeExpectations`）；
★★ **但判"已满足"时必须剔除「前态判据」**（如 `edge-absent` / `call-exists` —— 它们在**未施工时天然成立**），
否则**任务还没领就被误收口** —— ★ **这是 v1 的真 bug（评审挑出）**。
★ **只落"意图与事件"**，**不落任何读数快照、不落校验结果**（读数永远现算）。

## 一、形状（v2）

```
design/<f>.dsl.json
  geometry.nodes[].task {
      id,                       ← 任务 id（= node_id）
      summary,                  ← 要做什么（人读一句）
      expectations[],           ← 判据（六类，对着 DB 判）
      state,                    ← ★ 候选 / 已领 / 已完成 / 失效 / 被取代
      owner, claimed_at,        ← ★ 谁领的 + 何时（今天"根本没有"）
      release_reason,           ← 释放/失效原因（可选）
      replaces,                 ← ★ 取代了哪张卡（评审补）
      evidence[],               ← ★ 只落 {kind, at, by, verdict} —— ★ 不落读数（见 §三）
      discussion {              ← ★ 讨论登记格（用户要求）
          micro,                ← 微缩（10 秒；★ 默认只渲染这一行）
          user_quote,           ← 用户设想（逐字）
          conclusion,           ← 整理结果 + 出处
          open[],               ← 未定/待拍
          decided_at,           ← ★ 评审补：定下来的时间
          supersedes            ← ★ 评审补：推翻了哪一条讨论（版本链）
      }
  }
```

## 二、状态机（v2 · 五态）

```
候选 ──领取时校验──▶ 已领 ──施工+对拍全过──▶ 已完成
  │                    │
  ├─▶ 失效             └─▶ 候选（显式 release 或 TTL 超时回收）
  │   （target 在 DB 已不存在）
  └─▶ 被取代（新卡 replaces 旧 id）
```

| 迁移 | 触发 | 备注 |
|---|---|---|
| `候选 → 已领` | ★ **剔除「前态判据」后**期望未全过 **+ target 存在** + **原子写 `owner`**（读 `state==候选` 才写，CAS） | ★ CAS 是评审补的（否则并发领卡互相覆盖） |
| ★ `候选 → 失效` | **target 节点/文件在 DB 里已不存在**（期望不再可判） | ★★ **与"已满足"是两种不同结局**（v1 混为一谈） |
| `已领 → 候选` | 显式 release，**或 `now - claimed_at > TTL`**（lease 超时回收） | ★ 评审补：没有 TTL 就是死锁字段 |
| `候选/已领 → 已完成` | `judgeExpectations` 全过 **且** evidence 闸过（复用 `validateProgressEvidence`） | |
| `候选 → 被取代` | 新卡显式 `replaces: <old_id>` | |

## 三、铁律检查：会不会"复制事实"（评审逐条判）

- ✅ **`state` / `owner` / `claimed_at`**：是**事件与意图**，DB 算不出来 ⇒ **可落盘**，不违铁律；
- ❌ ★★ **`evidence[]` 不能复用 `progress_evidence` 原样**：它今天记的 **"checked=6 passed=3 failed=3" 是「对拍读数快照」⇒ 必陈旧**
  ⇒ ★ **只许落 {kind, at, by, verdict}，读数永远现算**；
- ❌ ★ **"领取时校验的结果"不许落盘** —— 它只是**闸的通过/拒绝信号**（明写禁止）。

## 四、`discussion` 格的展开条件（评审给的，机器可判）

★ **默认渲染：只出 `micro` 一行 + `open[]` 计数** ⇒ ★★ **这才是"不直接展示"的机制**（不是口头约定）。
**展开触发**：① **闸内领取该卡时**（领任务必须读原话校准意图）· ② `judgeExpectations` **判失败、需人工裁决时** · ③ 调用方显式 **`expand=discussion`**。
★ 评审指出：**`user_quote` 逐字进 `dsl.json` 会撑爆微缩层** ⇒ ★★ **必须有「字段级排除」机制**，否则"不直接展示"只是空话。

## 五、迁移顺序（★ 评审挑出 v1 没说清）

★ **不能先退 overlay** —— **`get_dsl query=pending` 今天直读 overlay**（台账 §①）⇒ 先退会**把读端打断**。
**正确顺序**：① **设计侧落地** → ② **读端切过去**（先读设计侧，**读不到再回退 overlay**）→ ③ **测回退**（设计侧删掉仍能读）→ ④ **才退 overlay**。
★ 并行期**双写 = 破坏"一处权威"** ⇒ ★ **必须加"双写哨兵"**（§六③）。

## 六、评审补的三条（都带判据）

1. ★★ **lease / TTL**：`claimed_at` 不配超时**就是死锁字段**。
   ★ **红**：`state=已领 且 now-claimed_at>TTL 且 无 release 事件` 的卡数 **> 0**；
2. ★★ **漂移巡检**：**live 每次重算后，对所有非 done 的卡跑一遍 `judgeExpectations`**。
   ★ **红**：`候选 且 期望（剔前态后）全过`（漏收口）或 `target 从 DB 消失`（应转失效）的卡数 **> 0**；
3. ★ **迁移期双写哨兵**：overlay 与设计侧同 `node_id` 卡并存。
   ★ **红**：两边同名卡数 **> 0 且任一边 `updated_at` 晚于另一边** ⇒ **权威不明**。

## 七、未定 / 待拍（★ 单列，免得被当成已定）

1. ★★ **"已满足"的卡**：**自动收口（标 done）还是只提示**？★ 用户尚未拍；
2. ★ **TTL 取值**；
3. ★ **`失效` 的卡**要不要留档；
4. ★ **`discussion` 的版本链**要不要可 diff。

## T1 说明：为什么删掉那道门（一笔要留痕的判断）

**它是什么**：`tests/tools/scan_bounds_gate.test.ts` —— 判「**会扫仓库的工具，回执里必须给出
统一形状的边界自证 `data.bounds`**」。为此它需要一份"谁会扫仓库"的清单 ⇒ 就是那 43 条。

**它买到了什么**：① 新增扫仓库类工具未登记 ⇒ 红；② 登记 `bounds:true` 但源码里没有 `bounds` 字样 ⇒ 红
（**静态**，头注自认"不验它在成功路径上、内容对不对"）；③ 23 条 `bounds:false` 存量 ⇒ **只打印提示，不失败**。
⇒ 实际效果 = 「**别再加第 24 个不带 bounds 的扫仓库工具**」。

**代价**：43 条 provider + 28 条工具，**手维护**。而我在台账里一度断言"这 43 条可由判据推导"
—— ★ **实测证伪**：机械信号（`readdirSync` / walker / glob）命中 **65** 条（多报 51%），
且**漏掉 13 条**；`storage.ts` / `handlers.ts` / `serve.ts` 有 `readdirSync` 但**不是**扫描提供者。
⇒ **这份清单在做判断，不是在抄。** 但正因为它在做判断，它就得一直有人喂。

**裁决**：收敛期工具数在**减**（面收敛 68→58），"新增扫仓库类工具"的频率 ≈ 0
⇒ 用 71 条手维护状态换一个"防未来新增"的门，**不划算**。
⇒ 删门 + 删表；**纪律改为写在 T1 这一行里**（给人看）。
★ 保留的是**能力**：`src/tools/scan_bounds.ts` 契约 + 已迁 5 个工具（`code_health` /
`rename_symbols` / `move_symbol` / `find_references` / `impact_analysis`）的 `bounds` 照常输出。

## 为什么这么定（背景，读一次就够）

**状态群** = 一份需要人喂、且**腐了没人知道**的东西（登记表 / 基线 / allowlist / frozen 计数）。
09-30 实测 `tests/fixtures/` 10 个文件，按更新机制分三类：

| 类 | 数量 | 是不是负担 |
|---|---|---|
| 自动重生成（`UPDATE_*=1` 一条命令） | 6 | 否。其中 **G1 对外契约 / G8 行为等价** 有**独立判据**，改基线**必须记账** ⇒ 是「**变化即红**」 |
| 空表（`frozen={0}`） | 1 | 否 |
| ★ **真手维护** | 2（删 T1 后 → **1**） | ★★ 是 |

★ 判"是不是自己验自己"，**不是问有没有 `UPDATE_*`**（那只是入口），而是问：
**这份基线的期望值，是不是从当前实现反推出来的？**
有独立判据 ⇒ 靠谱；纯棘轮存量 ⇒ 它冻结的是**当时的读数**，而读数**可能本来就是假账**
—— 09-30 那份 21 条就是活证（2 条是假的，若做成棘轮会被原样冻成"允许的存量"）。

## 9. 2026-10-15 用户修正四：「在 DSL 里加一块内置 todo」—— 我的判断（**方向对，但"加一块"要改成"加一格"**）

用户原话：*"那就在设计 DSL 里面再设计一块，或者说加一块它内置的 todo，这样的话我们目前的 todo 就是一个历史 todo，
那里面的 todo 就只留存活 todo。或者是说刚好相反，你觉得怎么样？"*

### 9.1 方向：**A（todo 的家搬到 DSL）成立；B（反过来）不成立**
**判据 = 家应该在有"判据能力"的那一侧**：
- md todo **没有任何判据能力**：今天量出 77 条里 **24 条给不出判据**；`[x]` 已勾 26 条与"真做完"之间**无判据**；
  且 **T236 的判据被它自己污染**（`grep -c 关键词 == 0`，而它把关键词写进了 todo.md）。
- DSL 侧有 `expectations`（**机器可判**，`geometry.ts` 的 `NodeDecision` 字段）+ `consistency_check` 对拍
  ⇒ **只有 DSL 侧能自动判"完成"**。
⇒ 所以 md todo 该降为**历史归档**（不删：它是证据），活 todo 住 DSL。

### 9.2 ★★ 但**"加一块"要改成"加一格"**
- **理由**：todo 与决策**不是两件事**，是同一件事的**两个状态轴** ——
  决策问"**是否仍生效**"（`status: active/superseded/draft`），任务问"**是否已做完**"。
- **加"一块"新的数据结构** = 又造一个与决策平行的体系 ⇒ **同一信息住两份**（正是用户否掉卡片方案的那条理由）。
- **改为**：在**既有决策卡上加一格"兑现状态"**（候选名 `delivery: 'pending' | 'done'`，或复用
  `expectations` 的判定结果）；★ 而 **todo 是一份投影**（`query decisions where delivery=pending`）——
  **视图不是住处**（与 §7"md 只是投影"完全一致，逻辑自洽）。

### 9.3 ★ 硬前提：**"完成"这一格现在不存在，且必须可判定**
- `status` 的枚举是 `active | superseded | draft` —— **里面没有"已完成"** ⇒ 这一格是**新增语义**。
- 而"完成"**不许靠人勾**：md 侧已经证明会腐（26 勾 vs 77 未勾，且"勾了"≠"做了"）。
- ⇒ 完成的判据**只许三档**：① `expectations` 全绿（**自动**）· ② 附一条**可复跑的读数**（半自动）·
  ③ 明确标 **"人工确认"**（诚实）。★ **不许第四种：默默勾上。**

### 9.4 我上一轮的卡口要**放宽**（但有未验完的一格）
- 上一轮说"工程待办挂不上设计节点 ⇒ 不进 DSL"。★ 这条**可能过严**，因为有一条**间接证据**：
  `retire-flow` 真跑过 `edit_dsl` 给**文件** `src/application/meta/llm/gateway.ts` 标 `deprecated`
  （`src/domain/chain_wiring.ts:449`）⇒ **决策至少能针对文件**。
- ⇒ 若文件可作为承载点，则"工程待办"也能住 DSL（挂它所属文件），**不必为放待办造节点**。
- ★★ **但这一格我没验完**（我跑的 `grep` 模式偏了，没查清 DSL 有没有"文件级节点"）⇒ **标 `[待核]`**，
  下一轮补验。**未验完的结论不许当依据用**（今天已经吃过三次这个亏）。

## 12. 2026-10-15 用户修正六：「唯一权威 + 投影（可写可回落）+ 状态互通 + 强制 LLM 登记」

`src/domain/overlay.ts` 头注释逐字：
> *"定位：真相 DSL（base）由代码扫描每次可再生，但设计意图（决策卡 / 决策历史 / 设计参数 / 标注 /
> user_node / 分镜 / 主题）不是扫描能重造的。**过去真相一刷新，设计 DSL 整体被 `finalizeDsl` 覆盖
> （`saveDSL` 直写），意图全丢。**"*
> *"本模块把设计意图抽成独立 overlay，通过「稳定锚点」增量对账，真相刷新时只替换 base，overlay 按锚点
> 保留 / 迁移 / 孤儿 / 标过期，**绝不整体覆盖**。与项目铁律同构：**真相单源 + 单向投影 + 对账（不改 DSL 只报偏差）**。"*

⇒ **"唯一权威 + 投影 + 不覆盖"这套**已在，且 `_migratedFrom` / `orphaned`（§11.2）就是它的实现细节。

### 12.2 ★★★ 但**"投影也能修改"这一半，与铁律"单向投影"直接冲突** —— 而且冲突的理由就在同一段注释里
- 铁律逐字：**"单向投影 + 对账（**不改 DSL 只报偏差**）"**；
- 而那段注释**第一句就是事故**：双向写 ⇒ *"**意图全丢**"* ⇒ 才立了 overlay。
⇒ ★★ **"投影可写"= 两个写入口 ⇒ 正是当年丢意图的成因**。所以**不能直接照做**。

### 12.3 折中（**行为上等价于你要的，结构上不破单源**）
> **投影可以有"写操作"，但写操作不许落在投影上** —— 它必须**翻译成对权威的一次调用**。
> 即：**投影是"入口"，不是"住处"**。
- 判据①：**投影侧的任何写，最终必须产生"一次权威写 + 一次对账"**（可观测：权威文件在变，投影文件不成为第二份真相）；
- 判据②：**权威不读投影**（依赖方向单向不破 —— 这条一破，就回到"两个写入口"）。
- ⇒ 于是用户要的"在投影上改 = 改了权威"，**在行为上成立**，而 `overlay` 那条铁律**不被违反**。

### 12.4 「状态互通」= §11 的收敛 + 一条硬判据
"在 A 交完任务，B 也知道" 的结构含义 = **只有一个住处**（§11 的 4 个正交轴）+ **改一处只动一处**（§11.4 判据③）。
★ 若"改一处动了多处"，互通就是**伪装出来的**（多处副本靠同步脚本维系 ⇒ 迟早分叉，正是 overlay 当年的事故形态）。

### 12.5 ★★ 「强制 LLM 登记 / 完成」：唯一能落地的地方是**闸**，不是提示词
- ★ **靠提示词要求"自己记得登记" = 又一条会腐的软约束** —— 今天刚证过：md 的 `[x]`（26 勾 vs 77 未勾、
  且"勾了"≠"做了"）就是这么腐的；
- ★★ 项目里**已有现成的闸**：`src/application/write_gate.ts`（且 `edit_code` / `apply_writes` /
  `remove_dead_imports` / `scaffold` / `index_integrity` 都在用它）
  ⇒ **把"未登记任务不许落盘"挂在 `write_gate` 上**，这是**唯一"结构上不可能绕过"**的位置。
- ⇒ 形状：**改源码 ⇒ 先要求该改动挂到一条任务上（否则拒绝落盘并给出"怎么登记"的一句话）**。
  ★ 这与"探针不许抛错但错误必须可见"是同一种设计：**不是不许做，而是不登记就别想悄悄做**。

## 13. 2026-10-15 用户修正七：**「如果我们是唯一权威，那为什么还会有六套状态？真的不需要重写吗？」**

用户原话：*"实际上也就是一个意思嘛，这个投影可写其实就是所有的投影的位置都给它提供一个唯一的写工具……
**提示他**去使用这个工具，但是**使用的还是同一个工具**。然后**如果我们是唯一权威的话，那为什么还会有六套这个状态呢？
真的不需要重写吗？**"*

### 13.1 第一点：**用户说得对 —— 我们说的是同一件事**
"所有投影位置都提供**同一个**唯一写工具的入口（提示去用它）" = 我 §12.3 的折中（**投影是入口不是住处**）。
★ 唯一差别只在**"提示"还是"拦"**：我建议**两者都要**（投影处给提示 + `write_gate` 上拦一道），
因为**纯提示是软约束**（今天已证会腐），而**提示的意义是让"怎么登记"随手可得**，不是靠自觉。

### 13.2 ★★★ 第二点：**"唯一权威"与"六套状态"确实矛盾 —— 因为那六套并非都是"权威"**
★★ **权威的判据不是"类型唯一"，而是"这份数据能不能再生"** —— 判据就写在 `overlay.ts` 头注释里：
*"真相 DSL（base）**由代码扫描每次可再生**，但**设计意图**……**不是扫描能重造的**"*。
⇒ 于是六套要**先分成两类**：
| 类 | 谁 | 该不该有存储 |
|---|---|---|
| **可再生的**（扫描/重算就有） | `Node.status` · `SemanticFile.status` · （大概率）`Chain.evidence` | ★ **不许有存储** ⇒ 只该是**投影函数** |
| **不可再生的**（意图/人·LLM 的判断） | `NodeDecision.status` · `OverlayGoal.status` · `data.lifecycle.retire_reason` | ★ **必须有，且只许一处** |

⇒ ★★★ **"六套"的真正成因**：**可再生的那几份没有全部退化成投影 —— 被存下来了**；
   而不可再生的那几份，**各自存了一处**（谁也不知道它们"本来是一件事"）。
⇒ 所以**"权威唯一"完全成立**（权威 = 不可再生侧），矛盾来自**可再生侧漏了存储**。

### 13.3 ★ 回答"真的不需要重写吗"：**需要，但重写的对象与方式分两种**（这是本节的结论）
1. **可再生的那些** ⇒ **不是迁移值，是"删掉存储、改成派生"**（每次由扫描/权威算出来）。
   ★ 若只把值搬过去，**等于又存了一份** ⇒ 六套变五套，病还在。
2. **不可再生的那些** ⇒ **合并到一个住处**，用现成范式迁移（`_migratedFrom` 留来源、映射不上标 `orphaned`，§11.2）。

### 13.4 判据（可判定，且能一行数出来）
- 对**每个**状态字段问一句：**"这个值能不能从代码/权威重算出来？"**
  - 能 ⇒ **写入点数必须为 0**（只读派生）。可数：`grep` 该字段的写入点。
  - 不能 ⇒ **写入点数必须为 1**（唯一住处）。同样可数。
- ★ 于是"六套"应变成：**≤3 个存储点（不可再生的那三件）+ N 个投影（可再生的那些）**，
  而**"改一处只动一处"（§11.4 判据③）自动成立**（因为不可再生的只剩一处、可再生的根本不存）。
- ⇒ **这条判据的妙处：它把"状态收归"从一个设计争论变成了一个可数的检查**（数写入点）。

## 14. 2026-10-15 实测：六个状态字段的**写入点**（口径先钉住再数）

  **写入点集中 ⇒ 投影；写入点分散 ⇒ 已经是存储（且是病）**。判据从"语义辩论"变成"数写入点"。

### 14.3 ★ 如实记的三处存疑（子代理主动列的反方论据与 `[可能漏]`，不许当结论用）

## 22. 2026-10-15 回答用户：**为什么一个进度字段会有七处写它？**

用户原话：*"话说为什么会有七处这个任务？这个任务按理来说，**任务状态不应该有那么多处**。这是我突然想到的。"*

### 22.1 答案：这七处**不是七个重复实现**，而是**五种"时机"各写一次**（有清单）
| 时机 | 谁 | 例（本仓） |
|---|---|---|
| ① **建对象时给默认** | 创建函数 / 模板 | `feature_ops.ts:43`（`'draft'`）· `templates.ts` · `node_ops.addNode` · `file_ops.addFile` |
| ② **扫描算出** | 索引/结构分析 | `import_project`（3 处 `'done'`）· `monolith.ts:587` · `simulation_engine.ts:326` · `narrate_step.ts:117` |
| ③ **复制/转写** | 把已有进度抄给另一个对象 | `api_ops.ts:238-239`（`node.status = file.status ?? …`） |
| ④ **显式改** | 工具（人/LLM 的判断） | `node_ops.ts:278` · `file_ops.ts:109` · `status_tools` |
| ⑤ **读侧兜底** | 渲染/查询时给缺省 | `query_feature.ts:295/321/381/445`（`?? '-'`）· `set_design_intent.ts:88`（`?? prev?.status`） |

### 22.2 ★★★ 根因：**从来没有规定"谁有权写它"** —— 而这五个时机**都以为自己"知道"它的值**
- 扫描"知道"的其实只是「**文件存在**」这种**结构事实**；创建时"知道"的只是「**这东西刚出生**」；
  读侧"知道"的只是「**我没读到值**」。**只有 ④（人/LLM 的判断）真正知道"实现到哪了"。**
- ⇒ ★ **七个写点 = 五类时机各顺手写一次**；不是有人偷懒，而是**每个时机都以为自己该写**。
- ⇒ ★★ 这是 §18"**没归类**"的另一面：**没归类 ⇒ 谁都能写**。

### 22.3 于是"该有几处"有了判据（不是"越少越好"，而是**写权按"谁知道"分配**）
> **一个字段的写权，应该只属于"真正知道它"的那一方。**
⇒ 五类里**只有 ④ 有写权** ⇒ 其余四类一律降为**读侧默认** ⇒ **收敛目标是 1 处**，而且**收敛的正当理由不是"减少重复"，是"写错了人"**。

## 25. 2026-10-15 §24.3 第 1 条（范围型决策）**核验结果**：一半已存在、一半真缺

### 25.1 核验（四个问题逐个有证据）

| ① `scope` 里的 `<id>` 是不是 `geometry.nodes[].id`？ | ★ **一半是**：`subtree:<id>` 的 id **就是 node id**（`scope.ts:187` `byId.has(scope.node_id)`）；`files:` 的 file id **也 = node id**（`types.ts:189`） | ★ 但 `swimlane:<id>` 过滤的是 `n.swimlane` = `Swimlane.id`（`geometry.ts:133`）、`arch_layer:<id>` = `ArchLayer.id`（`types.ts:136-138`）⇒ **不是 node id，无节点可挂** |

### 25.2 ⇒ 结论：**"范围型决策"今天能表达一半**
- ✅ **能**（零改动）：**`subtree` / `files` / `nodes` 那几种范围** ⇒ 挂**范围根节点**上的 `Node.decision` 即可；
  判据：`get_dsl{query:"scope",scope:"subtree:X"}` 得节点集 + `get_dsl{query:"node",node_id:"X"}` 读回该决策。
- ❌ **不能**：`swimlane:` / `arch_layer:` / `all` / `layer:` 是**分组谓词、无对应节点** ⇒ 这几种范围**没有落点**，
  今天只能靠 `thread` 命名 + 逐成员节点决策**近似**，**不能按范围一次查出一条决策**。

### 25.3 ★★ 我选的最小形状（**不破坏"决策与节点 1:1"这个现状**）
> **给决策卡加一个可选的 `scope` 引用**（存 `scope` 字符串，**不复制节点集**）——
> 决策**仍挂在一个节点上**（落点不变、1:1 不变），但它**声明自己管哪一片**。
- 为什么是它（三条）：① `scope` 文法**已有唯一落点**（`src/domain/scope.ts`），**不新增语言**；
  ② `consistency_check` **已在吃这套文法**（差异块按它命名）⇒ 接上后**对拍能按范围折块**（点亮 §24.2 判据④）；
  ③ **不变形状** ⇒ 不触发"决策 1:N"那一类破坏性改动（§24.2 判据②的风险点）。
- ★ 它顺带解决用户的**原话缺口**："节点上挂**这一范围**的决策" ⇒ 从此**"范围"有字段了**（哪怕 `swimlane`/`layer` 无节点）。
- 判据（可复跑）：登记一条带 `scope` 的决策 ⇒ `query decisions` 能**按范围过滤**出来，且该 `scope` **不落任何节点集副本**。

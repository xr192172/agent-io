# 闸的原则（gate principle）

> ★★★ **用户 2026-10-17 定**：*"我们就缺少一个**每一个环节独立的入口**，每个闸应该是**提醒和校验**，而不是**堵到其他的产生死循环**。"*
>
> ★★ **本文件是「闸」这一概念的权威**。★ 设计 DSL 的 `task_plan.gate_principle` 指向本文件（★ 不在两处各写一份）。

---

## 一、核心（一句话）

★★★ **闸默认是【校验器】，不是【关卡】。**

## 二、三种职责（★ 按优先级）

| 职责 | 什么时候用 | 输出 |
|---|---|---|
| ★ **校验** | **主体** —— 每次都用 | **通过 / 不通过 + 判据**（★ 让人知道该怎么改） |
| ★★ **提醒** | **不通过但【无害】** | ★ **放行 + 留痕**，让流程继续（★ 否则会堵出死循环） |
| ★★★ **阻断** | **例外** —— ★ **只在【会损坏数据 / 造成不一致】时** | 拒绝，并点名 |

★★★ **判据（遇到"不通过"先问这一句）**：
> **【它会损坏数据吗？】**
> ★ **不会** ⇒ **提醒 + 放行**（★ 因为"没在账上"是**记录问题**，不是**数据问题**）
> ★ **会** ⇒ **阻断**
> ★★ **不问就阻断 = 造死循环。**

## 三、每个环节独立的入口

★ **造节点 / 立卡 / 接取 / 做事 / 回执 / 收口** —— ★ **各有各的门，不许 A 依赖 B 而 B 又依赖 A。**

★★ **诊断法**：
> ★ **若某个入口"必须有下游的产物才能进"** ⇒ ★★ **那不是闸，是【环】。**

★★ 今天三个"鸡生蛋"都是同一形态（**用 A 造 B，而 A 又依赖 B**）：
1. ★ 新文件 vs 写闸（★ 闸不许建新文件，而它正是为"建新文件"设计的）；
2. ★ `publish` 要 `decision`（★ 而第一个 `decision` 从哪来）；
3. ★ `claim` 要 `path` 型节点（★ 而写端造不出 `path` 型节点）。

# 三份独立意见综评（2026-10-16）

> ★ **关于"是不是三个不同模型"**：我**无法从这边确认**它们实际跑在哪个模型上（只有用户界面能看到路由）。
> 所以我只把这称为**三份独立意见** —— 若界面显示它们回落成了同一个默认模型，那"多模型"这层就不成立，但**三份意见本身的内容仍然有效**。
> 三份都是**只读**产出的，未改任何文件。

## 一、两个洞（三份意见共同确认，且第三份把前两份都驳正了）

### 洞 A：**rename ⇒ "身份死亡"**（第一份发现，第二份说"修不了"，第三份说"能修"）
- **病**：id 从路径派生（`file_<sanitize(rel)>`）⇒ **改名后旧 id 变"要实现"、新 id 变"未纳入设计"**
  ⇒ **一次 rename 伪造成两条差异**（第一份）；
- 第二份断言"**`file` 改名后无共同 path 可配** ⇒ `renamed` 只救 symbol 级"；
- ★★★ **第三份驳正**：**"没有共同 path"不成立 —— git 早就把这个事实记下来了**：
  **首选键 = git 的 rename 边**（`git diff -M --name-status <base>..HEAD`）⇒ **由事实判定，不是由猜测定**；
  退化键（无 git）= **剔掉 id 与 path 字段后的规范化内容哈希**（文件级用成员 sig 多重集）；
- ★ **认错的代价控制**（第三份）：自动配对**仅当** ① sig 一对一唯一 ② 至少一个非路径属性一致；
  不满足 ⇒ **只报 `renamed?` 候选、不进施工单、不写别名** ⇒ ★ **"宁可漏配（响亮地报删+增），不可错配（假绿）"**；
- ★ 别名 `rename_map(oldId→newId)` 存**设计侧、仅人工确认后生效**；未确认前每轮重报（幂等）。
- **判据**：纯 rename、不改内容的提交 ⇒ **恰好 1 条 `renamed`、0 条 `to_remove`、0 条 `要实现`**。

### 洞 B：**项目本体双写**（第二份发现，第三份把"裁法"改对了）
- **病**：人手/外部工具改项目 ⇒ `live` 变 ⇒ 对拍报偏差 ⇒ **LLM 按设计把 hotfix 改回去** ⇒ **静默回滚，人机拉锯**；
- ★★ **第三份驳第二份**：「裁**项目源码谁能写**」是**无解题**（拦不住编辑器与 hotfix）⇒ **要裁的是"工具的反应"，不是人的权限**；
- ★★ **第三份驳第一份**：**`stale_gen` 对此无效** —— hotfix **不产生决策卡**，两侧 gen 上都看不出来；
- ★★★ **可判形式**：`live` 节点带 `observedHash` + `scanRev` ⇒ 对拍产出 `{designVal, liveVal, liveHash, adoptedHash}`：
  - `adoptedHash == liveHash` ⇒ `adopted`（设计已承认）⇒ 正常派"要实现"；
  - 不等 ⇒ **`unadopted_drift`** ⇒ ★★ **禁止生成任何"把它改回设计值"的任务**；只留两个**显式**动作：
    `adopt(actual)`（抄 live 进设计）或 `pin(designVal)`（选设计为真，**才**允许改源码，且**必须同时落决策卡**）；
- ★★★ **最深的一句**：**"方向不可从数据推出来（上轮 LLM 实现与本轮人 hotfix 字节相同）
  ⇒ 默认不许自动修，把方向变成「人写下的一个二值」。"**

## 二、★ 优先级裁定（第三份给的排序判据，我认为该采纳为通用判据）

> **响亮失败（显式报错/红）可后置；静默错（假绿、不可逆改写）必须前置。**

0. ★ **先驳"两个洞平分预算"**：**它们差一个量级** —— **洞 B 最坏 = 不可逆毁掉人写的代码**；洞 A 最坏 = 假绿（可查、可补）。
1. **洞 B 裁决**（`unadopted` → **不派工**）—— 挡"静默回滚人代码"；
2. **洞 A 首选键 = git rename 边 + 分级认亲** —— 挡假绿（漏做）；
3. **`unjudgable` 趋势读数 + `>0` 时 `overall` 只能 `unknown`、禁报 pass** —— 挡**对抗性**假绿（LLM 学会把难判的全标 false 换绿灯）。

## 三、其余增量（按"挡什么"归类，共 15 条）

**挡「假绿」**（本仓最深的病）：
- ★★ **零期望节点报 `uncovered`**（结构全绿但签名/边漂移无期望可抓 = 假安全）；
- ★★ **期望删除审计**：上代有、本代被删的期望**目标仍在实际** ⇒ 报 `dropped`；**删期望必须显式转 `deprecated`**
  ⇒ ★ **"无此读数 ⇒ 删期望 = 免费绿灯，报告可被静默清零"**；
- ★★★ **反向洞：LLM 会改设计去迎合实际** —— **消红最快 ⇒ 设计退化为投影，一致性满分、价值归零**；
  判据：只改 `value` 未动 `expectations`/`why`、且该节点上代对拍为红 ⇒ 记 `conformance-drift`（黄），连续两次 ⇒ 红并**强制写 `why`**。

**挡「噪声累积 ⇒ 报告被无视」**：
- ★ **"未纳入设计"要有分级/读数**（否则单调累积 ⇒ 狼来了）；
- ★★ **报告可寻址 + 幂等**：`{scanRev, designRev, liveRev, report_id}`；两次无改动重算 ⇒ **内容逐字节相同**；
- ★ **`scanRev`**：重算器版本变 ⇒ 差异标 `rescan`、**不进施工单**
  ⇒ **否则"扫描器升级被当施工任务，LLM 会去改项目'修'工具自身的变化"**。

**挡「并发/覆盖」**：
- **设计写乐观锁**：写设计须携 `baseGen`，≠ 当前 gen ⇒ 拒写 + `concurrent-write`；
- **id 碰撞闸**：`sanitize` 剥字符 ⇒ 不同路径可撞同一 id（`a/b.c` vs `a_b.c`）⇒ 写入前查唯一，撞 ⇒ 拒写 + `id-collision`；

**挡「语义丢失」**：
- **`status: deprecated` ⇒ 第五类 `to_remove` + 拆除单**（否则"不想要的东西"只能删，删完变"未纳入设计"，语义丢）；
- ★ **分类空间必须闭合**：1:N / N:1 / 两侧同错 ⇒ 报 `split`/`merge`，**禁止摊平成多条噪音**；
  每个 live 节点须被**恰好一个**设计节点认领、或显式标 `unmapped`。

**增强（非防病）**：
- **施工单**：对拍产物升为**有序任务列表**（`order` + `deps[]` 从 edges 派生 + 建议工具名）；
  ★ 注意第三份的提醒：`deps` 依赖 edges 先完整；"建议工具名"会随工具改名腐烂（可接受噪声）；
- **可选 `phase`**：只排序、**不做层次结构**（避免重蹈"投影层"覆辙）。

## 四、★★★ 共同盲区（第三份点的，我认为是今天最值钱的一段）

1. ★★ **三份都假设"报告会被读完"** —— 上百条差异时人/agent 只读前 10 ⇒ **分类再准也无效**；
   **前两轮全在优化"分类精度"，没人在优化"被读到的比例"**；
2. ★★★ **都在防"LLM 改错实现"，没人防"LLM 为了让报告变绿而改设计"**
   ⇒ **"一致性 ≠ 有用性；设计镜像 actual 时，对拍永远满分而价值为零。"**
3. ★★ **都在"节点/路径粒度"找身份，谁都没上到「事件粒度」** —— **git 早已把 rename 记成事件**。

## 五、我的裁决（综评后）

- ★★ **采纳第三份的排序判据**（"响亮失败可后置，静默错必须前置"）—— 它比"按重要性排"更能落地；
- ★★ **洞 B 前置**（先写"`unadopted_drift` 不许派工"这条**禁令**）—— 它是唯一**不可逆**的那个；
- ★ **洞 A 的键改用 git rename 边**（不是启发式 path 匹配）—— **由事实判定**这一条我完全同意；
- ★★ **把"反向洞"（设计迎合实际）写进规划的验收原则**：**"一致性 ≠ 有用性"**
  ⇒ 对拍全绿**不等于**做完（这条和本仓"总数变绿 ≠ 每条真绿"是同一族，但更根本）。

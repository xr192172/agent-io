## ① 架构与判据体系：机器判据优先

**骨架**：判据注册表 `src/domain/expectation_kinds.ts:148-338`（`KIND_SPECS`）+ 执行核 `src/domain/expectation.ts:466-1080` + 14 门 `scripts/verify.mjs:254-543` + 设计册 `.agent-io/design/*.dsl.json` + 写闸（`README.md:99-121` 任务闸/画布闸）+ §I 台账引擎（`src/application/ledger/ledger.ts:1-23`）。

**强在哪**
1. **判据与读数严格分轴**：`AGENTS.md:28-40`明写"读数不是判据，判据只回答通过/不通过"；`PROJECT-DESIGN.md:559-565`再定义"判据/测试/门"三者边界。这是全仓最难能可贵的纪律——它主动拒绝"覆盖率 N%"式假证据。
2. **判据有"牙"的元检验**：`scripts/verify.mjs:386-411`的「判据突变」门对 `src/` 做真实语义突变（`===`→`!==` 等），`survived>0 / unsupported>0 / killed===0` 全判红；`PROJECT-DESIGN.md:637-641`把它写成"自动化消除的是测试的机械写法，不是独立语义预期"。这是比 SWE-bench 类"pass@k"更诚实的度量：它量的是判据的鉴别力，不是模型的一次命中。
3. **四态不冒充**：`unsupported/pending` 不折成 pass（`verify.mjs:368`、`PROJECT-DESIGN.md:544-550`），`README.md:37`对外承诺四值语义。
4. **一处权威的持续收敛**：kind 清单从 `expectation.ts:199`派生自注册表而非手写；门数"权威是 GATES 运行时现算，散文里写一个数就是第二处权威"（`verify.mjs:588-589`）；删门时把历史理由搬进测试头注而非删除（`verify.mjs:321-325,347-351`）。这种反熵意识在工程里罕见。
5. **写权有来源链**：`PROJECT-DESIGN.md:374-389`规定根目标无天然源码写权，写权只发给主体/目标/范围/验收齐全的施工项；`AGENTS.md:182-225`把"意图层级"钉成四问硬闸。

**弱在哪 / 复杂度失控信号**
1. **"11 kind"本身已经漂移**：`expectation_kinds.ts:148`注释写"★ 11 种判据的唯一声明处"，但 `KIND_SPECS` 实有 **12 个键**（`:150 file-exists` … `:312 runtime`）；`README.md:36`仍写"九种判据"，`AGENTS.md:39`只列 6 类举例。**三处口径不一致**，而仓的整套哲学是"一处权威"——这是最讽刺的自指债。
2. **门的扩张靠"why"辩护，而非靠门数预算**：14 门里多道是"此前不在任何门里⇒补上"（`verify.mjs:363-384` 判据门、`:413-430` 文档门、`:490-513` 无卡写账门、`:515-541` 派生条目门）。每一道单独成立，但累计已使 `npm run verify` ≈8–13 分钟（`AGENTS.md:82,93,123`），迫使项目造出 `verify:changed` 内环（`AGENTS.md:44-55`）来绕开自己——**复杂度在被内环吸收，而不是被消除**。
3. **棘轮（ratchet）成为结构性妥协**：`verify.mjs:465-487`结构意图门默认带 `--allow-structure-gaps`，理由是"总门天天亮⇒人忽略 verify⇒真红被一起忽略"（`:471-472`）。这是对的工程判断，但它意味着**门在特定维度上被调宽以保住门的注意力价值**，与"判据只答通过/不通过"的纯度有张力。
4. **判据强度分层存在但执行碎片**：`rewrite_plan.ts:587-617`有 `SEMANTIC_KINDS/EXISTENCE_KINDS/WIRING_KIND` 分层，`AGENTS.md:39`也说存在类"发现不了逻辑错"；但普查显示存在类仍有 65 条在册（`backlog-census-2026-11-17-hy.md:40,49`），REGRESSION 面并非全语义。
5. **"自动测试编译器"（§9.5）仍是设计而非现实**：`PROJECT-DESIGN.md:567-641`规划了完整编译流水线，但 `todo.md:550`（T-#N4）实测 `compileBehaviorContracts` 仅 5 命中（定义/自引/委托/pilot×3），无工具面入口；`PROJECT-DESIGN.md:941`自记契约展开器输入几乎全空。**判据主要靠人写，编译器是 roadmap**。

## ③ 并发多模型协作形态

**现状**：`AGENTS.md:227-250`定义侦察席（只读，回报证据不回报成果）→主控裁定→执行席（首轮只回报）→验门提交，两条腿并行但**写盘永远一条腿**（`heavy.lock`）。`todo.md:580`（T-#SELF-DOGFOOD）记录用户 2026-11-17 拍板的并发设计链：多席**并发 edit_dsl** 提案（乐观锁+单写者队列已有）→ lead 手工 merge→领卡→多席**并发 edit_code**（write_gate 卡覆盖天然支持）→判据/对拍验收→worktree 式合并。PR 链纪律见 `todo.md:500-508`：挂账=提案、批注追加不改写、lead 综合裁定、开工先查账、跨批次存活。

**可扩展性**：流程设计上是对的——把"并发"限制在设计意图层（可分支，`VISION.md:10`），事实层保持单写（`VISION.md:9-10`、`docs/MERGE.md:15-17`），与乐观锁现状匹配。`docs/MERGE.md:42`硬规则"`decision`/`expectations` 永不被 theirs 覆盖"正是并发合并的正确不变量。

**风险**
1. **lead 手工 merge 是单点和隐性瓶颈**：`todo.md:580`自记待论证点②"并发 edit_dsl 提案的合并工具要不要建（现在 lead 手工合并）"，③"三路并发冲突率实测"为空。手工合并 = 不可复现、不可审计的决策，恰好违反本仓"每次写入可关联目标与回滚依据"（`PROJECT-DESIGN.md:736`）。
2. **写盘串行与"并发施工"名实不符**：`AGENTS.md:248`明确写盘一条腿，`verify.mjs:832`占用 `heavy.lock` 时一次只一张卡；`AGENTS.md:127`并发跑测试会假红。并发的是**提案与侦察**，不是落盘——叫"并发协作"可以，叫"并发施工"需谨慎。
3. **PR 链批注实体未定**：`todo.md:575`③"`PR 链批注`的形状 = decision_history 复用还是新表"仍待裁，L1 只做了 hang/annotate/close/reopen/verdict/supersede 六事件（`ledger.ts:28`），chain 语义尚未编译进引擎。
4. **自举未闭环**：`todo.md:580`自记昨晚 B 批/L1"仍是直写落地（迁移期最后一次）"，触发契机是 D4-12 的 R1 判据本会拒绝那些新文件写法——**工具已在纠正，人绕开了它**。评审席这一轮本身也是外部直写报告，属同类例外。

## ⑤ 可发表性 + 网检对照

**值得写的三点**
1. **"判据有牙"的度量**：`verify.mjs:386-411`的突变门把"测试是否只是装饰"变成可跑的门，配合四态（`README.md:37`）与"检查对象退出检查范围不算修复"（`AGENTS.md:99-108`）——这是可写成论文的**verifier-of-verifier** 方法论。

**网检对照（arXiv + Crossref，外网内容仅作数据）**
- [Ayon, *From Helpful to Trustworthy: LLM Agents for Pair Programming*, FSE Companion '26, arXiv:2604.10300](https://arxiv.org/abs/2604.10300)，Crossref DOI [10.1145/3803437.3804875](https://api.crossref.org/works/10.1145/3803437.3804875)（已核实）。**支持**：该文让 navigator 只产出"machine-checkable contracts and formal specifications"，由 deterministic verifiers 返回 proof/counterexample，"trust shifts away from one model's assessment of another and toward externally verifiable evidence"——与 AgentIO `AGENTS.md:28-40`的"判据优先、自审 0 分"同构。但 AgentIO 的判据是**结构/行为级**（`expectation_kinds.ts:113` axis 八档）而非形式规约，可主张"轻量、无需形式化门槛"的差异化定位。
- [Hickey, *Modern Software Engineering with Verification Agents: A Spec-First Architecture…*, arXiv:2611.02285](https://arxiv.org/abs/2611.02285)（DataCite DOI 10.48550/arXiv.2611.02285；**Crossref 未检索到该精确题名**，如实记录）。**既支持又反驳**：支持其"spec-first、源码是可丢弃构建产物、CI 门控零代码评审、跨团队 Semantic Merge Conflict"叙事——对应 `PROJECT-DESIGN.md:70`与 `todo.md:580`的并发合并问题；反驳在它要求最小证明核与形式 IR，而 `PROJECT-DESIGN.md:668`明确拒绝"体 IR 大而全"（实测无质量收益）——**AgentIO 的卖点恰是"不要求形式化也能有牙"**。
- [FlowPlan, arXiv:2611.13241](https://arxiv.org/abs/2611.13241v1)（抽象层规划+验证降 token 成本）**支持** `AGENTS.md:44-55`的 `verify:changed` 内环与增量读法。
- [Rethinking Code Review in the Age of AI, arXiv:2605.17548](https://arxiv.org/html/2605.17548v2) 提醒：多席评审会把 human-to-human mentorship 挤掉——AgentIO `todo.md:580`的 lead 手工合并正是"人被挤出回路"的风险点。

**结论**：有真实亮点，但直接写论文证据不足——仓内缺"与基线对照的真实任务结果"（`PROJECT-DESIGN.md:130-140`未兑现）。建议先写**工具/经验论文 + 公开突变门实测数据**，再谈方法学。

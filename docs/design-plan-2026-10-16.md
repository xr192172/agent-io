# 设计 / 实际 —— 完善版规划（2026-10-16 定稿）

> 本文**取代**流水账里散落的临时裁定。它综合了两边：
> **用户的模型**（简单、对：两个文件、fork 初始化、决策卡 + 代）
> ＋ **已实测可用的部分**（id 作指代物 · 认亲 · 写前自洽闸 · 错误键口径 · 四类判定）。

## 〇、一句话

**写只写两处：设计（`design/`）与实际（`live/`，由重算写、不由人写）。投影是算出来的。**

## 一、两份文件 · 两个消费者（用户的原则，作为地基）

| | `live/<f>.dsl.json`（实际） | `design/<f>.dsl.json`（设计） |
|---|---|---|
| **消费者** | ★ **LLM 读** —— 掌握项目**实际情况** | ★ **LLM 改/创作新方案** |
| **来源** | **每次从项目重算** | 人 / LLM 写（EditDSL） |
| **可写？** | ★ **不可写** —— 改它 = 让 LLM 看到**假的现状** | ★★ **唯一可写** |
| **决策卡** | 显示**它当时被改的那一代** | 挂**最新一代** |

★ **可写性判据（判据源泉）**：**一个数据该不该可写，看它有没有「要修改它」的消费者。**
⇒ `features/<f>.json`（合并视图/投影）**两个消费者都不认它** ⇒ **没有消费者 ⇒ 退役**（退化为读时派生）。

## 二、id 的定位（★ 回答"实际侧的 id 有没有指导开发的效果"）

★ **有。id 不是"edit 专用"，它是「跨视图的稳定指代物」** —— 五处消费者：
1. **期望/决策卡的挂载与判定**：`expectations` 的结果按 **`node_id`** 报（"该做什么"必须能指到具体节点）；
2. **对账配对**：四类判定（同 id / 要实现 / 未纳入设计 / 认亲）全靠 id；
3. **`scope` 点名**：`files:` / `nodes:` / `subtree:`；
4. **overlay 锚点对齐**：按扫描 id；
5. ★★ **LLM 读 live 时，把"结构"与"意图/进度"关联** ⇒ **没有 id 就无法稳定地指"这个节点"** —— **这就是指导开发**。
⇒ ★ **裁定：id 留着**（两侧都留）。

### ★ 为什么要 fork 之后两边天然对齐
**id 是从路径派生的**：`file_<sanitize(rel)>`（`import_project.ts:889-890` 实测）⇒ **可再生**，
⇒ 只要"同一个路径"，**两边算出的 id 相同** ⇒ **fork 一份实际当设计时，id 自动对齐**。
⇒ ★★ **只有"设计里凭空造的东西"（没有路径）才需要 LLM 自己起名**（`Design One` 那种）—— schema 要求 `Node.id`，它必须给。

## 三、四种身份（对拍的全部判定，已实现）

| 情况 | 判定 | 说明 |
|---|---|---|
| 两边同 id | **对齐** | 比属性（有差 ⇒ 属性差） |
| 只在设计里（有路径/名字） | **要实现** | ★ = "拖建筑"得到的任务 |
| 只在实际里 | **未纳入设计** | 提示，未必是错 |
| ★ 设计侧**无 id**的条目按路径命中实际 | **认亲（`resolved`）** | ★ 带出实际的 id ⇒ "要实现"**自己收口** |

## 四、初始化（fork）—— 唯一有分歧的一处，我裁定如下

| 情形 | 动作 |
|---|---|
| **两者都空** | ★ **LLM 自己从零写设计** |
| ★ **设计空、实际有** | ★ **把实际 fork 一份 ⇒ 作为设计** ⇒ 再按文档/用户需求改它 |
| 设计有 | 直接改设计 |

★ **fork 时带不带决策卡？—— 裁定：不带**（设计从"无意图"开始；决策卡由人/LLM 挂"最新一代"）。
★ 理由：决策卡是**意图**；fork 过来的是**结构现状**。若把实际的卡一起 fork 进来，
  会让"设计侧"看起来已经表过态（而它其实还没有）。
★ ★ **这一条会影响迁移** ⇒ 见 §七。

## 五、代（generation）

用户描述：**设计挂最新一代；实际显示"它当时被改时的那一代"**。
★ **实现路径（待核）**：实际侧在每次重算时，把它当时**看到的决策卡快照**一起带上（"代"= 快照的版本标记）。
★ 用户说"**这个应该已经是实现了的**" ⇒ ★ **本规划不重写它**；只做**核 + 迁移评估**（见 §七）。

## 六、阶段（每阶段一个判据，单包做单包验）

| 阶段 | 做什么 | 判据 |
|---|---|---|
| **P1** | **设计图的初始化 = fork 自实际**（设计不存在 && 实际存在 ⇒ 拷结构当设计） | fork 后 `design/<f>.dsl.json` **过 `validateDSL`**；`getDSL` 读得到它；重建不抹它 |
| **P2** | ★ **`edit_dsl` 一族写 `design/`**（今天写 `features/<f>.json` = 投影 ⇒ **没写完**） | ① 改设计后 `getDSL` 读得到新值；② `rebuild_design=true` 后**改动仍在**；③ 无设计图的 feature **零行为改变** |
| **P3** | **扫描/重算一族写 `live/`**（今天也写 `features/` = 错位） | `live/<f>.dsl.json` 由重算写；不再依赖 `features/` |
| **P4** | ★ **`features/<f>.json` 退役**（退化为读时派生） | `getDSL` 不再需要它；全证绿 |
| **P5** | ★ **迁移**（按 §七 结论执行） | 迁移前后**真仓对拍读数不退化** |

★ **顺序纪律**：P1 必须先（没有设计图，P2 无从写起）；**P2 与 P3 不能颠倒**（否则出现"写 A 读 B"）；
★ **每阶段独立可回滚**，且**不许留"半修"**（本仓铁律：半修比不修更坏）。

## 七、迁移（★ 待核，用户点名要看的）

**要核的三件事**（已派只读核）：
1. 决策卡**物理在哪一份**（`features/<f>.json` / `.overlay.json` / `design/`）⇒ 它算设计侧还是投影侧；
2. **"实际按同 id 看卡"今天怎么实现的**（`applyOverlay`/`mergeDesignLayer` 的匹配键）；
3. **"代"今天存在吗**（`decision_history` / `progress.history` / snapshot / `baseRev` …），**是不是用户描述那样**。

**迁移的判据**：★ 若"决策卡现在住在 `features/<f>.json` 或 `.overlay.json`"（**投影侧**）
⇒ ★ **它们是"要修改的意图"⇒ 必须挪到 `design/`**（否则 P4"投影退役"会把它们一起退掉）。
★ **真仓现有 feature 逐个清单**（决策卡数 / overlay 内容 / 有无 design）是"迁移要不要做"的事实基础。

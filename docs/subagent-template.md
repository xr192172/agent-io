# 派子代理的模板（2026-10-20 起，每次派活照抄）

> 起因：2026-10-20 一次工具链体检发现 —— **子代理改代码时默认会用 `Write` / `Edit`，
> 而 `edit_code`（会重建索引的那个）一次都不调**。
> 根因不是子代理懒，是**我的 prompt 里没要求**（dogfood #18：写闸只管仓内工具，`Write`/`Edit` 不受管）。

---

## ★ 零、派活前先让子代理读这三份

写进 prompt 的开头（**不是建议，是要求**）：

```
先读这三份（按顺序，不必读完，读与你任务相关的节）：
1. docs/INDEX.md      —— 入口，先看它知道该翻哪份
2. docs/VISION.md     —— 用户对这个功能的原话（"应该是什么"）
3. docs/DESIGN.md     —— 实现现状（"现在是什么"）；你改的东西可能已在缺陷台账里
```

**为什么**：`VISION.md` 是"应该是什么"的唯一权威。
子代理不看它，就会按**自己以为的**"应该"去改 —— 今天一天我因此被推翻 4 次。

---

## 一、硬约束（必须原样写进 prompt）

### 改代码只许用本仓工具

| 必须用 | 不许用 |
|---|---|
| `edit_code`（`replace_text` / `range` / `symbol` / `insert`） | `Write` 工具 |
| `design_line … action=rewrite`（把源码拉回设计签名） | `Edit` 工具 |
| `refactor_line … apply=true` | `sed -i` / shell 重定向写文件 |
| `remove_dead_imports`（删死 import） | Python / Node 脚本写文件 |

**唯一例外**：可以在 `_design-canvas-labs/`（实验区，仓外）写任何东西。

### 为什么（写进 prompt 让子代理理解，不只是服从）

1. **`edit_code` 会重建索引**（`symbols.ts` 的 `syncFile`）；`Write` 不会
   ⇒ 源码与索引不同步，后续所有读数都是旧的。
2. **写闸（`write_gate.ts`）只装在仓内工具**（`edit_code` / `rename_*` / `symbol_move`）
   ⇒ `Write` / `Edit` **完全绕过它**。「无卡改动」是**结构性诱因**，不只是纪律问题。
3. **只有走仓内工具才有回执**（`匹配 L1·exact` + 行号 + diff + 符号 diff）
   ⇒ 没有回执的改动 = "悄悄改了"。

---

## 二、回报格式（必加，尤其是第 3 条）

1. 目标达成情况（做了什么、验收数字）
2. **工具调用清单**（逐条：命令 + 结果一句话）
3. **工具摩擦**：★ 用这个仓库的工具时，**哪里让你多做了动作 / 让你猜了 / 让你重试了**
   —— 这条是给**工具本身**的反馈，用户要看。
4. 有没有**违规用过 Write/Edit**（如实说，不扣分 —— 这本身就是"强制绑定为什么必要"的证据）
5. 有没有**还原不了的残留**（改坏了要 `git checkout --` 还原，别留半成品）

## 三、已知坑（写进 prompt 帮它省一轮）

| 坑 | 对策 |
|---|---|
| **行号会漂** | 引用代码**带符号名**（`reopenTask`），别只给行号 |
| `design_line --help` **不可用**（返回 schema 校验错） | 用 `--schema` |
| `design_line action=report` **不列文件** | 要文件级差异得用 `action=rewrite file=…` |
| `design_line` 的 `ok:true` **语义过载** | 别只看 `ok`，看 `differ` / `scanned` 的实际值 |
| `remove_dead_imports` **不能按文件调**（必填 `dead` 列表） | 得先有别的工具算出候选 |
| `edit_code` 的「索引失败」混在 `✓` 行里 | 看 `---DATA---` 里的 `written` |
| `import_project` 的 `max_files` **默认 200** | 全量重建要传 `max_files=10000` |
| 清库后 `SCHEMA_VERSION` **不会二次触发** | 直接 `DELETE FROM nodes/files/...` 再导入 |
| 长进程（MCP server）**会用旧 dist 写库** | 改完代码先 `tsc`，再确认没有旧进程；必要时杀 |

## 四、侦察 / 实现两阶段（2026-10-20 用户裁定）

**一次派活只做一件事**：

- **侦察**：只读，产出"问题在哪 + 修法候选 + 代价"。**不许改代码。**
- **实现**：输入是侦察结论（精确到 `文件:符号`），产出是改动 + 验收数字。

**为什么分开**：今天的实测 —— 侦察型子代理读了 4 个文件 500 行才敢回答"闸该插哪"；
如果让它同时实现，它会**在没想清结构时就动手**。

**例外**：修法完全明确（1-2 行）时，可以一次派完（如 `pruneDeletedFiles` 的 `existsSync`）。

---

## 五、验收的三条纪律

1. **正面 + 反面都要**（修好 X 的同时，Y 不能被堵死）—— 今天的 `reopenGate` 33 项就是这么设计的。
2. **断言要能红**（故意改坏一处，看断言是否变红）—— 否则是空转。
3. **数据 vs 代码**：跑出来的**数字**才算验收，`source-has` 只能证明"代码里有这个词"。

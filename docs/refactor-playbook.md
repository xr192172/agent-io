## 0.0 ★★★ 加「防御性判据」之前先问一句：**我能造出那个坏状态吗？**

（2026-10-09 立。来源是真事：我做了 `diagnoseFactsOffset`（核对"事实抵消"的两个前提）之后，
**试了两种造法都造不出它要防的坏状态** —— 删 `features/<f>.json` 的字段没用（`getDSL` **优先读"活态文件"**）；
传不同 `live_dir` 也没用（它只决定"去哪找 live 文件"，**不改 `source_root`**）。）

按"**能不能造出坏状态**"分三级：

| 级 | 坏状态能造出吗 | 真发生过吗 | 怎么处理 |
|---|---|---|---|
| **A** | 能 | **是** | ★ **必留** —— 有**出生证**（注入 ⇒ 变红 ⇒ 还原） |
| **B** | 能 | 否 | 留（有验收即可） |
| **C** | ★ **造不出** | — | ★★ **要么删，要么"减噪"：让它在常态下零成本** |

★★★ **C 类就是「过度防御」的可判定定义**：造不出坏状态 ⇒ 它**几乎永远为空** ⇒
**不该占常态输出的位置**（否则每次输出多一个恒空字段，还会让人以为"这里有东西看"）。

★ **落地样板**：`diff_views` 的 `data.notes` —— **只在非空时才出现**
（`...(n.length ? { notes: n } : {})`），**类型上也是 optional**（`notes?: string[]`）
⇒ **正常路径零噪声、异常路径明说**。
★ **反面样板**：同一处我第一版写成**恒有 `notes: []`** ⇒ **常态即噪声**（当场改掉）。

★ **它还有第二个用处**：一条防御**造不出坏状态** ⇒ 先回去确认**"它防的是不是我以为的那件事"**，
别急着加代码。★ 这条与 `guard-blindspot-diagnosis` 的教训同源：
**守卫的判据若与它声称守的东西不一致，它照样会静默放行。**

## 1. ★ 搬移/收敛一块的标准 8 步法（顺序即纪律）

> 核心：**先有判据，再动代码**。没有判据的搬迁，验收只能靠人看 diff —— 而 71k 行的 diff 没人看得完。

### 第 0 步（2026-10-01 新增，实测一天踩了 4 次）：**搬之前先跑 `preflight_move`**

```bash
node scripts/preflight_move.mjs <将被移动的相对路径> [新路径]
```

它按**"谁抓得到"**把全仓引用分档，★ **重点是把 tsc 抓不到的那一类单独标出来**：

| 档 | 谁抓得到 | 踩过的实例 |
|---|---|---|
| `tsc-import` | `tsc --noEmit` 当场报 | 改就行，**不会漏** |
| ★ `registry(钩子/脚本)` | **只在提交时炸**（pre-commit ENOENT 挡下）或**运行时** | `scripts/capability_scan.mjs` 的 `FEATURE_FILES` |
| ★ `registry(夹具)` / `registry(架构基线)` | 跑测试时红 / `arch` 判 stale | `server_registry.consistency` 的 `importedBy`；`.dependency-cruiser-known-violations.json` 的环 |
| `test-ref` / `doc` | 测试慢抓 / 靠人同步 | — |

★ **它不覆盖、但同样会炸的两件事**（工具输出里也会提醒）：
1. **门的判据可能认不出"文件夹形式的模块"**（只认 `<name>.ts`）⇒ 泛化成 `文件 or <name>/index.ts` 两形态都认。
2. **依赖环会随文件位置变化** ⇒ 搬完**必须**跑 `npm run arch`（0 违规 / EXIT=0）。

★ 配套量具：`node scripts/lang_density.mjs`（决定「下一刀拆哪个文件」）。

### 第 0.5 步：**批量搬迁的相对路径，要用「解析→映射→重表达」算，不要手抄**

```
target = normalize(join(解析目录, spec))        # spec 形如 './x.js' / '../x.js' / import('./x.js')
mapped = OLD2NEW[target]                        # 目标自己也搬了的话用新位置；否则 None
rel    = relative(mapped or target, 表达目录)    # ★ 保留原扩展名写法（源码里写 .js 是 TS 惯例）
```

★★★ **两个 pass 的规则不同** —— 这是唯一要记牢的点（2026-10-02 我在这里连错两次）：

| pass | 对象 | 规则 |
|---|---|---|
| **A** | **被搬的文件自身** | 它自己动了 ⇒ **所有**相对说明符都要重表达（`target = mapped or 原目标`） |
| **B** | **没动的引用方** | 只有**目标被搬走**时才有理由改；`mapped is None` ⇒ **一个字都不改** |

- ★ 把「顺手归一化」用在 pass B ⇒ 会把**测试夹具里模拟的**字符串也改掉
  （实测：`"import { A } from '../tools/verify_refactor'"` 是在模拟 `sub/live.ts` 里的 import，
  被改成 `'./verify_refactor'` —— 对测试文件成立，却**破坏夹具意图**）⇒ **搬迁工具只该做搬迁**。
- ★ 把「只有 mapped 才改」用在 pass A ⇒ 被搬文件里指向**没搬的**模块的 import 不会重表达 ⇒ `tsc` 一片红。
- ★ **别分两遍改同一批文件**（第二次会把深度**叠加**：`'../../x'` → `'../../../x'`）。
  非要重来就先回滚：`git reset` → `git checkout -- .` → 删新路径。
  ★ 目标目录若**已存在**（如 `observe/` / `impact/`），只能删搬进去的那几个文件，**不能整目录删**。
- ★ **机械变换 > 手抄清单**：实测手抄计划漏了 3 个引用方（含"同文件内 / 多行 import / 再导出"三类），
  机械匹配全找出来。★ 但注释里的示例串属**假阳**，别改。
- ★ 跑完**必查假阳**：`git diff` 里「不涉及目标目录」的改动行，逐条判是真是假。

| 步 | 动作 | 判据 / 产出 |
|---|---|---|
| 1 | **先量** | 把"要动的东西"量出来：行数、副本数、口径、真实调用面。**不许凭印象**。命令见 §3 |
| 2 | **先建门** | 若本块缺少"与文件位置无关"的判据，先补门（G1 这类快照门最优先）——**门可以当天不红，它是买未来** |
| 3 | **脚本化搬移** | 用一次性脚本按**文本区段**精确搬，不要手抄。★ 区段边界必须用编译器复核（§4.1） |
| 4 | **补依赖** | 脚本按"标识符是否出现"算 import；**算不出的（默认导入、动态导入）靠 tsc 兜**（§4.2） |
| 5 | **过 ①** | `tsc --noEmit` 干净。**不许带病继续** |
| 6 | **过 ②③④⑤⑥⑦⑧** | 门全绿；若有门红，先判断是"门对了"还是"门跟着被搬走的代码失效了"（§4.3） |
| 7 | **过 ⑨ + 对账** | 全量回归；★ **测试数与搬迁前逐字相同** = 纯结构移动的证据 |
| 8 | **提交 + 更新台账** | 一笔一提交；规划书 §7 与 §9 同步；推送 |

★ 反面教材（本仓真实发生）：先改代码、后补测试 → 缺陷在 237 个测试下存活数周
（`865a388` 的 `.js` 后缀缺陷就是这么活的）。

★★ **新建门之后必加第 6.5 步：做出生证**（逐个制造它能抓的错，确认会红）。
P1c 的实测：新门 7 项全绿，看起来很好；一做出生证，**6 条里有 1 条是恒真的空门**
（见 §4.11）—— 若不做，这条假门会一直在那里给人虚假的安全感。

## 2. 三类"改了一块就会断"的路径敏感（★ 全部踩过）

| # | 类别 | 症状 | 处置 |
|---|---|---|---|
| 1 | **静态 import** | 文件名改了/深度变了 ⇒ 找不到模块 | 脚本按"标识符出现"重算 import，`tsc` 复核 |
| 2 | **动态 import** | `await import('./tools/x.js')` —— 字符串里的相对路径**编译器只查形式不查语义**……实际上会查，但**只在它被搬动时**才暴露 | 搬移时对条目文本做 `import('./` → `import('../../` 之类的深度修正；**手动清点一遍** |
| 3 | **★ 门按路径读源码** | 门不报错，它**读到空**：要么空过，要么把全世界判成"新增/删除" | 见 §4.3 |

```bash
# 谁按路径读 src 源码
grep -rn "src/" tests scripts --include=*.ts --include=*.mjs \
  | grep -E "readFileSync|readdirSync|existsSync|git show"
```

## 4. 已知陷阱（每条都有现场实例，别重犯）

### 4.1 区段边界差一行 ⇒ 函数被静默截断
首次抽 `handlers` 时区段取到 `941`，而结尾 `});` 在 `942` ⇒ 抽出的函数缺右括号。
- 症状：`TS1005: '}' expected`。
- 纪律：**回滚重做，不要就地打补丁**（`git checkout -- <file>`，改脚本，重跑）。
- 教训：边界用**编译器**复核，别靠肉眼数行号。

### 4.2 依赖清单算不全：默认导入 / 动态导入
按"标识符是否出现"匹配 import 表，只能覆盖**具名导入**。踩过两次：
- `import path from 'node:path'`（默认导入）漏了；
- 条目内的 `await import('./tools/write_gate.js')`（动态导入）漏了。
- ⇒ 让 `tsc` 抓，别指望脚本一次算全。

### 4.3 ★ 门"跟着被搬走的代码失效"（最隐蔽，P1b 一次打红两个 CI 门）
| 门 | 失效形态 |
|---|---|
| `readme_tools_gate.mjs` | 写死读 `src/server_registry.ts` 数工具数 ⇒ 搬到 `lanes/` 后**扫出 0 个**，把全绿回归打成红的 |
| `contract_docs_gate.mjs` | 写死路径 ⇒ `cur` 空而 `prev` 67 ⇒ **把 67 个工具全判成"改名残留未清"**，CI 一片假红 |

**修法（已落地，作为范式）**：
1. 把"输入在哪"收成**唯一实现**：`scripts/tool_sources.mjs`；
2. **扫目录，不写死文件清单**（`src/server_registry.ts` + `src/registry/lanes/*.ts`）；
3. 需要历史对比的，**逐个文件**从 git 读（HEAD 里还没有的跳过）。

> ★ 判据：**"门的输入在哪"本身也是一处知识。** 写死路径 = 又造一份副本，迟早与事实分叉。
> ⇒ **新建任何门，一律不许写死"工具定义 / 内核 / 注册表"的路径。**

### 4.4 破环：两个东西互相需要 → **延迟注入，且不给"看起来能用"的默认值**
实例：`capability_map` 的目录必须来自真实注册表，但它属于 meta 线，而 `TOOL_DEFS` 是各 lane 汇总出来的。

```ts
let toolDefsRef: ToolDef[] | null = null;
export function bindToolDefs(defs: ToolDef[]): void { toolDefsRef = defs; }
function laneCatalog(): ToolDef[] {
  if (!toolDefsRef) throw new Error('[capability_map] TOOL_DEFS 尚未注入 …'); // ★ 不给空表
  return toolDefsRef;
}
```
★ **不给 `[]` 兜底** —— 空表会静默报"0 个工具"，那是把"没接上"伪装成"确实没有"（规划书 §2d）。

### 4.5 夹具不覆盖生产写法（同一类缺陷在本仓靠这个存活两次）
- health 旧夹具用**无后缀** import，而生产 961/971 条带 `.js`；
- `project_root` 夹具同理，导致 `.js` 盲区（966/967 条解析失败）长期不可见。
- 纪律：**新夹具先 diff 一遍生产的写法约定**（后缀、模块系统、路径风格）再写。

### 4.6 一致性断言会挡"改善方向"的改动 —— 要显式放宽并写明理由
- G1 快照按 **name 排序**比较（lane 拆分必然改顺序，而 MCP 工具按名寻址）。
- 这是**有意放宽**，必须在门的文件头写明理由，否则后人会以为漏了判据。

### 4.7 ★ 收敛副本时**先给权威写单测** —— 写作过程会逼出"副本们一致地错了"
B1 实测：把 `cli_extract` / `registry_extract` 里**逐字相同**的函数收进 `ts_kernel/import_text.ts` 后，
我按"注释声称的语义"写了单测（`a as c` → 应映射**本地名** `c`），**立刻红了** ——
两份旧实现取的都是 `as` **前面**的远名。仓内已有 **4 处**带别名的相对具名 import
（如 `tools/rule_apply.ts:31`），只是都不在被反查的位置上 ⇒ **潜伏缺陷**。
- 纪律：**副本相同 ≠ 副本正确**。收敛时按注释/意图写测试，让测试去证伪。
- 处置：修成"远名与本地名**都收**"（**严格增量**：旧行为保留、新能力补上、零风险），
  而不是二选一 —— 当你不确定哪种语义是消费方要的，**收两者的并集**通常最安全。
- 附带发现：这两份副本的**覆盖不对称** —— `registry_extract` 有测试、`cli_extract` **没有**。
  副本能悄悄分叉，往往就是靠这种不对称。

### 4.8 ★ 「提示」与「失败」必须在不同的返回值里 —— 否则**任何改善都会把门打红**
品牌残留门第一版把"债务减少（好事，应收紧基线）"和"新增命中（坏）"拼进了**同一条**信息字符串，
调用方于是写成 `expect(msg).toBe('')` ⇒ 我第一次重构**减少了 188 处**旧品牌串时，
门**红了** —— 惩罚了正确的方向，正违反棘轮纪律（"只在新增命中上 fail"）。
- **纪律**：`added` / `grown`（这两类）单独断言 ⇒ 红；`shrunk` / `cleared` 只 `console.log` 提示。
- 通用化：**任何"棘轮/基线"型门都要把"变差"与"变好但不合规"分开返回**。
  顺手把这条也写进 `tests/helpers/ratchet.ts`（那份便利函数的注释解释了为什么刻意不提供它）。

### 4.9 ★ 单点化会把"看起来必须保留旧名"的地方暴露出来 —— 但先问"那东西**该不该存在**"
把 `.design-canvas`（193 处 / 130 文件）收成 `src/data_dir.ts` 的常量后，品牌残留门**立刻报红**，
因为**新模块本身就是"新增的旧名出现处"**。门没错。我当时的处置是加一个 `DATA_DIR_NAME_LEGACY` 常量
（"迁移期回退"）并写进 `allowFiles`（**这一步是错的**）。

用户纠正后查实：那批预留（`DATA_DIR_NAME_LEGACY` / `DATA_DIR_NAMES` / 4 个 helper）
**引用数全为 0 —— 出生即死代码**，因为**本项目没有下游**（唯一下游 dsh-brain 走 MCP+桥接，改完重桥即可）。
⇒ 那条"豁免"是在**为不存在的下游写脚手架**；正确处置是**整批删掉**（已删，见规划书 §10.4 / §11.1）。

★ **所以门报红时有两问，顺序不能反**：
1. **"它拦的这件事是否本来就该存在？"**（该存在 → 写进 `allowFiles` 并写明理由）
2. **"如果不该存在，我为什么还在为它写豁免？"** —— 豁免是逃逸阀，**不是**默认动作。

### 4.10 ★ 正则解析"多形态 + 混合换行符"的表 ⇒ 用**逐行状态机 + 数量守卫**
P1c 要把 `LANE_OF` 的 67 条改写成 `WHEN_OVERRIDES`，我写了一版单条正则去刮条目：
```
/^  ([a-z_]\w*): \{([\s\S]*?)\n?  \},$/gm
```
**实测只刮到 1 条**（应为 67）。根因两条，都不是"正则写得不够聪明"：
1. 文件是 **CRLF**，而我的 `$` 边界假设了 LF；
2. 67 条里 **66 条是单行形态**（`  get_dsl: { lane: ..., when: '…' },` —— 收尾是 ` },` **一个空格**），
   只有 1 条是多行形态（收尾 `  },` 两空格）。我的正则把"多行形态的收尾"当成了通用边界。

⇒ 规则：
- **逐行状态机**（`^  name: {$` 起 → `^  },$` 止；单行形态单独特判），不要用一条正则吃掉嵌套缩进；
- **先备份**（`cp x.ts /tmp/x.bak.ts`）；
- ★ **数量守卫**：脚本里写 `if (parsed.length !== 期望值) throw` —— **未达预期条数就不落盘**。
  这一条救了这次：脚本报错退出，文件一个字节都没被改坏。
- ★ **换行符要按行保留**，不要"整文件统一 EOL"：本仓文件是**混合**的（CRLF 为主 + 若干 LF 行），
  按单一 EOL 拼字符串会让只有全 LF 的那个文件命中、其余静默跳过（P1c 就撞到了，第二次运行才发现）。

### 4.11 ★★ 恒真的断言不是门 —— 新门**必须逐个做出生证**
"门全绿"不等于"门有效"。P1c 新门 7 项全绿，我逐个制造它能抓的错，**6 条里 1 条原形毕露**：
我断言"`TOOL_DEFS` 里的 def 就是 lane 数组里那个**同一个对象**"，而 `TOOL_DEFS` 正是
`LANE_SOURCES.flatMap(...)` 派生出来的 ⇒ **恒真**，探针（故意改成 `map(d => ({...d}))` 产复制品）照样绿。

⇒ 纪律：
- 每条新门写一个**探针脚本**（在 `.inspect/`）：逐个注入它能抓的错 → 跑门 → 断言变红 → 还原（`process.on('exit', restore)`）。
- 探针要**同时包含"本门应该抓不到"的对照项**，否则你不知道自己的断言是在抓什么。
- 发现恒真断言 ⇒ **删掉，不要保留**（保留会给人虚假安全感，正是本项目"兜底代码"的同一种病）。
- 出生证结果写进门文件头（本仓惯例，见 `tests/registry/lane_sources.test.ts`）。

## 8. 全局串改名（品牌 / 前缀 / 目录约定）怎么做

> 与"搬移一块"的区别：搬移改**位置**，本程序改**内容**，而且**触及几乎每个文件**。
> 具体案例与清单见规划书 §10。

### 8.1 先判"这是不是字符串替换"—— 先回答**"有没有下游"**

> ★★ **纪律：兼容层必须有下游才配存在。**（2026-09-28 用户纠正 —— 我起初给数据目录名/环境变量
> 设计了"新名 + 旧名仍生效 + 弃用提示"，用户一句"我们又没有下游"就否掉了，且实测那批预留
> **引用数全为 0、出生即死代码**。）
> 判断要**取证**（谁在用、怎么用、怎么改），不是习惯性留一手 —— 留一手的代价是
> **永久多背一份代码 + 一条永远没人走的路径**。

**有下游时**，下列三类**不是字符串替换**，必须单独处理：

| 类别 | 判据 | 例（本仓） |
|---|---|---|
| **运行时契约** | 改了它，盘上已有数据/外部调用方就找不到 | `.design-canvas/` 数据目录（`rules/` 住这儿） |
| **外部写死的名** | 用户脚本 / CI / 别人机器上已写死 | `DC_DAEMON_PORT`、`DESIGN_CANVAS_MEMORY_WATCH` |
| **对外契约 / 仓库级** | 客户端配置、包名、bin、git remote | MCP client 的 server key（`mcp__<key>__*` 的前缀来源） |

**→ 有下游**：新名 + 旧名仍生效（读新优先、回退旧）+ 弃用提示，**不许**静默改用新名。
**→ 无下游**（本仓现状）：**直接全量干净改**；本地已存数据由使用者自己迁移或丢弃，
代码里**不留下任何回退路径**。

### 8.2 五步程序

1. **先量形态**（不是"一个词"）：把大小写/分隔符/派生缩写**全列出来**再动手。
   本仓实测品牌串有 **7 种形态**（`design-canvas` / `.design-canvas` / `DESIGN_CANVAS` /
   `design_canvas` / `DesignCanvas` / `DC_` / `dc-`），**漏一种就是半成品**。
   ```bash
   for p in 'design-canvas' 'DESIGN_CANVAS' 'design_canvas' 'DesignCanvas' 'DC_' 'dc-'; do
     printf "%s : %s\n" "$p" "$(grep -rIl "$p" src tests scripts docs README.md AGENTS.md package.json | wc -l)"
   done
   ```
2. **复用"判断"，别新造工具**：本仓 `rename_symbols` 的 `report_literals`/`apply_literals` 已带
   `decideLiteral(kind, …)` —— `contract`=需人审 / `history`=保留 / 冻结行跳过 / 生成文件跳过。
   品牌串**不是符号**，所以要**给工具开一个显式字面量入口**（能力补齐），而不是再写一个工具。
3. **先建"残留门"**（棘轮：存量不拦、新增即红）+ **history 允许表** ——
   本仓惯例：**历史决策/核验记录保留旧名是正确原貌**，不算残留。
4. **改产物与契约**：`package.json`（name/bin/repository/bugs/homepage）、README/AGENTS/skills、
   MCP server key、git remote、桥接。
5. **兼容 + 重桥 + 收紧冻结**：旧名回退生效一段时间；重连下游；残留门 frozen 逐笔收紧到 **0**。

### 8.3 判"死代码"要**按模块说明符**查，且覆盖后缀变体

删任何文件之前，逐模块查引用 —— **我前三轮查错了三次**，三个坑都会导致误判：

```bash
# 对每个候选模块 m（注意 \(\.js\)\? —— 本仓测试里的 import 有的写 .js、有的不写！）
grep -rIn "['\"][^'\"]*/$m\(\.js\)\?['\"]" src tests --include=*.ts --include=*.mjs
```

| 坑 | 后果 |
|---|---|
| **按 basename 裸查** | 噪声极大（`daemon`/`serve` 这种词到处都是）⇒ 满屏假引用 |
| **只查 `src`** | 漏掉"**只被测试引用**"这一类（同样不是活代码，但是**另一类**，要单独决策） |
| **只查带 `.js` 的说明符** | 本仓两种写法混用 ⇒ 漏掉一半引用 ⇒ **删错就炸** |
| 用 `grep -c "import"` 当引用数 | 那是"数含 import 字样的行"，不是证据 |

**四类判定**（`orphan_file` 只回答"没有 import 边"，**不回答"该不该删"**）：

| 判定 | 依据 | 处置 |
|---|---|---|
| **真零引用** | src / 测试 / 字符串三处都没有 | ✅ 直接剪（删后 `tsc` 0 错误是第二证据） |
| **只被自己的测试引用** | 一个测试 import 它，src 零引用 | ⚠️ 测试自舔 ⇒ 要连测试一起删，单独一批决策 |
| **静态边看不见的用途** | 被 `package.json` scripts / 动态 `import()` / **文档契约** 点名 | ❌ **不删**（同 P0-② 的可达根问题） |
| **barrel（`index.ts`）无人 import** | 纯再导出且零引用 | ✅ 可剪 |

★ 实例（本仓）：`view_inputs.ts` 只被自己的测试引用，**但 README 明写它是"不受挂起影响的中性数据层，
仍由 CI 守着"** ⇒ 是**有意保留的契约表面**，不删。**删之前一定要查文档/契约有没有点名保留它。**

### 8.4 排序纪律（★ 与"搬移"不要交错）

**改内容与改位置都触及几乎每个文件 ⇒ 一次只做一件**，且：

- **先改名、后搬移**更好：改名自己的判据是 **"除品牌串外逐字相同"**，在文件**未被移动**时 diff 最可读；
  先搬 200 个文件再改名，判据会被 move 噪音淹没。
- 改名前确认"**不改工具名**"或"改了并有墓碑机制"（否则 G1 会红，见 §4.6 与规划书 §9-F2）。

### 8.5 ★★ 改名实操：六条（2026-09-28 实战，`DesignCanvas → AgentIO`，176 文件 / 617 处）

1. **先量**：清点**逐形态**命中 + 逐文件数，并**把歧义形态单独列出人审**。
   ★ 只数一个总命中数没有用 —— 实测 7 种形态里 `DC_`/`dc-` 的性质与另外 5 种**完全不同**。
2. **有序映射**，形态按"最长/最具体优先"；**需要边界的形态单走正则**
   （`(?<![A-Za-z0-9_])DC_` —— 裸子串替换会误伤 `SOME_DC_X`）。
3. **生成物不手改**：本仓涉及 `AGENTS.md`、`*.gen.ts`、`schema/*.json`、`package-lock.json`。
   改**生成器源码**后重算（`npm run build` / `npm run gen:schema` / `npm install --package-lock-only`）。
   ★ **交叉验证**：若基线文件（如 G1/G8 快照）恰好也被替换带到新名，**另行用官方重算命令重算并比对哈希**
   —— 哈希一致才证明"文本替换 == 正规重算"；不一致说明有别的真相源。
4. ★★ **门的"什么算文本"必须内容嗅探，不能是扩展名白名单**。实测白名单漏掉三处：
   `.gitignore`（无扩展名）、`go-observe/go.mod` 与 `go-slim/go.mod`（`.mod`）——
   **它们既没被改名、门也照样绿**。判据：前 8KB 无 NUL 字节 ⇒ 当文本。
   教训：**"手抄的清单"代替"可判定的规则"，就是这个项目的病根，它连门自己都没放过。**
5. ★★ **"不需要兼容层" ≠ "没有下游"**：这两步的取证强度完全不同，别合并成一句。
   先真的去量下游（`ls /d/project_develop/*/` + 逐仓 `grep -rIl <品牌>`，再逐个看**耦合方式**：
   是按路径 import？走 HTTP？还是只是文档里的字符串？）。本仓实测 4 个真实使用方，
   结论仍是"不做兼容层"，但**理由要写成"没有下游依赖旧名继续可用"**，并列出迁移清单。
6. ★ **改名会 un-hide 被 ignore 规则遮住的东西**：本仓 `.gitignore` 里 `.design-canvas/` 与
   `design-canvas.json` 是**无路径前缀**规则（匹配任意层级）⇒ 改名后规则不再匹配，
   原先被遮住的产物**立刻出现在 `git status`**（实测：根活态 DSL 要 `mv`、`src/` 下有个游离 `cache.db`）。
   ⇒ 改名收尾**必看 `git status` 的 untracked**，逐个判"迁移 / 删除"。

## 9. ★ 目录约定即索引（替代"再生成一份资产清单"）

**背景**：用户指出"遍地是脚手架，而 agent 上下文一压缩就忘、然后又做一遍"。
我最初提议**再生成一份「仓库资产地图」**（扩展 `gen_agents.mjs`）—— ★ **该提议被用户否掉，是对的**：
**为了管理乱而再加一层，那不是清乱、是把乱编目**（与本项目自己批的"兼容层"同一个动作）。
⇒ 改成的做法：**用目录名当索引，零新机制**。

| 目录 | 放什么 | 规矩 |
|---|---|---|
| `scripts/` | **产品链脚本**（build / setup / 门 / 生成器） | 长期维护，进 `package.json` 或文档 |
| `scripts/mcp/` | **MCP 驱动**（`mcp_smoke.mjs` 握手冒烟 / `mcp_call.mjs` 单次调任意工具） | ★ **必须路径无关**（取 argv/cwd，不硬编码本仓路径） |
| `tests/probes/` | **门的出生证探针**（可选） | 见 §4.11；**趋势是做共享 helper，而不是每门一个脚本** |

★★ **`scripts/oneoff/` 已撤销（2026-09-28，同日二次判定）**
原约定是"一次性脚本用完丢这儿、**留作可复现证据**"。实测证伪了它：
- 那 12 个脚本**全仓零引用**（grep 证实）；
- 多数依赖 **当时** 的 `dist/` + `.agent-io/` 状态（如 `sim_gap.mjs` 读 `.agent-io/mindmap/*.teach.json`）⇒ **很快就不跑不通**；
- 其中 `probe_mcp_smoke.mjs` 已被 `scripts/mcp/mcp_smoke.mjs` **取代**（留着一份旧版＝两份实现）；
⇒ 结果就是"**留了却不记得**"的墓碑 —— 正是用户点过的病（"上下文一压缩就会忘，然后重做一遍"）。

**★ 新约定：一次性脚本用完即删。** 若某步诊断**确实值得留**，二选一（都不许原样落一份脚本）：
1. 转成 `tests/` 下的**测试**（能复跑、能判红）；
2. 转成 `scripts/mcp/` 或 `scripts/` 下的**路径无关驱动**（长期维护、进文档）。

★ 账（2026-09-28 执行 + 同日修正）：仓库根下 12 个散落脚本 → `scripts/oneoff/`（根下现为 0）；
2 个真复用的 MCP 驱动**改成路径无关后进仓**（`scripts/mcp/`）；其余仓外脚手架**不搬**（见 §18.6）。
★ **同日稍晚复核后把 `scripts/oneoff/` 本身也撤掉** ⇒ 仓库根与 `scripts/` 下**现均无一次性脚本**（详见 plan §28.1）。

### 9.1 ★ 仍然欠的一条：把"出生证"做成**共享 helper**（而不是每扇门一个一次性探针）
现状：我为每扇新门各写了一个探针脚本（`probe_brand_gate.mjs` / `probe_g7.mjs` / …）——
**那就是"同一种活各写一遍"**，正是用户的"每个工具一条干净线"要消灭的东西。
⇒ 应抽成**一个** helper：`expectGateGoesRed({ mutate, restore, expect })`（注入→跑门→断言红→还原），
   各门只需声明"注入什么、期望什么"。**这条已列 §18.6。**

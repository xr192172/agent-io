# 原则：不打补丁，收归原生结构（rewrite, not patch）

> ★★★ **用户 2026-10-16 重申的原则（逐字）**：
> *"**不要打补丁，而是直接重写**，就是说**把补丁收归进原生结构里面**，**有补丁说明你原来的设计有问题**，
> 那你就**重新连同这个补丁一起重新去设计这个东西**。**补丁只是一个兜底性的东西**，但是你把它重新写了以后，
> **未来就不会再出现这个是最好的**，而且**补丁的话，你以后改的话可能会漏看这个补丁**，
> 但是你把它**重新结构写进去了，你会得到一个更好、更优、更优雅的一个项目**。"*

## 一、判据：怎么认出"这是一块补丁"

| 症状 | 说明它是补丁 |
|---|---|
| ★ **别处要"记得"配合它**（如"记得剔除它"、"记得跑它"） | 说明规则没进结构，只在人/agent 的记忆里 |
| ★ **它生活在目标结构的"外面"**（另建的清单 / 另写的 runner / 另挂的字段） | 说明它不是原生属性 |
| ★ **同类问题再来一次时，你要"再加一条"** | ★★ 说明结构缺了一维（该加的是一维，不是一条） |
| ★ **它的存在需要注释解释"为什么要这样"** | 说明它与结构不自然 |

## 二、处置：收归（三步）

1. ★ **找出"它想补的那个结构缺陷"**（★ 不是"这条规则"，而是**缺的那一维**）；
2. ★★ **把那一维加进原生结构**（类型 / 字段 / 语义），★ **然后删掉补丁**；
3. ★ **跑门 + 证**（★ 收归是"重写"，**行为可能变** ⇒ 要重跑对拍，不是"小改"）。

## 三、★ 与"清单"的关系（★ 这里有个容易搞混的地方）

★★ **"清单要更细"（用户上午说的）与"不要打补丁"（用户现在说的）不矛盾，是前后两段**：
```
发现阶段：清单越细越好   ← 边界不是想出来的，是读/撞出来的（A1–A6、B1–B4）
收归阶段：清单越用越短   ← 每条被收归进结构 ⇒ 从清单里删掉（★★ 这才是终点）
```
⇒ ★★★ **所以清单的健康指标是"它在变短"**，而不是"它在变长"。
★ 一条清单条目**被收归之后必须从清单里删掉**（★ 否则清单自己就变成"会被漏看的补丁堆"）。
